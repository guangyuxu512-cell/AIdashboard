# 开发、集成与发布流程

## 1. 目的与术语

本流程把业务开发、集成验证和发布拆成可追溯的责任边界。`Green dev` 指已经通过 Gate 2、可作为新 Feature 起点的 `dev` 提交；它不是“本地能启动”的同义词。

本规范与根 `AGENTS.md` 同级生效。发生冲突时以根 `AGENTS.md` 的硬规则为准。

## 2. 分支与 Worktree

| 对象 | 角色 | 允许的变化 |
|---|---|---|
| `main` | 稳定/发布基线 | 仅接收通过 Release Gate 的 Green `dev` |
| `dev` | 唯一集成线 | 仅由 Integration Worktree 接收通过 Gate 2 的候选 |
| `feat/*` | 业务 Feature | 从最新 Green `dev` 创建，由 Feature Owner 完成开发与 Gate 1 |
| `hotfix/*` | 紧急修复 | 采用与 Feature 相同的 Gate；发布后按发布记录回流 |

- 不建立长期 `qa/*`、`test/*`、`review/*` 或第二条集成线。
- 一个 Worktree 只能绑定一个分支；同一分支不得在两个 Worktree 同时开发。
- 每个新 Feature 都从最新 Green `dev` 创建。长期存在的 AI 与 Mobile 分支已登记为 grandfathered 分支，不要求为迁移流程而 rebase、重建或改名。
- 文档与 `AGENTS.md` 是分支快照。执行当前任务只能读取当前 Worktree 的版本作为规则；其他 Worktree 只能作为历史或对照，不得替代当前分支事实。

## 3. Two-Gate 流程

```text
最新 Green dev
    ↓
Feature Worktree（实现、测试、文档）
    ↓ Gate 1：Feature Owner 自检与 Handoff
Integration Worktree（评审、集成、验证）
    ↓ Gate 2：通过后 --no-ff 合入 dev
Green dev
    ↓ Release Gate
main
```

### Gate 1：Feature Owner

Feature Owner 对候选的正确性负责。交接前必须：

- 完成该 Feature 的实现、相应测试和必要的契约/文档更新；
- 运行与改动匹配的验证，并记录命令和结果；
- 检查 `git diff --check`、工作树状态、未跟踪文件和允许的改动范围；
- 确认候选基于最新 Green `dev`，如需要同步，先由 Feature Owner 解决自身冲突与回归；
- 提交候选，并提供可审查的 Handoff。

Handoff 至少包含：Feature 名称与候选提交、目标 `dev` 基线、改动范围、契约/文档变化、Migration Slot（无则明确“无”）、使用的数据库、验证命令与结果、风险/回滚方式、未覆盖项。不得把密码、连接串、Token 或其他机密写入 Handoff。

### Gate 2：Integrator

Integrator 只在 Integration Worktree 操作：

1. 读取候选差异、Handoff、当前 `dev` 和工程文档；
2. 做只读工程审查，确认范围、边界、测试、文档、Migration Slot 和临时材料；
3. 在 `control_center_integration` 与 Integration 端口环境完成必要的集成验证；
4. 仅在候选通过时执行 `git merge --no-ff feat/*` 到 `dev`，再复验合并结果；
5. 推送 `origin/dev`，并将验证证据与结果回传给 Feature Owner。

Integrator 不是候选业务 Bug 的补救开发者。候选有业务缺陷、缺失测试、契约不完整、越过 Migration Slot 或污染环境时，直接拒绝并退回原 Feature Owner；不得在 Integration 分支补写业务功能以“救过”候选。

#### 桌面功能的真实 Electron 验收（Gate 2 硬门禁）

候选只要影响 Electron 壳、Preload / IPC、桌面桥接、平台登录窗口，或需要在已安装桌面客户端中使用的 Renderer 功能，Integrator 必须在 Gate 2 启动**唯一一个**真实 Electron，并完成与本次影响范围相符的实际操作验收。验收记录必须明确：

- Electron Renderer 指向 `http://127.0.0.1:5180`，Backend 为 `http://127.0.0.1:8100`，数据库为 `control_center_integration`；
- 正在验收的 Candidate SHA，以及 `--no-ff` 合入后的 `dev` SHA；合入后必须复验受影响操作；
- 实际执行过的页面/桌面操作、结果与未覆盖项。

浏览器 E2E、Production Build、单元测试或截图文件存在，均不能替代上述 Electron 实操。不得关闭、改接或复用用户正在使用的生产桌面客户端；必须遵守单实例约束。若当前环境没有安全完成 Electron 实操的能力，Gate 2 标记为阻塞，不得宣告通过或进入 Release Gate。

### Green dev 与失败处理

只有 Gate 2 通过、`dev` 已推送且工作树干净时，`dev` 才是 Green。合并后发现失败时：

- 尚未合入：拒绝候选，Feature Owner 在原 Feature 修复后重新走 Gate 1；
- 已进入共享 `dev`：以明确的 `git revert` 回退破坏性合并，并保留失败原因和验证记录；
- 禁止对共享 `dev` 使用 `git reset`、强推改写、未经审查的 rebase 或 cherry-pick。

## 4. Release Gate

Release Gate 以 Green `dev` 为唯一候选来源，至少确认：Gate 2 记录完整、对应测试/集成验证通过、Migration 与回滚方案明确、发布说明齐备、无未解释的环境或 Git 污染。通过后才可将 `dev` 合入 `main`；本规则不授权直接把 Feature、AI 或 Mobile 分支合入 `main`。

## 5. 文档、临时材料与 Git hygiene

- 契约、架构、运行和工作流变化必须与代码同一分支、同一提交链更新；文档是可审查的工程资产。
- 可共享的正式文档放在版本化 `docs/`；临时笔记和草稿只能放 `docs/_local/` 或 `docs/_drafts/`，两者均被 Git 忽略。
- `.env`、密钥、连接串、PID、日志、截图、build/test artifact、临时脚本和运行状态不得提交。Gate 1 与 Gate 2 都要检查它们是否清理或被忽略。
- 提交保持单一目的、可回滚，并只暂存本次允许路径；不得借工程流程提交业务代码、数据库或无关格式化。

## 6. 运行隔离

端口与数据库的权威登记见 `02-工程环境与工作树登记表.md`。Vite 一律显式端口并使用 `--strictPort`，端口冲突必须失败而非漂移。`.dev-runtime/` 的记录仅是 Main 偏置管理器的辅助信息；启动、停止或清理前必须同时核对实际进程、命令和端口占用。
