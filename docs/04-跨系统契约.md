# 跨系统契约

## Frontend ↔ Backend
以 Backend Pydantic/OpenAPI Contract 为权威来源。
Frontend 不自行发明字段。

## Frontend ↔ Electron
通过 Preload 暴露有限、类型化 API。
Renderer 不直接使用 Node/Electron 原生模块。

## Backend ↔ Worker
统一 Device Registration、Heartbeat、Claim、Lease、Task Status、Result、Logs、Artifacts。

Provider Discovery 也沿用同一 Task 链路。Worker 使用认证后的通用
`provider-inventory` Endpoint 上报最新成功快照，Backend 从 Worker Principal 取得
`device_id`；请求 Body 不携带可冒用的设备身份。Inventory 上报成功后才能完成 Task，
Discovery 失败保留旧快照。

只有执行目标为 `WORKER` 的 Action 才创建 Worker Task；`SERVER` Action 进入 Backend
Module / Service / Job。当前 Task 不增加 execution_target 数据库字段，目标由创建该
Action 的正式契约决定。

Credential Secret、Session payload 的未来下发必须附着于合法 Task，并校验 Shop 与 Device 授权；普通 Frontend Route 与 Worker 枚举接口均不得返回敏感原文。平台认证统一使用 `PlatformAuthAdapter`、`VerificationChallenge`、`VerificationProvider` 和 `SessionSnapshot` Contract，详见 `06-平台认证与Session架构.md`。

## Worker ↔ Skill/RPA
统一输入：
- task_id
- skill_id
- shop_id（需要时）
- params
- runtime context

统一输出：
- status
- result
- error_code
- error_message
- artifacts

禁止每个 RPA 自定义完全不同的通信格式。

Backend 只持有稳定 `skill_id`，不直接持有影刀应用名称。Worker Skill Registry 将
Skill 映射到 `runtime=rpa`、`provider=yingdao` 及本地应用 ID；应用映射缺失或不可用
时必须明确失败。

Worker 本地 `SkillDescriptor` 固定表达 `skill_id`、`display_name`、`runtime`、
`provider` 和 `version`，不得携带本地路径。当前仅定义类型和测试；Skill Inventory
上报与持久化等待首个真实业务 Skill，不提前建立空契约。

## Backend ↔ Platform

服务器平台请求使用明确业务语义的 Platform Connector，链路为：

```text
shop_id → 当前 ShopSession → 解密后的认证上下文 → Platform Adapter → HTTPX
```

业务 Service 不直接解密 payload、解析 Cookie 或拼通用原始请求。Connector 不读取
Management Login Profile，不暴露 Raw HTTP Proxy，也不得记录 Cookie、Token、
Authorization、Session payload 或完整请求 Header。只有真实接口证明确认需要时才引入
Request Signer；认证失败返回明确 `AUTH_INVALID`，不自动登录。

## Backend ↔ Integration

飞书、邮件、短信等从 `backend/app/integrations/` 通过显式 Adapter 接入 Backend Service。
Integration 不是业务数据库，也不得绕过 API/Service 让 Worker 直接读写外部表格。
