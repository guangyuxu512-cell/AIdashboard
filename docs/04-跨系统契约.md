# 跨系统契约

## Frontend ↔ Backend
以 Backend Pydantic/OpenAPI Contract 为权威来源。
Frontend 不自行发明字段。

## Frontend ↔ Electron
通过 Preload 暴露有限、类型化 API。
Renderer 不直接使用 Node/Electron 原生模块。

## Backend ↔ Worker
统一 Device Registration、Heartbeat、Claim、Lease、Task Status、Result、Logs、Artifacts。

Human Management Identity 与 Worker Identity 完全分离。Human 请求由 Backend 认证后解析
HumanPrincipal、Active Team Membership 与 ActorContext；Worker 仍只使用 Device Token 与
`X-Device-ID`。Task 创建前由 Human Scope 完成授权，Worker 领取 Task 后不解析 Membership 或
Human Data Scope。

Provider Discovery 也沿用同一 Task 链路。Worker 使用认证后的通用
`provider-inventory` Endpoint 上报最新成功快照，Backend 从 Worker Principal 取得
`device_id`；请求 Body 不携带可冒用的设备身份。Inventory 上报成功后才能完成 Task，
Discovery 失败保留旧快照。

只有执行目标为 `WORKER` 的 Action 才创建 Worker Task；`SERVER` Action 进入 Backend
Module / Service / Job。当前 Task 不增加 execution_target 数据库字段，目标由创建该
Action 的正式契约决定。

Credential Secret、Session payload 的未来下发必须附着于合法 Task，并校验 Shop 与 Device 授权；普通 Frontend Route 与 Worker 枚举接口均不得返回敏感原文。平台认证统一使用 `PlatformAuthAdapter`、`VerificationChallenge`、`VerificationProvider` 和 `SessionSnapshot` Contract，详见 `06-平台认证与Session架构.md`。

## Worker ↔ Skill/RPA
统一输入：
- task_id
- skill_id
- shop_id（需要时）
- params
- runtime context

统一输出：
- status
- result
- error_code
- error_message
- artifacts

禁止每个 RPA 自定义完全不同的通信格式。

Backend 只持有稳定 `skill_id`，不直接持有影刀应用名称。Worker Skill Registry 将
Skill 映射到 `runtime=rpa`、`provider=yingdao` 及本地应用 ID；应用映射缺失或不可用
时必须明确失败。

Worker 本地 `SkillDescriptor` 固定表达 `skill_id`、`display_name`、`runtime`、
`provider` 和 `version`，不得携带本地路径。Worker 已通过认证后的
`PUT /api/v1/worker/skill-capabilities` 上报替换式能力快照，Backend 以当前 Worker
Principal 的 `device_id` 持久化；Human 管理端通过
`GET /api/v1/devices/{device_id}/skill-capabilities` 在既有 Device Scope 内读取。
空快照、已持久化快照与“设备当前可执行”是不同事实：调用方仍须独立检查 Device 启用、
在线状态、Provider 可用性及正式业务 Skill 输入契约。

## Backend ↔ Platform

服务器平台请求使用明确业务语义的 Platform Connector，链路为：

```text
shop_id → 当前 ShopSession → 解密后的认证上下文 → Platform Adapter → HTTPX
```

业务 Service 不直接解密 payload、解析 Cookie 或拼通用原始请求。Connector 不读取
Management Login Profile，不暴露 Raw HTTP Proxy，也不得记录 Cookie、Token、
Authorization、Session payload 或完整请求 Header。只有真实接口证明确认需要时才引入
Request Signer；认证失败返回明确 `AUTH_INVALID`，不自动登录。

Session 恢复固定为：Frontend 获取 Backend Refresh Lease → Electron Main 使用本机 Management Login Profile 重新采集 → 携带 `expected_version` 提交新 payload → Backend 加密写入并立即健康验证 → 释放 Lease。Profile 不上传，payload 不经过 Renderer；超时、平台 5xx 或响应异常不得误标 Session invalid。

## Backend ↔ Integration

飞书、邮件、短信等从 `backend/app/integrations/` 通过显式 Adapter 接入 Backend Service。
Integration 不是业务数据库，也不得绕过 API/Service 让 Worker 直接读写外部表格。

## Device 生命周期契约

- `enabled=false, deleted_at=null`：Worker Token 仍有效，Heartbeat 与能力快照上报仍可用，但 Claim 新 Task 返回无任务。
- `deleted_at!=null`：所有 Worker Credential 已撤销；Heartbeat、Claim/Poll 与 Provider Inventory Upload 统一认证失败。
- 正常 Device List、Picker 与新建 Task 的目标选择默认排除软移除设备；历史 Task、Runtime、Inventory 继续引用原 Device UUID。
- 软移除前存在 `PENDING` 或 `RUNNING` Task 时返回稳定错误 `DEVICE_HAS_ACTIVE_TASKS`。

## Notification Integration 契约

Frontend 只把通知配置提交给 Backend；不得直接请求第三方 Webhook。Backend 的 `NotificationService` 按 `channel_type` 选择 Integration Adapter，并在业务状态成功提交后尝试发送。发送失败只写脱敏日志，不回滚 DeviceRuntime，也不会在后续 `OFFLINE → OFFLINE` reconcile 中重复补发。
