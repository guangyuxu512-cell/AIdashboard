# 跨系统契约

## Frontend ↔ Backend
以 Backend Pydantic/OpenAPI Contract 为权威来源。
Frontend 不自行发明字段。

## Frontend ↔ Electron
通过 Preload 暴露有限、类型化 API。
Renderer 不直接使用 Node/Electron 原生模块。

## Backend ↔ Worker
统一 Device Registration、Heartbeat、Claim、Lease、Task Status、Result、Logs、Artifacts。

只有执行目标为 `WORKER` 的 Action 才创建 Worker Task；`SERVER` Action 进入 Backend
Module / Service / Job。当前 Task 不增加 execution_target 数据库字段，目标由创建该
Action 的正式契约决定。

Credential Secret、Session payload 的未来下发必须附着于合法 Task，并校验 Shop 与 Device 授权；普通 Frontend Route 与 Worker 枚举接口均不得返回敏感原文。平台认证统一使用 `PlatformAuthAdapter`、`VerificationChallenge`、`VerificationProvider` 和 `SessionSnapshot` Contract，详见 `06-平台认证与Session架构.md`。

## Worker ↔ Skill/RPA
统一输入：
- task_id
- skill_id
- shop_id（需要时）
- params
- runtime context

统一输出：
- status
- result
- error_code
- error_message
- artifacts

禁止每个 RPA 自定义完全不同的通信格式。

Backend 只持有稳定 `skill_id`，不直接持有影刀应用名称。Worker Skill Registry 将
Skill 映射到 `runtime=rpa`、`provider=yingdao` 及本地应用 ID；应用映射缺失或不可用
时必须明确失败。
