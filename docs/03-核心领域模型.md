# 核心领域模型

第一阶段长期稳定实体：
- User
- Shop
- Device
- Task
- Skill

后续按需求增加：
- Credential
- Session
- Workflow
- Trigger
- Order
- Product
- Finance
- AIAnalysis

所有关系通过稳定 ID 建立。

明确可能是多对多的关系，不要写死成单字段。
例如 Shop ↔ Device 推荐 `shop_device_binding`，支持 PRIMARY、BACKUP、enabled。

## Access Foundation V1

管理平面的身份与归属基础为 `User → TeamMembership → Team`。Membership 分别保存
`role_code` 与 `data_scope`，禁止从 Role 推导 Scope。每个 Human 请求在认证后解析为小型、请求级
ActorContext；Worker Device Token 不参与该流程。

Phase A 只建立 Team、Membership 与 Scope Policy，不给 Shop、Asset、Task、Schedule 或 AI Job
增加 Ownership。Phase B 的 Team Scoped 业务实体统一使用 `team_id` 表示数据归属、
`created_by_user_id` 表示创建者；现有负责人字段不能兼任权限边界。

## Backend Core Domain V1

阶段 2A 正式建立 `User`、`Shop`、`Device` 与关系实体 `ShopDeviceBinding`。`Shop.owner_user_id` 可选关联负责人；Shop 与 Device 只通过关系实体关联，不在 Shop 上保存单一 `device_id`。一个 Shop 最多只能存在一个启用的 PRIMARY 绑定，BACKUP 可按关系独立管理。

## Authentication Domain V1

阶段 3A 正式建立 `PlatformCredential`、`ShopCredentialBinding`、`ShopSession`。Credential 不进入 Shop 字段：同一平台账号可通过 Binding 绑定多个 Shop，而当前每个 Shop 最多一个启用 Credential。ShopSession 每店铺维护一个带并发版本的加密认证快照；Browser Profile 仍属于 `Device × Shop` 的设备侧资源。
