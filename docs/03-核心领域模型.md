# 核心领域模型

第一阶段长期稳定实体：
- User
- Shop
- Device
- Task
- Skill

后续按需求增加：
- Credential
- Session
- Workflow
- Trigger
- Order
- Product
- Finance
- AIAnalysis

所有关系通过稳定 ID 建立。

明确可能是多对多的关系，不要写死成单字段。
例如 Shop ↔ Device 使用 `shop_device_binding` 表达执行资格与 `enabled`；不存在 PRIMARY、BACKUP、
默认唯一设备或“主设备/备用设备”语义。

## Access Foundation V1

管理平面的身份与归属基础为 `User → TeamMembership → Team`。每个 Human 请求在认证后解析为小型、
请求级 ActorContext；Worker Device Token 不参与该流程。当前权限 V1 的正式输入是超级账号身份、有效团队、
团队模块/店铺/设备授权及业务对象归属；`team_memberships.role_code`、`data_scope` 和
`membership_module_accesses` 仅保留历史升级、审计和最小旧接口读取兼容，新功能不得据此授予权限或推导范围。

Phase A 只建立 Team、Membership 与 Scope Policy，不给 Shop、Asset、Task、Schedule 或 AI Job
增加 Ownership。Phase B 的 Team Scoped 业务实体统一使用 `team_id` 表示数据归属、
`created_by_user_id` 表示创建者；现有负责人字段不能兼任权限边界。

## Backend Core Domain V1

阶段 2A 正式建立 `User`、`Shop`、`Device` 与关系实体 `ShopDeviceBinding`。`Shop.owner_user_id` 可选关联负责人；Shop 与 Device 只通过关系实体关联，不在 Shop 上保存单一 `device_id`。Binding 是普通可启停多对多执行资格：同一 Shop 可同时绑定多台 Device，连接配置不因 Team 授权复制。

## Authentication Domain V1

阶段 3A 正式建立 `PlatformCredential`、`ShopCredentialBinding`、`ShopSession`。Credential 不进入 Shop 字段：同一平台账号可通过 Binding 绑定多个 Shop，而当前每个 Shop 最多一个启用 Credential。ShopSession 每店铺维护一个带并发版本的加密认证快照；Browser Profile 仍属于 `Device × Shop` 的设备侧资源。
