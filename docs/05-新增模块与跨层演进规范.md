# 05-新增模块与跨层演进规范

## 1. 目的

本规范用于保证未来不断增加：

- 页面
- 后端模块
- 数据库表
- Worker Skill
- Electron 能力

时，不需要反复推翻已有架构。

原则：

> 新功能默认以“新增模块 + 复用现有契约和基础能力”的方式演进。

---

## 2. 新需求第一步：先分类

任何新增功能先判断属于：

### 新属性
例如：
- Shop 增加 remark。

优先扩展现有实体。

### 新实体
例如：
- Credential
- Session
- FinanceRecord

建立独立实体。

### 新关系
例如：
- Shop ↔ Device。

使用关系模型。

### 新业务动作
例如：
- 刷新 Cookie。
- 批量发布。

属于 Feature / Service / Skill。

### 新展示
例如：
- 店铺列表增加 Session 状态。

不应因此创建新的后端实体。

---

## 3. 新模块跨层映射

例如新增 Product Center：

```text
Frontend
entities/product
features/product-management
pages/products

Backend
modules/products

Database
products + migration

Permission
product.view
product.edit

API
Product Schema / endpoints
```

只有真正需要本地能力才修改 Electron。

只有真正需要设备执行才修改 Worker。

禁止每增加一个页面就同时修改四个子系统。

---

## 4. 前端新增规则

新增页面优先：

```text
Entity
↓
Feature
↓
Page
```

复用：
- Design Token
- Base UI
- Page Pattern
- Existing Query/API
- Existing Status Meta

禁止以一个巨大页面文件承载全部能力。

---

## 5. 后端新增规则

新增业务模块使用既定模块结构。

优先：
- 复用公共 Contract。
- 复用 Connector。
- 复用 Repository 模式。
- 复用 Error。
- 复用安全和 Storage。

禁止因一个模块建立第二套基础架构。

---

## 6. 数据库新增规则

数据库可持续演进。

必须：
- SQLAlchemy Model。
- Alembic Migration。
- 稳定 ID。
- 明确关系。
- 必要索引。

不要求提前建未来所有表。

禁止：
- 为暂时方便加入大量 JSON 万能字段代替明确模型。
- 通过名称建立长期关系。
- 无 Migration 改数据库。

---

## 7. API 契约先于前端猜测

新增跨前后端功能：

```text
确认业务模型
↓
定义 Backend Schema / OpenAPI
↓
Frontend 使用正式 Contract
↓
实现页面
```

前端不得因为后端还没完成就自创真实 API 字段。

Mock 必须模拟目标 Contract，而不是另一套结构。

---

## 8. Electron 新增能力条件

只有需要：

- 文件系统。
- 本地程序。
- OS。
- Worker 进程。
- Desktop API。

才进入 Electron。

普通业务功能不得因为运行在 Electron 中就通过 IPC 实现。

---

## 9. Worker 新增能力条件

只有需要：

- 本地电脑执行。
- RPA。
- Browser。
- Python Script。
- Node Runtime。
- EXE。

才进入 Worker。

单纯服务器请求或数据库业务不应经过 Worker。

---

## 10. 新增 Skill

一个 Skill 表示明确能力。

例如：

```text
douyin.publish_product
douyin.fetch_orders
douyin.refresh_session
```

避免一个 Skill 同时承担大量互不相关业务。

Workflow 负责组合多个 Skill。

---

## 11. 重构触发条件

以下情况才考虑结构性重构：

- 模块边界已经无法表达真实业务。
- 大量功能持续绕过现有抽象。
- 同一逻辑已形成多个实现。
- 现有 Contract 成为明显阻塞。
- 性能/部署出现已验证瓶颈。

禁止为了“可能未来需要”提前大重构。

---

## 12. 新增功能强制检查

每个新功能开始前确认：

- 属于哪个 Domain？
- 属于哪个子系统？
- 是属性、实体、关系还是动作？
- 已有组件能否复用？
- 已有第三方库能否复用？
- 已有 API/Schema 能否复用？
- 已有数据库实体能否扩展？
- 是否真的需要新公共抽象？
- 是否影响现有 Contract？
- 是否需要文档同步？

---

## 13. 完成标准

一个新增模块完成后应满足：

- 没有复制现有基础组件。
- 没有复制基础设施。
- 没有猜字段。
- 没有私有协议。
- 没有随机视觉规则。
- 没有跨层职责泄漏。
- API 契约清晰。
- Migration 可追踪。
- 验证通过。

这样项目才能持续新增，而不是每增加一个功能就扩大技术债。
