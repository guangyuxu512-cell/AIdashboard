# 项目边界

## 双执行路线

系统按具体 Action 的执行环境选择目标，而不是按页面或业务模块一刀切：

- `SERVER`：默认路线。适用于 AI 作图/分析、财务计算、经营报表、订单与商品
  数据处理、数据清洗、数据库业务及服务器平台 HTTP 请求。
- `WORKER`：只适用于依赖具体 Device Runtime 的自动化动作，包括影刀 RPA、
  本地 Python Script、Browser Profile、本地 Windows 软件及未来 EXE/Node。

Worker 不是整个中控台所有功能的执行入口。模块归属与模块中某个 Action 的执行
目标是两个概念：商品列表仍由 Backend + PostgreSQL 提供；若“上架商品”必须依赖
影刀，该动作才创建 Task 并交给 Worker。

## Frontend
负责 UI、交互、路由、客户端状态、服务端数据展示。
不负责数据库、本地进程、RPA、Credential 解密、服务器任务调度。

## Electron
负责桌面窗口、Preload、IPC、本地文件/目录、Worker 进程生命周期、打包升级。
不负责服务器业务数据、Worker 长任务逻辑、Vue 页面业务状态。

## Backend
负责用户、权限、店铺、设备、Credential、Session、Task、Workflow、Trigger、API、PostgreSQL、审计、数据中心、AI 分析入口。

承载 `SERVER` Action 的 Module / Service / Job，并为 `WORKER` Action 建立 Task，
但不直接操作影刀或执行电脑。

## Worker
负责设备注册、Heartbeat、Task Claim、Lease、Executor、RPA/Script 调用、日志、结果和附件回传。

只承载 `WORKER` Action，不接管普通服务器业务模块。

## AI
默认只做结构化数据分析。
非必要不得让 AI 进入确定性的调度、权限、任务状态和财务计算核心链路。

## 长期模块与数据归属

- Shop、Product、Order、Finance 等业务实体各自由所属模块拥有 Entity、Service、API、
  数据库表与 Frontend Feature，不进入万能业务 JSON 表。
- 页面元素、Selector、Skill 默认参数、等待/超时/重试和平台自动化参数属于
  Automation Config，不属于 Shop/Product 等业务数据。
- Skill Registry 拥有稳定 `skill_id` 与 Worker 本地实现映射；业务模块不得依赖影刀
  App ID、本地 Python/EXE 路径。
- 飞书、邮箱、短信、对象存储属于 Integration。飞书可作为通知、审批、人工确认或配置
  编辑入口，但 Backend + PostgreSQL 仍是权威来源。

认证边界继续保持：Credential 与 ShopSession 在 Server；Management Login Profile 在
管理电脑本地；Worker Browser Profile 在 Worker 电脑本地。Backend 平台 HTTP 请求只
读取服务器 ShopSession，不依赖当前某台管理电脑 Profile。
