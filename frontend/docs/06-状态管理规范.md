# 状态管理规范

## Pinia

适合：

- 当前用户
- 权限
- 主题
- 当前应用上下文
- Sidebar 状态
- Electron 桥接状态

Human Auth Store 保存当前人员摘要、Membership 列表、当前 Team 选择与恢复状态，但服务端 Cookie
才是登录事实。应用启动或刷新必须通过 `/auth/me` 恢复，禁止在 localStorage 保存 Raw Session
Token 或 `isLoggedIn=true`。localStorage 只按 `user_id` 保存最近一次经过 Membership 校验的 Team
ID；Frontend 发送 Team ID 只表达选择意图，Backend 仍负责授权校验。切换 Team 时统一 Reset Query
Cache：先移除上一个 Team 的数据，再由 Active Query 使用新 `X-Team-ID` 重取，禁止背景刷新期间继续
展示旧 Team 数据。退出或已登录 Session 失效时清空人员态、当前 User 的 Team 偏好与 Query Cache。

## TanStack Vue Query

主题继续由唯一 Theme Store 管理；存储键 `control-center.theme-mode` 不变，保存预设或 `system`，旧 light/dark 映射 graphite/midnight。无偏好默认 graphite。`resolvedPreset` 驱动 CSS 与 Provider / 图表，`resolvedTheme` 只表达 light/dark 与原生标题栏。主题切换不得重置业务 Query、筛选、分页或表单，也不发起保存、运行、同步、生成或采集。

适合：

- 店铺列表
- 任务列表
- 设备列表
- 订单
- 经营数据
- 服务端详情

## Component State

只属于当前组件。

## Form State

vee-validate + Zod。

禁止：

- 把服务端所有数据复制进 Pinia。
- 同一数据同时由 Query 和 Pinia 各存一份。
- 自制缓存刷新机制替代 Query。

## AI Workbench 客户端恢复状态

AI 工作台的即时生成与批量生成可在 Pinia 中分别保存草稿、输入 Asset ID、当前
`generation_job_id` 和提交回执恢复所需的稳定 `submission_key`。为支持同一浏览器刷新或重新打开，
这些客户端字段按 `user_id + active_team_id` 隔离写入 localStorage；必须等待 Human Auth 与 Active
Team 恢复后再读取。

任务详情、Item 状态、输出 Asset 与结果仍由 TanStack Vue Query 和正式 API 提供，不复制进 Pinia 或
localStorage。不得持久化图片二进制、Blob/Object URL、Cookie、Token 或 Provider 数据；恢复输入图时只
使用 Asset ID 重建正式鉴权内容地址。已知 Job ID 的恢复只执行详情 GET。提交回执中断时只能用原请求与
原 `submission_key` 走服务端幂等恢复，禁止生成新 Key 盲目重提。

退出登录、Session 失效或切换 Team 必须删除原 Actor Context 的工作台持久状态，并使清理前的异步响应
失效。普通页面刷新期间的 Auth Restore 不能被当作退出。用户清空当前工作方式时只清除该方式的客户端
草稿、任务引用和持久记录，不删除 Generation Job、Asset、Storage 文件，也不取消后台执行。

## Task Query 与 Runtime Event

- Task List Query Key 必须包含分页、状态、设备、搜索与 `created_from / created_to`，日期范围变化后回到第一页。
- Task List 有缓存时的 background refetch 继续显示旧数据；只有首次无缓存且请求失败才进入页面级 Error State。
- Runtime Event 首次读取最新窗口，向前翻页使用 `before_seq`；RUNNING Task 仅以最新 `seq` 作为 `after_seq` 增量游标。
- 多页事件按 `(task_id, seq)` 去重并保持升序，Drawer 只渲染有界数量；禁止把完整日志复制进 Pinia 或无限累积在组件状态中。
- Terminal Task 停止自动增量轮询；手工“加载更早”与后台增量刷新是两条独立 Query 行为。
