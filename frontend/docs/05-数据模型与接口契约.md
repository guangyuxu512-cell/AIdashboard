# 数据模型与接口契约

Backend Pydantic/OpenAPI 为 API Contract 权威来源。
Frontend 不得手写“看起来差不多”的字段。

建议通用分页：

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

建议错误模型：

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "任务不存在",
  "request_id": "..."
}
```

最终字段以正式后端契约为准。

- ID：统一 string。
- 时间：ISO 8601 传输，dayjs 显示。
- 金额：按后端精度契约展示。
- Page 不直接 axios。

推荐：

```text
shared/api/http-client
entities/shop/api
entities/device/api
entities/task/api
```

Mock / Real 必须使用相同 DTO 契约，禁止 Mock 自创另一套字段。

Logging & Audit V1 的管理员列表只调用
`GET /api/v1/access-management/audit-logs`。分页沿用 `items / total / page / page_size`；每行严格消费
`audit_log_id / request_id / actor_user_id / actor_display_name / team_id / action / target_type / target_id /
details / created_at`。可选筛选参数仅为 `created_from`、`created_to`、`actor_user_id` 和 `action`；首版
页面不预设高级筛选器。`details` 仅作为最小变更摘要显示，不得假设或渲染密码、Token、Cookie、完整
Request Body 或 Before/After 对象。

Human Auth Real Data Source 只调用 `/api/v1/auth/login`、`/auth/logout`、`/auth/me` 与
`/api/v1/access/me/teams`。统一 Axios Client 使用 `withCredentials=true` 接收 HttpOnly Cookie，
并集中附加当前 `X-Team-ID`；Page、Feature 和其它 Entity 不得自行解析 Cookie 或重复写 Header。
只有 `HUMAN_AUTHENTICATION_REQUIRED / HUMAN_SESSION_INVALID / HUMAN_USER_DISABLED` 会触发全局
Human Session 失效处理，普通业务 401 与 Worker 认证错误不能误清人员状态。

Frontend Mock 默认使用“管理员预览”身份，供系统设置等管理员视觉场景验证；只有
`VITE_API_MODE=mock` 使用该 Fixture。Mock 中以非 `admin` 登录名登录仍会得到普通成员上下文，
用于验证管理员路由拒绝；Real Mode 的身份与权限仍完全由 Backend Contract 决定。

API Mode 必须显式设置。`pnpm run dev` 显式使用 `mock`，`pnpm run dev:real` 显式使用 `real`，
`pnpm run build` 显式使用 `real`。Production Vite 配置在缺失、非法或非 `real` 的 API Mode 时立即
失败，绝不将 Production Bundle 静默降级到 Fixture Data Source；视觉回归使用独立的
`pnpm run build:visual-mock`。

AI 模型管理只调用 `/api/v1/ai-models` 的 List、Detail、Create、Update 与 Set Default 资源接口。
`entities/ai-model` 显式映射 snake_case DTO 与 camelCase ViewModel；`model_code / provider_code` 创建后
不进入 Update DTO。Frontend 不读取或缓存 API Key、Base URL、Secret 或 Provider Payload。

阶段 1A 的店铺中心尚未建立 Backend Contract。`ShopListItemViewModel` 及其 Fixture 是明确的前端展示模型，仅用于 Design System 与领域分层验证，不得被解释为 DTO、API Response 或数据库字段。未来接入真实接口时，应先建立正式 Contract，再在 Entity 层完成 DTO 到 View Model 的显式映射。

阶段 1B 的 `DeviceListItemViewModel`、资源摘要、最近心跳、Worker 版本和执行能力同样只属于 Frontend Fixture。它们不是设备注册协议、Heartbeat Contract、Worker Capability Contract 或数据库模型。

## 阶段 2B Mock / Real Data Source

`/shops`、`/devices` 使用同一 Page 与 ViewModel，通过 `VITE_API_MODE=mock|real` 在 Entity Data Source 层切换。Page 不判断模式，不直接调用 Axios。

统一数据流：

```text
Page
↓
Feature Management Composable
↓
TanStack Vue Query
↓
Entity Data Source / Mapper / API
↓
shared/api/http-client
↓
FastAPI
```

Real Mode 的正式 DTO 字段严格来自 Backend Pydantic/OpenAPI：

- Shop：`shop_id`、`display_name`、`platform`、`enabled`、`owner_user_id`、`note`、`deleted_at`、`created_at`、`updated_at`；List 额外投影可空 `session_status`。
- Device：`device_id`、`display_name`、`enabled`、`location`、`note`、`created_at`、`updated_at`。
- Device 生命周期补充 `deleted_at`；普通列表不会返回已移除设备。`enabled=false` 与 Worker OFFLINE 是独立事实。
- Binding：`shop_id`、`device_id`、`enabled` 与时间字段；只表示执行资格，不含主备角色。
- 分页：`items`、`total`、`page`、`page_size`。

Shop 负责人名称由正式 Users API 在 Mapper 中解析；执行设备由正式 Binding API 与 Devices API
组合为普通多设备集合。同一个 Shop 可绑定多台 Device，不选择主设备。Backend 未提供的 GMV、
订单数据不进入店铺列表 ViewModel；操作记录只显示空态，不伪装自动化、同步或 Audit 数据。

`platform_shop_id` 非空表示 Shop 已由平台识别建立。此时 `display_name`（平台真实店铺名称）、`platform` 与 `platform_shop_id` 是只读身份：编辑表单只展示，Frontend Update Mapper 不发送这些字段，Backend 仍负责拒绝越权更新。`Shop.enabled` 继续表示 Shop 领域中的启用状态，明确不等于店铺自动化总开关。

Shop Center 最终生命周期语义：

- `Shop.enabled`：店铺业务启用状态；已停用仍保留 Shop、Credential、Session 与历史数据。
- `Shop.deleted_at`：软移除状态；正常 List、Picker 和业务查询不再返回该 Shop。
- `automation_enabled`：当前不存在，Frontend 禁止用 `Shop.enabled` 冒充自动化总开关。
- 单店“移除”调用正式软删除 API；当前不提供批量移除 UI。

店铺列表登录状态直接消费 `ShopListRead.session_status`：`null → 未登录`、`captured → 待验证`、`valid → 有效`、`invalid → 已失效`；既有 `refresh_required → 需要刷新` 继续使用统一 Session 状态元数据。列表不读取 Cookie、Token、Session Version 或 Profile 路径。

Shop Drawer 的设备管理复用既有 Device List 和 Shop Device Binding Contract。绑定只表示该设备
可执行该店铺；解绑使用 `enabled=false`，不发明 DELETE，也不再维护 PRIMARY/BACKUP 或唯一主设备。

阶段 2D-1 店铺列表的平台、启用状态、负责人和关键词均为“当前页前端筛选”。它们不进入 Real API Query Param，也不改变服务端 `total`。当前正式平台只来自 Backend Contract：`douyin`、`pdd`。

Device 的 `enabled` 只映射为“已启用/已停用”，不得映射为 ONLINE/OFFLINE。Worker
ONLINE/OFFLINE、版本和最近心跳来自正式 `worker_runtime`；CPU、内存和当前任务未在
Device Contract 提供时不得伪造遥测或活动任务。列表与 Drawer 对缺失的当前执行统一显示 `—`，不使用“未提供”充当业务状态。

NotificationChannel Read Model 只包含通道类型、名称、启用状态、事件开关与 `webhook_configured`。完整 Webhook URL 只在 Create/Update Mutation 输入中短暂存在；编辑已有通道时空值表示保留服务端 Secret。

设备中心执行状态语义分离：`空闲 / 待执行 / 执行中` 只描述当前活动任务；`成功 / 失败 / 丢失或中断` 只描述最近执行结果，禁止把终态映射为当前执行。历史任务由正式 Task List Contract 查询，Frontend 不得生成示例记录冒充真实历史。

设备列表中的影刀账号、应用数量来自 Provider Inventory；绑定店铺数量由现有 Shop Device Binding 组合统计。影刀应用数量表示 6.3.6 当前登录账号通过本地会话 API 可访问的云端应用，不再表示本机 `user.db3` 缓存数量。

阶段 3B-1A 的影刀环境来自
`GET /api/v1/devices/{device_id}/provider-inventories` 的最新成功快照。Frontend 通过
Task API 创建 `yingdao.discover` 并轮询终态；SUCCESS 后只 invalidate Provider
Inventory Query。影刀可用状态与 Worker 在线状态是两个独立字段。应用列表 DTO 展示
App 名称与 App ID；`versionId` 等 Provider 元数据不作为主表列，也不等于中控台 Skill。

应用列表提供复制 App ID、配置和运行。参数配置调用
`/api/v1/automation-app-configs/yingdao/{app_id}`，V1 只维护手工 text/number/boolean/select
Schema；Frontend 不推断影刀 detail 响应。运行统一创建 `yingdao.app.run` Task，input 为
`app_id + params`，并通过独立 `shop_ids` 选择本次使用的有序店铺集合；禁止把账号或 Shop 关系
混入 Skill input。选择器只读取当前 Device 的有效 Binding，打开时默认全选，至少保留一项，
最终只创建一个 Task。成功创建后立即打开复用的 `TaskRuntimeDrawer`。Task Read 可显示关系 ID，但
Frontend 不读取 Claim 的 `accounts` 明文。

图片资料库 Entity 严格消费 Backend Asset DTO：`asset_id / media_type / source_type /
original_filename / content_type / size_bytes / sha256 / created_at`。`media_type` 表达媒体类型，
`source_type` 表达资产进入系统的来源，二者均不替代真实 MIME `content_type`。当前资料库仍只上传、
展示与选择图片；Frontend 只在 Contract 层保留未来媒体扩展语义，不提前增加 VIDEO UI。每个真实 Asset
分别构造原图 `/content` 与卡片缩略图 `/thumbnail` URL：`previewUrl/contentUrl` 始终保留原图，用于下载、
放大查看和 AI 输入；`thumbnailUrl` 只用于资料库、选择器、素材格、即时/批量结果和生成记录的卡片显示。
两类请求都经统一 Axios Client 获取 Blob，确保 HttpOnly Cookie 与 `X-Team-ID` 生效，再创建短期 Object
URL；缩略图组件只在进入视口后发请求，失败显示显式重试，并在组件失活时撤销 Blob URL。不能用普通
`<img src>` 直接访问受 Active Team 保护的接口，也不读取或猜测 `storage_key`。视频缩略图仍未实现。
即时“运行应用”Dialog 使用同一 Asset Query 选择图片；图片默认不选，允许有序多选、移除单张与
清空，最终只把 `asset_ids` 作为 Task 的独立关系字段提交。多店铺与多图片仍只创建一个 Task，
图片 Base64、下载 URL 和服务端路径不得进入 `input`。Scheduler 本阶段不提供图片选择。

设备 Skill 能力来自 `GET /api/v1/devices/{device_id}/skill-capabilities`，Frontend 不写死
`yingdao.app.run`、`system.echo` 等列表。Skill Capability 与 Provider Inventory 分开查询：
前者表达 Worker Registry 已实现能力，后者表达影刀是否 READY 及当前账号可访问的 Application。
设备离线时 Skill 列表显示最后已知能力，但即时运行按钮不可用。

Skill Capability DTO 的 `classification` 为 `internal | business | null`。Frontend 保留完整
Capability 集合供 Application 运行条件判断，只将明确为 `business` 的记录计入并展示为
“业务 Skill”；`internal` 和无法可靠分类的旧记录不进入普通业务列表。过滤后为零属于成功空态，
不是请求失败。Frontend 禁止根据 Skill ID 或前缀自行推断分类。

Business Skill Catalog 使用 `GET /api/v1/devices/{device_id}/business-skills`，按 Device 查询真实
业务能力。Input Schema 来自 Worker Pydantic Input Model，经 Backend 规范化后由通用
`SchemaParameterFields` 消费；Frontend 不维护 Skill 清单或参数副本。Catalog 明确区分
available、schema unavailable 与 schema unsupported：后两者可以展示，但不能开放 Scheduler
参数配置。支持的 V1 字段为 string/integer/number/boolean/enum 及 required/default/title/
description；复杂 Schema 显示“不支持”，不得静默错误渲染。

设备当前执行使用正式 Active Task Summary：没有活动 Task 显示“空闲”，PENDING 显示
“待执行”，RUNNING 显示“执行中”。执行对象优先使用 Backend 在 Task 创建时保存并返回的
`execution_display_name`；兼容旧数据时才依次使用 Runtime Event App 名与 `skill_id`。
Device 主表固定为单行“状态 + 执行对象 + 详情”，不显示当前步骤或最新日志；详细阶段、步骤
与增量事件只进入复用的 `TaskRuntimeDrawer`。Task Events 使用有界 seq 游标：首次读取最新一页，
向前翻页使用 `before_seq`，RUNNING 增量轮询使用 `after_seq`。单次请求和前端渲染均有上限，
禁止一次加载完整历史。

Task List 的创建时间查询使用半开区间 `[created_from, created_to)`，参数均为带时区的 ISO 8601
时间。任务中心默认最近 7 个自然日；今天、昨天、最近 30 天、自定义和全部仅在 Frontend
转换为明确的起止时间，不改变 Backend 的 `Task.created_at` 查询语义。

Task 永久保留，Runtime Event 按 Backend 保留策略清理。`runtime_events_purged_at` 表示该 Task
的历史事件曾被保留策略清理；它与“从未产生事件”是不同语义。清理后又收到晚到事件时，
Frontend 必须显示“较早日志已清理”的部分历史提示，并继续展示仍存在的事件。

Device 主列表、Active Task、Provider Inventory、Binding 等自动刷新在已有数据时必须保留
previous data；只有首次无缓存使用 Loading。已有缓存后的后台失败保留当前内容并局部降级，
不得清空列表或显示页面级 ErrorState。Device 行键固定使用 `device_id`，不得使用索引、Task
或排序位置。

Worker 凭证 DTO 只包含 Device ID、`not_issued / issued / revoked` 和签发时间。签发/轮换
Mutation 的 Token 明文只保存在短生命周期本地状态并显示一次，关闭 Dialog 立即清除，不进入
TanStack Query Cache。Frontend 不读取 Token Hash，也没有“查看旧 Token”能力。

Backend V1 列表仅支持 `page`、`page_size`，Real Mode 不发送 Fixture 筛选字段或虚构 Query Param。

## Platform Registry 与 Backend Contract

`entities/platform` 是前端平台名称、图标、导航和选择支持状态的唯一来源，但不是 Backend Contract。Registry 的 `registered` 与各项 capability 必须与真实 OpenAPI 能力区分：当前 Legacy Shop Create 仍只允许 `douyin`、`pdd`；淘宝、视频号可以展示，但 Legacy Create Select 必须禁用。不得因为 Registry 存在平台就扩展 DTO、Query Param 或数据库枚举。

店铺平台栏仍只对已加载的当前页 ViewModel 做 client-side filter；Backend 未声明平台筛选参数前不得伪装 Server Filter。

## Credential / ShopSession

`entities/credential` 与 `entities/shop-session` 分别维护正式 DTO、Data Source、Query 和安全 ViewModel：

- Credential Read 只有脱敏登录账号、密码已配置状态、启用状态、验证码渠道和更新时间。
- 密码只存在于提交 Form 到 Mutation 的短生命周期输入中；Query Cache 和 ViewModel 不得出现密码字段。
- 已配置凭证更新时，空账号/空密码不发送给 Backend，表示保留原值。
- ShopSession 只展示状态、版本、来源设备和采集/验证/过期时间，不定义 Cookie 或 payload 字段。
- Drawer 可调用健康检查、获取恢复 Lease，并通过类型化 Electron Bridge 启动本机 Profile 恢复；Renderer 只持有 lease ID、expected version 和状态元数据，不持有 Session payload。
- “验证中”“正在恢复”是前端流程状态，不扩展数据库 Session Status。恢复成功后重新拉取 Backend 元数据并显示新版本。

Frontend 不提供完整密码/Cookie 查看、复制或导出能力。
