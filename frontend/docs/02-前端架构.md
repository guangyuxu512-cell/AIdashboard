# 前端架构

数据流：

```text
Page
↓
Feature / Entity composable
↓
Query / API
↓
shared/http-client
↓
Backend
```

- 客户端状态：Pinia。
- 服务端状态：TanStack Vue Query。
- HTTP：统一 Axios Client。
- 类型：避免 `any`，使用正式契约。
- 错误：统一错误类型与全局请求错误入口。

页面不得直接创建 Axios 实例。

## Module Registry Lite

`src/app/modules/registry.ts` 是现有应用模块的导航与模块元数据唯一来源，表达
`moduleCode`、名称、导航分组、显式路由、图标、启用状态、权限码和顺序。Router 保持
显式 Page 配置，但从 Registry 读取 route/module metadata；Sidebar 不再维护第二份菜单
常量。权限系统尚未落地时 `permissionCode` 必须显式为 `null`，不得提前编造权限码。

Registry 同时负责可折叠导航组。当前 `自动化中心` 只是一层无路由的导航分组，子项为
`设备中心 / 任务中心 / 定时计划 / 参数配置`；不得为分组创建空首页，也不得在 Sidebar 另写第二份 children。
稳定路由分别为 `/devices`、`/tasks`、`/schedules`、`/parameter-presets`。员工权限尚未落地，Schedule 的
`permissionCode` 继续显式为 `null`，不得用预想字符串冒充真实权限契约。

`parameter-preset` 是独立的前端路由标识，但当前 Backend 没有同名 ModuleCode：Registry 通过
`accessModuleCode: 'device'` 复用既有 Device Guard，导航过滤和 Router Guard 都必须调用
`getModuleAccessCode`。该别名不出现在成员模块权限配置中，也不新增 Backend 权限或扩大可见数据。

`operating-dashboard` 是“数据中心”下的独立前端路由标识。它通过
`accessModuleCode: 'shop'` 复用现有 Shop Guard，而不新增未经定义的 Data Center 权限码；该别名不进入
成员权限配置。经营数据的正式 Read/Collection API 也使用同一 Backend Module Guard，并在数据库查询前
应用当前 Actor 的 Shop Scope；路由可见性不替代服务端授权。

经营看板 Feature 同时维护两个显式数据源：`VITE_API_MODE=mock` 只用于 UI Fixture；Real 模式只调用
`/api/v1/operating-dashboard`，不把 Shop 列表伪装成经营数据，也不在请求失败时回退 Mock。后端返回的
`collection_available` 是环境执行开关：为 false 时页面仍可读取已持久化数据，但“更新数据”必须明确禁用，
不能创建永远不执行的平台采集任务。

Registry 只登记已经存在的模块。新增业务模块时先完成 Page/Route，再注册定义；不得为
未获明确范围授权的未来模块创建空页面。本期用户明确授权商品中心 UI_ONLY：只登记
`product-selection`、`product-library` 两个页面，不提前建立商品实体、API、表格或后续功能。

## 系统通知配置边界

通知配置使用 `entities/notification-channel` 表达无 Secret 的读取模型，`features/notification-settings` 编排保存和测试，`pages/settings` 只负责页面组合。Webhook URL 只存在于提交表单的短生命周期输入，禁止进入 ViewModel、Query Cache 或持久 Store。
