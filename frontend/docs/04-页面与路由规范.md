# 页面与路由规范

## 工程初始化路由

阶段 0B 提供 `/` Design System 验证路由，用于验证 Renderer、AppShell、基础组件和页面模式。阶段 1A、1B 分别引入 `/shops` 店铺中心和 `/devices` 设备中心路由；阶段 2B 起两页通过统一 Data Source 支持 Frontend Fixture 与 FastAPI Real API，不连接 Worker 或虚构实时运行数据。

阶段 3D-1 通过 Module Registry Lite 正式注册 `/settings/notifications`“系统设置”。Access
Management V1 在同一系统设置内增加 `/settings/users`“用户与权限”：只有当前 Team Context 的
`access_admin` 可访问；“通知配置”仍要求 `settings` 模块访问。设置内导航从当前权限状态生成，
不预建 AI、存储、安全或平台配置空页面。

Logging & Audit V1 在同一设置内增加 `/settings/audit-logs`“操作日志”。它与“用户与权限”同样
仅对当前 Team Context 的 `access_admin` 可见和可访问；页面只显示关键管理变更的紧凑分页表格，
不建立日志 Dashboard、实时滚动、全文搜索或告警中心。

Task Center V1 正式注册 `/tasks`。导航由同一 Module Registry 形成
`自动化中心 → 设备中心 / 任务中心 / 定时计划`；`自动化中心` 无独立 Route，既有 `/devices`
与 `/tasks` 路由继续兼容。任务中心只观察现有 Task，不提供创建、取消、重试或删除入口；
Scheduler V1 使用独立 `/schedules` 管理页，生成的 Task 天然进入原任务中心。

图片资料库 V1 通过 Module Registry 注册顶层 `/assets`“资料库”入口，直接进入紧凑图片列表，
不建立“资料中心首页”空壳或二级目录。页面只提供上传、文件名搜索、分页、预览与删除；已被
Task 引用的图片由 Backend 拒绝删除。

AI 工作台 V1 通过 Module Registry 注册一个顶层“AI工作台”入口，默认进入
`/ai-workbench/generate`，模块内使用独立路由 `/ai-workbench/assets`、
`/ai-workbench/templates` 与 `/ai-workbench/records` 切换 AI生图、素材库、模板库和生成记录。四个页面共享 AI 模块页面壳，并通过
通用 `ContextSwitchBar` 呈现顶部切换；该导航同时承担当前页面身份，不重复渲染 Page Title 或
Page Subtitle。AI生图保持左侧设置与右侧结果双栏，素材库和模板库保持工具栏与内容区的正式
管理结构。该模块不展示平台切换，只复用现有 AppShell、Design Token 与页面模式组件，不建立
单页专属 Token 或设计规范。正式 UI 默认只呈现名称、值、状态、操作与单行 Empty State，开发
解释仅保留在代码注释或文档中；工作台通过固定外壳与明确的 Pane 局部滚动保持单一滚动边界，不产生 Document Scroll 或横向溢出。V1 只实现 Frontend 业务视图与开发态交互，不触碰
Backend、Worker、数据库或 Migration。

AI Generation Workspace V1（含 Instant Result Viewer V1 与 Batch Result Viewer V1）和 Generation Records V1 均为 **Frozen（已冻结）**：正式路由只呈现工作台与空数据，Development 下仅精确 `?visualMock=1` 加载交互 Fixture；Production 不包含 Fixture，不建立 Mock Fallback，也不接入 Generation、Provider 或任务队列 API。

AI Assets Library V1 已完成正式前端交互并标记为 **Frozen（已冻结）**；冻结契约、Template Library 复用边界与未冻结范围统一记录于 `10-页面模式与复用规范.md`。后续模板库实现不得顺手修改该 Frozen Contract。

AI Template Library V1 的单一提示词契约定向解冻已验收完成，当前为 **Frozen（已重新冻结）**。`/ai-workbench/templates` 保持正式 Empty State，仅 Development 下精确 `?visualMock=1` 加载三栏交互 Fixture；Production 不加载 Fixture，不建立 Mock Fallback，也不接入 Template、Generation 或 Provider API。Frozen Scope 与未冻结范围统一记录于 `10-页面模式与复用规范.md`。

Human Auth V1 注册公开 `/login` 认证布局。除明确 `meta.public` 的认证页外，PC 业务路由统一经过
Auth Guard：先向 Backend 恢复服务端人员会话，无有效会话时携带安全站内 Redirect 返回登录页；
多 Team 且没有有效 Team 选择时停留在登录页的 Team 选择步骤。Router Guard 只提供页面体验，
不能替代 Backend 的 Human Principal、ActorContext 与未来业务 Data Scope 校验。

Access Management V1 在会话与有效 Team 恢复后单独读取当前 Membership 的模块访问。Sidebar 从
现有 `app/modules/registry.ts` 过滤已授权的正式模块，路由同样拒绝未授权模块；development-only
`foundation` 不进入人员授权清单。`/settings/users` 额外要求 `access_admin`，拒绝时统一进入
`/permission-denied`；`/settings/audit-logs` 使用同一 Guard。Router Guard 不可替代 Backend：当前资料库已在服务端强制 `asset` 模块授权，
其它尚未采用 Human Management Plane 的历史业务 API 不因前端菜单隐藏而获得安全承诺。

阶段 2D-2 起普通列表管理页统一使用 Compact Management Pattern：`可选 Tab / Platform Bar → FilterBar + Primary Action → DataTable → PaginationBar`。这类页面默认不显示 PageHeader、Section 标题、固定说明或筛选字段顶部标签；Sidebar、Breadcrumb、业务切换栏和表格共同表达页面上下文。`/shops`、`/assets`、`/devices`、`/tasks`、`/schedules` 已采用该模式。

设备中心管理列表与店铺中心共用 `ManagementListSection`：页面、Section、Table Body 通过 `flex: 1 / min-height: 0` 消费剩余空间，分页固定在列表卡片底部。0 条、1 条和多条数据不得改变列表卡片高度或分页位置，也不得通过视口减法写死高度。

设备详情 Drawer 采用 `运行概览 → 执行能力 → 最近执行 → 更多信息`。运行概览表达当前状态和当前活动任务；最近执行只表达已经结束的任务结果。影刀作为首个 Capability Card，后续 Python、Browser、EXE 等 Provider 继续追加同类卡片，不得把 Drawer 退化为基础字段表格。

任务中心回答任务队列、执行设备、当前进度、最终结果和运行日志；设备中心只回答设备
是否具备执行能力及当前大致活动。任务详情统一打开既有 `TaskRuntimeDrawer`，不得新增
独立日志页或第二套 Drawer。运行日志始终依附 Task。

建议路由：

```text
/dashboard
/shops
/shops/:shopId
/devices
/devices/:deviceId
/tasks
/tasks/:taskId
/workflows
/data-center
/ai-analysis
/permissions
/audit
/settings
```

Page 负责：

- 路由参数
- 页面级 Query
- 页面区域编排
- Feature 组合

Sidebar、Breadcrumb 和 Route Metadata 统一从 `app/modules/registry.ts` 取得模块定义。
路由可以继续显式声明 lazy Page，但模块名称、路径、图标、启用状态、权限元数据和顺序
不得另建菜单常量重复维护。

## 店铺首次接入

`/shops` 的新增店铺 Drawer 使用 `选择平台 → 账号与密码 → 登录并识别 → 确认店铺 → 完成`。不再选择 Worker 设备，也不允许用户填写店铺名称。只有 Platform Registry 中 `shopOnboarding`、`authentication`、`sessionCapture` 均为 `available` 的平台可选择；阶段 3C-1 只有抖店。

密码只存在于 Drawer 组件内存，不能进入 Router、URL、localStorage 或 sessionStorage。Frontend 只通过类型化 `window.desktop.managementLogin` 获取状态和真实店铺身份，不能接触 Session payload。识别身份并采集 Session 后由 Electron Main 自动关闭平台窗口，确认页继续显示只读的平台店铺名称、平台店铺 ID、识别状态和会话状态；用户提前关闭则保持未完成并允许重新登录。只有点击完成且 Backend 原子闭环成功，列表才刷新。

Shop Drawer 的登录会话区紧凑展示状态、最近验证、版本和最近采集。`invalid` / `refresh_required` 提供“重新登录”，先获取 Backend Refresh Lease，再由 Electron 复用或创建本机 Management Profile；“验证会话”直接调用 Backend 健康检查。Cookie、Token 和 payload 不进入页面、Query Cache 或 Console。

禁止：

- 直接写大段业务算法
- 直接创建 HTTP Client
- 复制公共布局

## 滚动

默认 AppShell 固定，主内容区域负责页面滚动。
只有确有需求时建立局部滚动。
禁止多个不必要的嵌套滚动条。

阶段 0B 的统一滚动链路为：

```text
Electron Window
↓
AppShell（固定 Sidebar / Topbar）
↓
app-shell__content（唯一主滚动区域）
↓
Page
```

## Header

PageHeader 保留用于复杂详情页、编辑器和独立工作区，并继续使用统一 Token。普通列表管理页默认不渲染 PageHeader，禁止为了重复 Sidebar / Breadcrumb 上下文而占用额外首屏高度。
