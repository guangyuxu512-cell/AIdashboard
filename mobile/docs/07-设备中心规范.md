# Mobile 设备中心规范

## 1. 范围与分层

Device Center 是设备观测与未来执行入口，提供 `/devices` 列表与 `/devices/:deviceId` 完整详情页。
当前仍只消费正式只读 Contract，不提供启停设备、编辑资料、管理 Capability、操作 Provider 或控制当前任务
的写能力。Device Detail Visual V2 已完成工程化迁移并处于 Candidate for Visual Review；Capability Refresh
只重新获取正式 GET Query，逐 Application/Business Skill 的配置与运行入口在未接正式 Mutation 前不发写请求。

```text
pages/devices
├── features/device-center  刷新、无限列表、辅助数据状态与页面组合
├── entities/device         DTO、API、Mapper、Query 与设备语义
├── entities/task           复用正式 Active Task DTO、API、Query 与状态语义
└── shared                  唯一 API Client、基础 UI 与 Query 错误分类
```

Page 只组合 Feature 与 Entity；Device Entity 不依赖页面；Active Task 必须扩展既有 Task Entity，禁止复制 Task DTO、状态映射或详情实现。所有正式请求经唯一 `shared/apiClient`，生产代码不得包含 Mock DataSource。

## 2. Device 列表

> `/devices` 已完成并冻结 Mobile Visual V2；列表的最新视觉、响应式和验收契约以
> [`10-Mobile-Visual-V2-设备列表.md`](./10-Mobile-Visual-V2-设备列表.md) 为准。`/devices/:deviceId`
> 已完成 Visual V2 工程化迁移但仍待人工复核，权威候选规范见
> [`11-Mobile-Visual-V2-设备详情.md`](./11-Mobile-Visual-V2-设备详情.md)。Backend Contract 未改变。

- 正式接口为 `GET devices`，仅发送 `page`、`page_size`；Device Center 每页 20 条并完全服从 Backend 顺序，
  不自造搜索、筛选参数或排序。
- Infinite Query 按 `device_id` 稳定去重；首屏加载、空、首屏错误、缓存背景错误与下一页错误必须分别展示。下一页失败保留当前设备，并在列表尾部提供明确重试。
- 列表与详情的 Device 主查询每 15 秒后台刷新；Mobile 对 Provider 与 Skill 快照每 60 秒后台刷新。Provider 周期与 Worker 默认发现周期一致，Skill 的 60 秒仅是 Mobile 观察策略，不代表 Worker 同步 Contract。下拉刷新先把 Device Center 收敛到第一页，同时刷新当前已经挂载的 Active Task Query。
- Task 筛选器仍使用每页 100 条并完整翻页。Device Center 与 Task 筛选器的 Query Key 必须携带各自 `page_size`，防止缓存相互污染。
- Visual V2 列表固定使用 Device Page Header → Search → 四项 Summary → 独立滚动 Device Card List →
  Bottom Navigation。Search/Summary 位于固定区，不随 Card 滚动；旧 `MobileListToolbar` 不再出现在
  `/devices`，筛选只维护唯一 `DeviceQuickFilter` 状态。
- 卡片固定为左侧 `DeviceStatusArtwork`、设备名 / 视觉状态 / Meta 三行主要内容和右侧 Chevron。Meta
  固定显示“心跳 {相对时间} · 已启用/已停用”；列表不展示 Worker 版本、任务名称或 `latest_event`。
  整张 Device Card 只有一个至少44px的 Device Detail 入口，列表内不再提供
  Task Detail 按钮；只有设备详情明确点击 Current Task 才进入任务详情。
  Provider Inventory 与 Skill Capability 只在详情请求，禁止列表 N+1 拉取。

### 设备总览与快捷筛选

- 列表顶部一个 Summary Surface 内严格四等分，顺序固定为“全部设备 / 在线设备 / 运行中 / 离线设备”。
  Visual V2 不显示 Metric Icon；数字强于 Label。四项均为快捷筛选，共用唯一 `DeviceQuickFilter`；点击切换，
  再次点击当前非全部项恢复全部。Metric 触控区至少 44×44px。
- 在线与离线只读取 `Device.worker_runtime.connection_status`：`online` 计入在线、`offline` 计入离线，
  `worker_runtime=null` 不并入离线。运行中只读取 Active Task 正式 `status=running`；`pending` 与成功的
  `204=null` 都不计入运行中。
- Backend 当前不支持上述服务端筛选或设备搜索。“全部设备”可展示 Backend `total`；其它状态计数、
  本地筛选与按 `display_name` 的 Search 只有在 Infinite Query 已加载全部 Backend 分页，且对应 Active Task
  事实完整确认后才可用。未完整时显示 `—`/禁用 Search 与对应 Metric；禁止只过滤当前分页、发送自造
  参数或把局部结果包装成全量筛选。
- Device 列表与三卡通过同一个动态 `useQueries` 结果集合消费 Active Task。统一 query-options 固化相同 Query Key、正式 API 与 5 秒刷新；列表卡不得再建立第二组 Active Task Observer 或重复请求。
- 下拉刷新收敛到第一页后，如果 Backend 仍有后续分页，当前快捷筛选和 Search 必须恢复空查询/“全部”；下一页失败不得
  让未完整数据获得筛选能力。

### Visual V2 状态插画

- Card 公开视觉状态只允许 offline / running / online，优先级为：Backend `offline` → Backend `online` +
  正式 running Active Task → Backend `online`。公开 Registry、Artwork State 与 UI 不得出现 unreported。
  `worker_runtime=null` 没有第四种公开状态，Card 使用 offline artwork 作为安全显示 fallback，但不得把它计入
  Backend Offline 统计或改写 DTO。`enabled` 独立显示，不得改变连接/运行状态。
- `DeviceStatusArtwork` 的 Kind 与视觉状态是两个独立输入。当前 Backend 无设备 Kind Contract，生产列表
  统一使用 desktop fallback；不得根据设备名、位置、Worker 版本或 Provider 猜测设备种类。
- 组件层可验证 desktop/laptop/server 三种视觉容量；正式 Kind 映射必须等待 Backend Contract。
- 390×844 只作为设计基准。生产页使用 `width: 100%`、`100dvh` AppShell、四向 Safe Area 和剩余高度列表
  滚动；禁止固定 390/844 或整体缩放。

## 3. 设备状态边界

- `enabled` 只表示设备是否启用：`true` 显示“已启用”，`false` 显示“已停用”。它只是 Backend 判断执行资格的一项前置事实，不等于当前可执行或 Worker 在线，也不由 Mobile 推断。
- `worker_runtime = null` 表示 Backend 没有 Runtime 事实，不能解释为 Backend 返回离线。Visual V2 Card 为
  保证公开状态只有三种使用 Offline Visual Fallback；Summary / Filter 仍不把该记录计入正式离线数，第三行
  Heartbeat Meta 显示“心跳未上报”。
- Runtime 非空时，`connection_status` 只接受 Backend 持久化的 `online | offline`，分别显示“在线”“离线”。Mobile 不依据 `last_seen_at` 重算连接状态。
- `last_seen_at` 仅用于“刚刚 / N 分钟前 / N 小时前 / N 天前”的相对展示；相对时间不参与启用、在线或 Provider 状态判断。
- 启用状态与连接状态始终保持独立语义，不互相推断。紧凑列表第二行展示单一视觉状态；详情 Hero 展示
  同一个 Visual State，启用状态作为真实只读事实进入“更多信息”，不参与三态推导。

## 4. 当前任务

- 正式接口为 `GET tasks/active/{device_id}`。只有在 Device 列表项已有效，或 Device 详情主请求成功后，才允许调用该辅助接口。
- `200` 仅返回 `pending | running` 的 `ActiveTaskSummaryReadDto`；`204` 映射为 `null`，在已确认有效的设备上下文中表示“空闲”。
- Active Task 每5秒刷新。列表卡只把正式 Active Task 状态投影到单一主要状态，不显示任务名称且不提供 Task 跳转；详情的 Current Task 才可进入
  既有 `/tasks/:taskId`，并携带单值 `fromDeviceId` 作为返回来源。任务详情返回时优先回到对应设备详情。
  禁止复制任务详情或重新声明任务状态语义。
- Device Detail 的 Current Task 固定为 Section Title + 正式 `TaskListCard`；Active Summary DTO 只在 Device
  Feature 做最小字段适配，Card 本身不感知 Device 上下文。有任务时点击整张 Card 进入 Task Detail，无任务
  时只显示“空闲”，禁止保留或复制第二套 Current Task Card。
- Active Task 的 Loading、首屏 Error、缓存背景 Error 与 Device 主数据互相独立。辅助请求失败不得把已成功的设备页面替换成全屏错误。
- Backend 当前没有批量 Active Task 聚合端点，因此列表存在每台设备一次辅助请求的 N+1 已知缺口；Mobile 不通过非正式接口规避该缺口。

## 5. Provider Inventory

- 详情通过 `GET devices/{id}/provider-inventories` 获取裸数组，不分页。空数组表示“尚未上报 Provider 快照”。当前正式 `provider_code` 仅为 `yingdao`。
- 影刀状态固定为：`not_installed` 未安装、`version_unsupported` 版本不支持、`starting` 启动中、`need_login` 需要登录、`interface_unreachable` 接口不可达、`ready` 就绪。
- `available`、`execution_available`、`logged_in` 必须分别展示，三者不可合并或互相推断。默认账号摘要仅展示登录状态、账号显示名与影刀版本；三项可用性、账号类型、企业账号、执行接口版本、发现时间和原因放入页面唯一的“更多信息”。
- 影刀应用列表只读取 `inventory.applications` 的正式 `app_name`；默认 UI 不显示 `app_id`、`version_id`、
  `group_id` 等技术标识。Capability Panel 每行固定为应用名、配置、运行；本轮入口不发起 Mutation。
- Provider 状态不等于设备在线、设备启用或 Skill Capability；状态值本身不是 HTTP Error。

## 6. Skill Capability

- 详情通过 `GET devices/{id}/skill-capabilities` 获取裸数组，不分页。Capability Panel 的 Skills 分类只展示
  `classification=business` 的 `display_name`；`internal` 与 `null` 不进入普通用户操作列表。总数和未分类
  计数继续放入“更多信息”。
- `classification = null` 必须计入“未分类能力”，禁止按名称、Runtime 或 Provider 猜测分类。
- Capability 只表示 Backend 上报的能力记录，不代表设备在线、设备已启用、Provider Ready 或当前可以执行。
- Business Skill 行只在 `input_schema !== null` 时显示配置入口，并始终保留运行入口位置；这些入口未来消费
  正式 Schema/Run Contract。空数组只表示当前没有 Capability 记录；本轮不提供 Capability 写操作。

## 7. 详情、错误与安全

- Device Detail Visual V2 是完整页面，固定顺序为 `DeviceDetailHero → Current Task → Capability Panel →
More Sheet`。透明 `MobileDetailHeader V2` 与五入口 Bottom Navigation 位于滚动区外，整个 Detail Content
  独立滚动并隐藏可见 Scrollbar；设备入口在详情保持 Active，不建立底部 Action Bar。
- `DeviceDetailHero` 是详情专属组件，不是放大的 DeviceCard。它复用 `DeviceStatusArtwork` Hero Variant、
  `getDeviceVisualState`、Heartbeat Formatter，并只显示真实设备名、三态、最后心跳及存在的 Worker / 影刀版本。
  长设备名单行 Ellipsis；Backend 没有 Device Kind 时继续使用 `desktop` visual fallback，不声称为 Backend
  事实。
- Hero 不展示 Device UUID、Provider ID、Account Internal ID、Application ID、Endpoint 或 Schema，也不为
  Prototype 对称造 Device Code。右上 More 打开默认关闭的 Vant Bottom Sheet，统一容纳设备 ID/启用/位置/
  备注/时间、Runtime 时间、Provider 次要字段和 Capability 技术计数；Sheet 只读，不提供假设置操作。
- Device 主详情成功后，Active Task、Provider、Capability 各自维护 Loading、首屏 Error、缓存背景 Error 和重试；任一辅助失败不得覆盖 Device 主数据，也不得覆盖其他辅助数据。
- 页面只展示正式业务字段，不读取 Worker Credential，不展示 Token，不发出 `POST`、`PATCH`、`PUT`、`DELETE`。
- 所有用户可见文案使用中文；优先复用 Vant 和既有 Mobile Token，不新增 Device 私有 Token、颜色字面量、PC Table 或 Drawer 复制实现。
- Current Task 有数据时显式使用正式 `TaskListCard` V2；无数据时只显示“空闲”。TaskCard 与 DeviceCard 共用
  `MobileBusinessCardFrame` Geometry，但业务内容和 Artwork 分离；`/tasks` 本轮不迁移 Visual V2。
- 详情遵守四向 Safe Area、`100dvh` 与真实 Viewport；428×926 和390×844只作视觉基准。Header / BottomNav
  保持固定，`AppPage` 自动获得剩余高度，禁止绝对定位硬编码 top/bottom 或整体缩放。

## 8. Capability Interaction

- `DeviceCapabilityPanel` 是 `features/device-center` 的领域组件，不放入 `shared/ui`。Anatomy 固定为
  Capability Header（能力标题区）→ Capability Type Selector（能力类型选择器）→ Scrollable Capability
  List（可滚动能力列表）；Header 左侧为“能力面板”，真实 Query Refresh 位于右侧。
- Selector 使用 Vant Tabs，只包含等宽且同一行的“影刀应用 N”与“Skills N”，顺序固定，并保留 Active /
  Inactive 与 Count 结构；Tabs 的文字、Indicator 和底部分隔必须完整落在44px Wrap 内，不得被父级
  `overflow` 裁切。
- Application 与 Business Skill 行固定为 `Icon Slot + Name / Optional Version + Actions`。Application
  正常 UI 只显示正式 `app_name`，不把技术 `version_id` 当可读版本；Business Skill 可显示正式 `version`。
  Name 单行 Ellipsis，Configure 位于 Run 左侧，Run 固定最右，UUID 只允许进入 More Information/Debug。
- Capability List 使用66px Row 与 `66px × 5` 固定 List Height，默认完整显示5行，第6行开始内部滚动且不露
  半行；Header 与 Tabs 不参与内部滚动。这些值属于 Device Detail V2 候选，人工确认前不冻结。
- “配置”未来复用正式 Parameter Schema；“运行”未来复用 Device → Application/Skill → Shop → Parameter →
  Create Task → Worker Claim 正式链路。当前 Refresh 真实并行 refetch Provider Inventory 与 Skill
  Capability GET Query，不伪造成功。
- Configure / Run 在未接正式 Mutation 前只显示简洁“功能建设中”，不得发出写请求，也不得显示应用已启动、
  参数已保存等 Fake Success。Current Task 继续跳转既有 `/tasks/:taskId`，不复制 Task Detail。
- Capability List 使用统一隐藏 Scrollbar 规则并保留触控滚动；到达内部边界后必须自然继续滚动 Detail
  `AppPage`，不得锁住页面或让 Document 承担业务滚动。
- 每行 Icon 只冻结统一槽位。最终资源由 Icon Registry（图标注册表）按显式 `icon_key`、业务/类型映射、
  默认图标的顺序解析；本轮只使用类型占位图标，不实现上传、用户选图或 Backend 图标配置。

## 9. Auth、Data Scope 与聚合缺口

- `/devices` 与 `/devices/:deviceId` 均使用 `requiresAuth: true`、`permission: 'device'`，
  复用正式 Human Session、Team Context 和 Module Access，不实现 Fake Auth。
- Backend Human Auth / Access Management 已存在，但 Device 旧读接口尚未注入
  `require_module_access('device')` 或 Actor Context Data Scope。Mobile 不拉取全量数据后
  本地模拟数据权限；服务端安全边界必须由独立 Backend Feature 补齐。
- Backend 当前没有 Device 列表聚合 Active Task、Provider 与 Capability 的接口。V1 仅对 Active Task 接受已知 N+1，Provider/Capability 保持详情专用；后续是否增加聚合 Contract 必须由 Backend 正式定义。
- Backend Device List 当前只有 `page/page_size`，没有连接状态或 Active Task 状态筛选；因此快捷筛选
  只能在完整分页与所需事实全部确认后本地执行。正式大数据量/服务端筛选仍是 Contract Gap，本轮不修改 Backend。

## 10. 验证

- Unit/Component 覆盖正式 URL/DTO、204 空闲、Mapper、分页去重、20/100 Query Key 隔离、连接/启用语义、相对心跳、Provider 六状态、三类 Capability、Device Card 的 Online Idle / Online Running / Offline / Disabled、长设备名、Chevron、整卡导航，以及列表五类加载/错误状态与辅助错误隔离。
- Mock E2E 覆盖列表、下拉刷新、无限加载、设备详情、当前任务跳转既有任务详情并返回，以及底部“任务 / 设备”导航。
- E2E 在 360/375/390/430 宽度与 Light/Dark 下检查 Console Error 为零、无横向溢出、Safe Area 和至少 44px 触控高度；测试 Fixture 只能位于 `tests/**`。
- Layout E2E 使用至少20条 Device 验证仅 Card List 滚动、Body 不滚动、Scrollbar 不可见；66px Header、
  44px Search、90px 四项 Summary 与 64px Bottom Navigation 主体均保持原位。还必须验证 Hamburger →
  Theme Sheet、40px Action Surface / 45px Touch Target、四个 Metric 的 44px Touch、点击筛选、再次点击恢复
  全部、唯一 Filter State 及分页未完整时禁用。Device Detail Visual Fixture 至少包含8个影刀应用与5个
  Business Skill；Light/Dark详情截图必须验证透明 Detail Header、Device Hero、Current Task、能力 Header、
  真实刷新、Tabs、5行 Capability、More Sheet 与五入口 Bottom Navigation，并验证第6行内部滚动、Skills
  分类、隐藏 Scrollbar、UUID不进入正常 Row 和所有占位入口不产生非 GET 请求。
