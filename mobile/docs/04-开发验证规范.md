# Mobile 开发验证规范

## 必跑命令

按改动范围至少执行：

```bash
pnpm --filter @control-center/mobile lint
pnpm --filter @control-center/mobile typecheck
pnpm --filter @control-center/mobile test
pnpm --filter @control-center/mobile build
```

涉及路由、主题、触控、Popup、Safe Area 或布局时，还必须执行：

```bash
pnpm --filter @control-center/mobile test:e2e
```

## 本地 API 联调

Mobile 开发环境通过 Vite `/api` Proxy 访问 Backend，不在业务源码硬编码主机地址。首次在本地联调前，
从 `mobile` 目录创建被 Git 忽略的本机配置：

```powershell
Copy-Item .env.example .env.local
pnpm dev
```

默认目标是 `http://127.0.0.1:8000`。启动 Mobile 前应确认 `/health` 与本次页面使用的只读 API 均能
进入成功或失败终态；仅有 `/health=200` 不代表业务数据库可用。代理或 Backend 不可用时，正式页面
必须在请求超时或失败后显示“加载失败”和“重试”，不得永久停留 Loading。Vite 返回的 HTML fallback
不是 API 成功响应，统一 API Client 必须拒绝非 JSON 响应。

## Visual 与 Real 两阶段验收

### A. Visual Acceptance

从 `mobile` 目录运行 `pnpm dev:visual`，或执行 `pnpm test:e2e:visual`。该模式只在 Development
启用 Entity Mock DataSource，用于稳定检查 Layout、Light/Dark、Spacing、Card、Press、Responsive、
Console 与横向溢出；不得依赖 Backend，也不得在 UI 显示 Mock 说明。Device/Task 列表与详情必须
复用正式 Query、Mapper、Feature、Page 和组件。

### B. Real API Acceptance

运行 `pnpm dev` 与默认 `pnpm test:e2e`，验证正式 Contract、Initial Loading、Success、Empty、Error、
Retry、Background Refresh 与真实数据。Real API 失败不得自动切换 Mock，Backend 是否在线也不得影响
Visual Acceptance 的结果。

## 单元与组件测试

Foundation 至少覆盖：

- 所有 Route Meta 字段完整。
- Production Route Table 不包含 `/__foundation`。
- Route Guard 是可注入插槽，Router 不自动安装假实现。
- Theme 的 Light、Dark、System 解析、持久化与 Vant Dark Class。
- Query 与 Mutation 全局默认策略。
- `MobileAppShell` 的三个 Slot 和安全区结构。
- Global Header 只有一份品牌实现且没有底部 Divider/整栏 Shadow；Theme Toggle 位于默认无 Badge 的 Bell 左侧，二者使用相同尺寸、Surface、透明 SVG 和 Press 体系；System 首次快切按实际解析主题切到相反固定主题；Detail Header 统一返回。
- Bottom Navigation 顺序固定为设备、任务、计划、店铺、我的，并验证 main/detail 均常驻且详情激活
  对应业务入口。
- Device/Task Card 共享 `mobile-card` 与 CSS Press 语义，长标题不溢出；Pressed 不能依赖 JS 才成立。
- 计划、店铺、我的复用同一个建设中页且没有假业务数据。
- Foundation Button、Field、CellGroup、Tag、Popup 交互。

API Client 测试由 API Client 所有者维护，其他模块不得重复创建第二份 Client 或对应测试。

Task Center 至少覆盖：

- Task/Device DTO、唯一状态映射、Mapper 与执行名称回退。
- 今天、昨天、最近 7 天（默认）、最近 30 天、自定义与全部时间六种日期预设；自然日半开区间及全部时间省略日期参数。
- 正式 query params、500 字搜索上限、稳定分页与 `task_id` 去重。
- 单页 5 秒背景刷新、多页暂停、下拉刷新、首屏加载/空/错误、成功空缓存的背景错误，以及 Task/Device 下一页独立错误与重试。
- 五种任务状态、成功摘要白名单、失败/失联脱敏错误、结构化进度与当前信息。
- Event 初始/`before_seq`/`after_seq`、终态连续 final sweep、竞态与独占 drain、游标不前进保护、四种保留状态，以及超过 500 条后滚动保留最新 Event。
- Final drain 必须覆盖初始缓冲已满 500 条、连续多页淘汰旧 Event，以及中途失败后显式重试；500 条上限只能限制 DOM/内存与 `before_seq`，不能停止 `after_seq`。
- 初始 Event 响应确定前不得展示保留状态；Running 耗时使用可清理的本地时钟持续更新。
- Task Route Meta、详情深链设备名称、详情返回与底部导航常驻。

Device Center 至少覆盖：

- Device、Worker Runtime、Active Task、Provider Inventory 与 Skill Capability DTO/Mapper，包含 nullable 字段和未知 Runtime 的独立语义。
- Device List 正式 `page/page_size` 参数、稳定 Infinite Query、下拉刷新与后台刷新；首屏加载、空、首屏错误、后台错误及下一页错误必须分别验证。
- `enabled` 与 `online/offline/no-runtime` 分离；Provider 的 `available`、`status`、`execution_available`、`logged_in` 分离；Skill 的 business/internal/unclassified 分类分离。
- Device Card 与 DeviceRuntimeSummary 的在线、离线、未上报 Runtime、空闲、执行中与停用映射；连接、
  Active Task 和 enabled 必须保持独立事实，辅助请求失败不能覆盖设备主列表或详情主数据。
- Device Detail 的当前任务/空闲、Worker 版本、最后心跳、六种影刀状态、Provider 空快照/错误、Skill 分类摘要/空快照/错误及更多信息。
- Device Route Meta、详情返回、现有 Task Detail 跳转、任务/设备底部导航常驻；不得出现任何设备写操作。

## Playwright 验收

Foundation 验收覆盖宽度：360、375、390、430；每个宽度使用手机高度和触控上下文。

必须验证：

- Light 与 Dark 均可解析并驱动根元素和 Vant。
- System 只解析为 Light/Dark，不建立第三套视觉值。
- 状态前景与 Soft Surface、Caption/Tertiary 文本的计算对比度不低于普通文本基线。
- Header、Bottom Navigation、Card、Cell、Popup 与页面背景均解析到 Mobile Semantic Token。
- 页面无横向溢出。
- 主要按钮实际高度不小于触控 Token。
- Back、Bell、Bottom Navigation、Collapse 与 Calendar Action 的触控高度不小于 44px。
- Theme Toggle、Bell、Back、Card 与 Bottom Navigation 都有克制 Press State；Theme 在 Bell 左侧。
- `prefers-reduced-motion: reduce` 下 Press Transition 被取消且所有入口仍可操作。
- 键盘可交互元素使用统一 Focus Ring，不能只依赖 Hover。
- Bottom Sheet 可打开、可关闭，并使用底部 Safe Area。
- Browser Context 启用移动触控能力，不以桌面鼠标视口冒充手机。
- 通过可控 Token 值断言 Header、Page、主内容区、Bottom Sheet 与自定义 Calendar 的实际 Safe Area Padding。
- 测试期间 Console Error 数量为零。

Foundation 不依赖真实 Backend 或 Mock DTO，E2E 不能通过伪造业务接口才能运行。

Task Center 的 Real Contract E2E 使用 `tests/**` 网络 Fixture，不得触发 Development Visual
DataSource；覆盖列表、状态/设备/六种日期/搜索、滚动加载、Task 与 Device 下一页失败重试、下拉刷新、
详情、`before_seq`/`after_seq` 日志与返回。360/375/390/430 和 Light/Dark 的交叉矩阵必须实际打开
筛选、详情及日志，并验证 Console Error 为零、无横向溢出、可控 Safe Area，以及 Shell 底部导航不遮挡主内容。

Device Center 的 Real Contract E2E 同样只在 `tests/**` 拦截真实只读 GET Contract，不得触发
Development Visual DataSource。必须覆盖设备列表、下拉刷新、服务端分页、详情、当前任务跳转既有
Task Detail、返回，以及任务/设备底部导航切换。360/375/390/430 与 Light/Dark 交叉矩阵必须检查
文字、Card、Border、状态、底部导航和详情能力摘要，保持 Console Error 为零且无横向溢出；System
主题继续由 Foundation 验证。

AppShell V2 E2E 必须额外验证：

- main Route 统一显示“思余AI中控台”和五入口 Bottom Navigation，顺序不得改变。
- 设备与任务可双向导航；计划、店铺、我的进入同一个建设中页。
- detail Route 显示统一返回 Header 与五入口 Bottom Navigation，并保持 Device → Current Task →
  Task Detail → Device Detail 返回链；Device/Task Detail 分别激活设备/任务入口。
- Header/Main/Bottom Grid 不重叠；顶部/底部 Safe Area 只有一个所有者；所有 Tab 触控高度不小于 44px。
- 390px Light 保留 Device List、Device Detail、Task List、Task Detail 验收截图；390px Dark
  保留 Device List、Task List 截图，并额外保留 Device Card Pressed State。截图只进入 Playwright artifact，
  不提交产品源码。

## Layout Review

每次新增或修改一级列表页必须逐项验证：

- Global Header 不随业务 Card 滚动。
- 可选 Summary Strip 不随业务 Card 滚动，当前高度基线为 98px；Metric 固定使用 Icon → Number → Label。
  可交互 Metric 必须具备 Button 语义和至少 44×44px Touch Target，并验证与 Toolbar Primary Selector
  共用同一状态、再次点击恢复全部；Selected / Press / Motion 的最终视觉不在 Stage 1 验收范围。
- `MobileListToolbar` 不随业务 Card 滚动，并在 360/375/390/430px 保持 `Title + Meta`
  与 `Primary Selector + Filter Action` 同一行，Selector 必须位于 Filter 左侧。
- `MobileListToolbar` 不套外部 Card、Border、Raised Surface 或 Shadow；当前 44px 工具行、32px 视觉控件只是
  Stage 1 实现基线，Selector/Filter 实际触控高度仍至少 44px。
- Device Summary 与 Toolbar Selector 必须使用同一 `DeviceQuickFilter`；需验证 Summary 选中、Toolbar 选择和
  清除均双向同步，且请求只含 Backend 已支持的 `page / page_size`。
- Bottom Navigation 不随业务 Card 滚动，也不遮挡最后一张 Card。
- 只有业务 List/Grid 区域是一级列表页主滚动容器；Shell Main 与 Document 不滚动。
- 正式主滚动区在 Chromium/WebKit、Firefox 与 Edge 隐藏可见 Scrollbar，但必须能滚动到底；详情
  `AppPage` 同样隐藏可见 Scrollbar，List 与 Detail 滚动区都必须有具名键盘焦点入口，并验证
  `PageDown` 能改变 `scrollTop`。
- Device/Task Card 使用稳定结构、统一 Padding/Gap 和文本行数，不以随意固定 Height 获得一致性。
- Initial Loading、Initial Error 与 Empty 只替换 Scroll Region 内容，不移除或移动 Header、Summary、
  Toolbar、Bottom Navigation。
- 不存在 Page 私有 Toolbar Height/Padding/Layout CSS，不存在多组 `position: fixed` 或手工 `top/bottom`
  魔法值。
- Device 与 Task 都用至少 20 条 Fixture 实际滚动，断言固定区域位置不变、第一张 Card 发生位移。
- 390px Mock 输出 Device/Task 顶部与中间滚动态截图；所有矩阵保持 Console Error 为零且无横向溢出。
- Device Detail Mock 截图必须在首屏确认 DeviceRuntimeSummary 单一卡片内“Upper Device → Separator →
  Lower Yingdao Account”的上下结构；Lower 固定为“影刀账号 + 登录状态”与“账号名 · 影刀版本”两行，
  长账号名单行省略且版本保持可见。继续确认 Capability Panel 与 Current Task 顺序；刷新、配置、运行等
  未接能力不得发出写请求或显示 Fake Success。
- Device Card 本身必须是单一 Device Detail 入口，列表卡内不得再出现 Task Detail 入口；只有详情页
  Current Task 可进入既有 Task Detail。
- Visual Fixture 至少包含20台设备、8个影刀应用与5个 Business Skill；CapabilityPanel 必须完整显示
  五行，第6行后仅 Rows 内部可滚，Header / Selector 保持不动。每行验证 Icon Slot、单行名称、正式版本
  （存在时）、Configure / Run 顺序，以及 Application/Skill UUID 不进入默认 UI；不以最终 Row 或 Panel
  像素值作为 Stage 1 断言。
- 嵌套滚动验收必须先滚动 Capability List 到末尾，再继续滚动 Detail `AppPage`，两者均可滚且均无可见
  Scrollbar，不得锁死、吞掉页面滚动或让 Document 承担业务滚动。

## Visual System V1 回归

视觉收口至少人工检查 Global Header、Detail Header、Bottom Navigation、Device Overview、Device
Card、Task Card、Device Detail、Task Detail、Coming Soon 与 Foundation。Device/Task 列表必须保持
既有信息密度，不得因增加 Surface、Padding 或装饰让 Card 回到一张占据近半屏。

390px 稳定 Mock 截图固定为：

- Light：Device List、Device Detail、Device Skills、Task List、Task Detail。
- Dark：Device List、Device Detail、Task List。

截图使用 `testInfo.outputPath` 进入 Playwright artifact；不得提交到 `mobile/src` 或正式静态资源。
视觉断言优先检查语义 Token、计算样式、几何、触控、对比度、Console Error 和横向溢出，不使用
脆弱的全页像素快照替代功能与可访问性断言。

## 正式 UI 文案与状态 Review

每个正式业务页面必须检查：

- 不存在开发说明、Contract 说明、API 说明、数据口径解释或长段帮助文案。
- Loading 只在首次进入且没有成功数据、请求确实处于 fetching 时出现。
- 请求失败、超时或非 JSON 响应必然进入 Error，不存在无限 Loading。
- Device List 等主 Query 成功后页面主体立即可用；Active Task、Provider、Capability 等次级 Query
  的 Loading/Error 只能影响对应局部区域。
- Background Error 保留上次成功数据，不退回整页 Loading 或整页 Error。
- Error、Empty、Placeholder 都使用可扫描的安全短句，不展示实现原因或未来架构。
- Review 必须逐项判断 UI Copy 是否可以删除而不影响用户操作与判断；可以删除就删除。
