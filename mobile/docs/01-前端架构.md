# Mobile 前端架构

## 系统边界

Mobile 只负责手机 Web 的界面、路由、客户端状态和服务端数据展示，不承担 Backend
业务规则、Authorization、Data Scope、任务执行或 Worker 身份职责。

正式数据流固定为：

```text
Page
↓
Feature
↓
Entity Query / DataSource
↓
shared/api 唯一 Axios Client
↓
Backend 正式 API
```

没有 Backend Pydantic/OpenAPI 或正式 Contract 时，不得增加 URL、DTO、状态、分页、
错误结构、权限码或 Mock Real API。

## 目录和依赖

```text
src/
├── app/
│   ├── router/     唯一 Route 注册与访问控制插槽
│   ├── providers/  全局第三方 Provider 配置
│   ├── stores/     跨页面 Client State
│   └── styles/     应用级全局样式入口
├── pages/          路由页面和页面级组合
├── features/       用户动作与用例
├── entities/       稳定业务实体、Query、DataSource 与复用展示
├── shared/
│   ├── api/        唯一 Axios Client 与通用 Backend Contract
│   ├── ui/         无业务语义且确有复用的 Mobile UI
│   ├── styles/     Token、全局基线与 Vant 适配
│   ├── utils/      无业务语义工具
│   ├── types/      跨业务通用类型
│   └── constants/  跨业务稳定常量
└── assets/         Mobile 自有静态资源
```

依赖方向固定为：

```text
pages → features → entities → shared
```

`app` 负责启动和组装，可以组合上述层级；`shared` 禁止反向依赖 Page、Feature 或
Entity。空目录只用于表达已确认的边界，不得提前放置虚构业务实现。

## 如何新增页面

1. 先确认产品用例、Backend Contract 与权限/Data Scope 边界；缺失时报告 Gap。
2. 复用已有 Entity 与 Feature；只有真实领域语义不存在时才新增对应模块。
3. Page 只组合 Feature、Entity 展示和 Shared UI，不直接调用 Axios、拼 URL 或复制 Backend Guard。
4. 在 `app/router/` 注册 Route，并显式填写 `title`、`layout`、`requiresAuth`、`permission`；
   `layout = main | detail` 只决定全局 Shell，不替代访问控制 Meta。
5. 按手机触控与信息密度重新组织，禁止复制 Desktop Page 后仅修改 CSS。
6. 一级列表页先复用 `MobileSummaryStrip`、`MobileListToolbar` 与 `.mobile-list-page` Pattern，
   只让业务 List/Grid 区域滚动；详情内容统一由 `AppPage` 滚动。
7. 补齐单元/组件测试；涉及布局、路由、触控或弹层时补 Playwright 验证。

## 如何新增 Feature

1. 用一个明确用户动作或用例命名，避免把多个无关动作塞进万能 Feature。
2. 通过 Entity 的公开 API/DataSource/Query 消费数据，不越过 Entity 直接使用共享 Client。
3. Feature 内部实现不向其他 Feature 暴露；跨 Feature 复用应回到合适的 Entity 或 Shared 语义。
4. Backend 业务合法性留在 Service；Feature 只负责输入、交互、请求与反馈。
5. 只有跨页面客户端状态才进入 Pinia，Server State 继续由 TanStack Query 管理。

## 状态归属

- Pinia：主题、未来正式认证上下文等客户端跨页面状态。
- TanStack Vue Query：未来正式 Backend 服务端数据、缓存、刷新和失效。
- Component State：单一组件内部的输入、Popup 开关等短生命周期状态。
- Router：URL 和页面导航状态。

禁止将 Query 数据复制到 Pinia，禁止自制服务端缓存，禁止为了 Foundation 创建假用户、
假 Token、假角色、假业务 Store 或假 Query。

`createMobileQueryClient()` 仅提供与业务无关的默认行为：Query 不自动重试、不在 Window
Focus 时自动刷新，Mutation 不自动重试。缓存时长、轮询、分页和失效由未来 Entity 按正式
业务语义配置。

Development Visual Mode 只在应用启动时把 Device/Task Entity 的 DataSource 显式切换为稳定
Fixture；Query、Mapper、Feature、Page 与 UI 不分叉。默认 Development 与 Production 都使用 Real
DataSource，Backend Error 或 Empty 永远不会触发 Mock Fallback。Visual Fixture 模块通过
`import.meta.env.DEV` 守卫和动态导入隔离，Production Build 不应包含其行为或数据。

## UI 层

Vant 是 Mobile 基础组件库。存在统一项目语义、可访问性约束、重复配置或跨页面复用时，
才在 `shared/ui` 建立项目级组件；不得为 Vant 每个组件创建一行 Wrapper。Page 只组合
布局、Feature 和 Entity，不复制 Desktop 页面后改 CSS。

## AppShell V2

正式页面统一由应用层按 Route Meta 组装：

```text
main Route
↓
MobileAppShell
├── MobileGlobalHeader（思余AI中控台 / 通知入口）
├── RouterView MainContent
└── MobileBottomNavigation（设备 / 任务 / 计划 / 店铺 / 我的）

detail Route
↓
MobileAppShell
├── MobileDetailHeader（返回 / Route title）
├── RouterView DetailContent（唯一滚动区）
└── MobileBottomNavigation（设备 / 任务 / 计划 / 店铺 / 我的）
```

Page 不感知也不导入全局 Header、Detail Header 或 Bottom Navigation。`App.vue` 是唯一 Shell
组装点；`MobileAppShell` 保持 header/default/bottom 三 Slot、稳定 Viewport 高度和隐藏溢出的 Main
插槽。一级列表页的 List/Grid 是该页唯一滚动区，Summary 与 Toolbar 留在滚动区外；详情及普通内容页
由 `AppPage` 持有唯一内容滚动，普通 Detail 同样保留 Shell Bottom Navigation。只有未来参数编辑、
图片选择或全屏工作台等明确沉浸式 Route 才能通过正式 Shell 语义隐藏底栏。设备进入当前任务时的
`fromDeviceId` 返回语义仍由应用层集中处理，
不下沉到 Page。

计划、店铺和我的复用同一个 `ComingSoonPage`，仅由 Route Meta 提供中文标题。占位页不得调用
业务 API，也不得创建假 Schedule、Shop、Current User、Auth 或 Notification 数据。
