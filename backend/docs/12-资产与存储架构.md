# 资产与存储架构

## 1. Asset 定义

Asset 是已经进入中控台资产体系、具有稳定 `asset_id` 的文件事实。它保存：

- `team_id`：素材所属 Team，是正式数据范围边界。
- `created_by_user_id`：素材创建者；历史或系统素材允许为 NULL。
- `media_type`：业务媒体类别，当前正式创建 IMAGE；表结构为未来 VIDEO 保留稳定扩展值。
- `source_type`：进入系统的来源，固定为 UPLOAD、AI_GENERATED 或 IMPORTED。
- `original_filename`：原始文件名的安全基名；真实图片格式与后缀不符时只校正后缀。
- `storage_key`：Storage 内部稳定键，不是服务器绝对路径。
- `content_type`：文件真实 MIME，与 `media_type` 分工。
- `size_bytes / sha256`：文件真实字节数与 SHA-256。
- `created_at`：资产事实创建时间。

当前资料库 UI 和 HTTP Upload 仍只处理 JPEG、PNG、WebP 图片；没有视频上传、视频播放或视频
Worker 传输。`media_type=video` 只是数据库与领域枚举的扩展边界，不代表功能已开放。

上传仍要求 `.jpg/.jpeg/.png/.webp` 文件名；在此范围内，文件实际签名决定 MIME、存储后缀和
下载文件名后缀，不因浏览器根据错误后缀上报的 MIME 拒绝合法图片。例如 PNG 内容名为 `.jpg`
时按 PNG 原字节保存，下载名校正为 `.png`，不转码、不损失透明度；已正确的 `.jpeg` 名称保留。
若校正后的更长后缀会超出既有 255 字符上限，仅截短文件名主体以保持上限。
未知签名、非图片和其它未支持格式仍返回 `ASSET_TYPE_UNSUPPORTED`，大小、权限、存储及引用保护沿用原入口。

## 2. Asset 不是什么

- Asset 不是 AI Generation Job。Prompt、模型、生成状态、成本不进入 Asset 表；未来 Job 成功后
  可以产生零到多个 Asset。
- Asset 不是 Task。执行状态、目标 Worker 和运行日志属于 Task；`task_assets` 只保存有序关系。
- Asset 不是 Shop。Asset 不持有 `shop_id`，同一资产可以被多个店铺、多个任务复用。
- Asset 不是素材组。V2 不建立 Group、Folder、Tag、Album 或商品素材集合。

## 3. 分层与创建流程

正式依赖方向为：

```text
HTTP Upload / 未来 AI Job
            ↓
       AssetService
       ↙          ↘
AssetStorage    AssetRepository
                     ↓
                 PostgreSQL
```

HTTP Router 只校验 HTTP 输入并将 `ActorContext` 交给 `AssetService.upload`。Human Upload 的
Ownership 固定来自当前 Actor，客户端不能提交或覆盖 `team_id / created_by_user_id`。`upload` 将
来源固定为 UPLOAD 后复用不依赖 FastAPI、`UploadFile` 或 Request 的 `AssetService.create`；内部
调用必须显式提供可信 `AssetOwnership`。未来 AI Image Job 获得文件流后直接调用同一内部入口，
传入 Job 继承的 Ownership 并指定 AI_GENERATED；禁止通过 Backend 自己发 HTTP 上传，也禁止另建
`ai_images` 文件系统。

Service 是 Storage 与 Repository 的协调和事务边界：先完成文件验证及原子写入，再新增 Asset
Row 并提交；数据库失败时回滚并删除本次新文件。Repository 只访问数据库，不做磁盘 IO；Router
不计算 SHA、不生成 Storage Key、不决定磁盘目录。

## 4. Storage Adapter

`AssetStorage` 是最小 Protocol，只包含：

- `store`：写入字节流并返回稳定 Storage Key、真实大小和 SHA-256。
- `open`：读取对象内容。
- `delete`：删除对象。
- `exists`：检查对象是否存在。

根目录来自 Backend Settings 的 `BACKEND_ASSET_STORAGE_DIR`；业务层不硬编码 Windows、Linux
或源码目录。`BACKEND_ASSET_STORAGE_MODE=local` 保留现有 `LocalAssetStorage` 行为：根目录可按需
创建。`mounted` 使用同一套文件读写与原子写入逻辑，但要求根目录已经由宿主机挂载完成，且存在
内容为 `control-center-asset-storage-v1` 后紧跟一个 LF（`0x0A`）的
`.control-center-asset-storage-v1` 标识文件。

`mounted` 模式不会创建 Storage Root。根目录、标识文件或读写执行权限不可用时，上传、读取、删除
和存在性检查都会明确返回 `ASSET_STORAGE_UNAVAILABLE`（HTTP 503），而不是写入 VPS 上由 Docker
意外创建的空目录。它只验证**容器内应用目录**的标识与权限，不把该检查当作 NAS 身份证明。生产发布
脚本在创建 Backend 容器前还会验证 Compose 的宿主绑定源是实际的 CIFS/NFS 网络文件系统；普通本地
目录即使具有相同标识文件也会被拒绝。两项检查都通过后，才允许 Migration。`AssetService` 与 AI
生成执行器通过同一个 storage factory 取得实例，确保上传、历史 Asset 读取和 AI 生成输出落在同一根
目录。

两种模式都先写同根临时文件、flush/fsync，再原子 replace 到 Storage Key；用户文件名
不参与唯一键，因此同名不会覆盖，路径组件也不能逃逸 Storage Root。

Frontend、Worker、Task Contract、日志和错误响应都不返回服务器绝对路径。Frontend 使用正式
Asset Content API，并通过统一 Human HTTP Client 携带 Cookie 与 Active Team Context 后读取
Blob；Worker 使用 Device Token 与 `X-Device-ID` 调用 Task Asset Download API，永远不读取
`storage_key` 或 Backend 磁盘。Human Scope 与 Worker Task/Device Authorization 是两条独立链路。

### 图片缩略图 V1

每个 IMAGE Asset 的原图仍由数据库 `storage_key` 唯一定位。缩略图没有第二个 Asset Row、公开 URL
或数据库字段，而是以原图 Storage Key 派生的同目录 key
`<asset_id-hex>.thumbnail.webp` 保存，固定为 WebP、最大边长 320px。这个 key 是 Backend Storage
内部事实，客户端只能使用受相同 Human Auth、`asset` Module Access 与 Scope 保护的
`GET /api/v1/assets/{asset_id}/thumbnail`。

新上传和 AI 输出通过同一 `AssetService.stage_for_transaction` 在原图落盘后尽力生成缩略图；原图、
Asset Row 与 AI Generation Item 的成功不依赖缩略图一次生成成功。若缩略图写入或图片解码暂时失败，
原图仍可通过 `content` 读取，AI Item 不会保持 RUNNING；下一次授权缩略图请求才会按需读取原图、
生成并以同一原子 Storage 写入复用。已有 Asset 也走此按需路径，成功后不会在后续浏览时重复读取原图。
挂载不可用继续返回 `ASSET_STORAGE_UNAVAILABLE / 503`；可读原图无法生成缩略图时返回
`ASSET_THUMBNAIL_UNAVAILABLE / 503`。Frontend 显示共享的加载占位与显式重试，不把缩略图失败解释为
生成任务失败。

原图 `/content` 的 MIME、字节、SHA-256、下载、放大查看及 AI 输入契约不变。缩略图端点仅用于卡片
显示，允许浏览器作 `private` 缓存，并按 `Cookie, X-Team-ID` 变化；Blob URL 在组件失活时必须撤销。
删除未引用 Asset 时，在原图删除后尝试删除同一派生缩略图，仍遵循本节后述的跨系统非原子边界。视频
没有缩略图、转码或播放器实现，继续属于后续独立需求。

### 日期目录 V1

新原图的 Storage Key 在开始写入时以 UTC instant 换算到固定 `Asia/Shanghai`，格式为
`YYYY/MM/DD/<asset_id-hex>.<suffix>`；它不接受客户端日期，也不使用可能晚于文件写入的数据库
`created_at` 默认值。派生缩略图复用原图的 `YYYY/MM/DD` 目录，因此两者始终同目录。Asset ID、业务
关系、权限、下载与 Worker 传输 Contract 均不变。

原有扁平 `<asset_id-hex>.<suffix>` Storage Key 继续可读，V1 不迁移、移动或复制任何历史文件。日期
目录键由当前 Storage Adapter 严格限制为三层数字日期加文件名，避免把任意嵌套路径作为 Storage Key
接受。

日期目录 Feature 之前的旧 Backend 只接受扁平 key，不能读取新日期目录 key。因此一旦已有新路径文件，
不得把应用直接回滚到日期目录 Feature 之前的 release；如需回退，必须使用仍包含新旧 key 读取能力的
兼容 release，并保留 NAS / Local Storage 上的全部新文件。这个限制不影响旧文件读取，也不意味着本轮
执行历史迁移。按产品、模板或生成批次把下载文件写入浏览器目录的能力尚未实现；当前多文件下载仍是逐个
浏览器下载，不能把 NAS 日期目录误认为该功能。

## 5. 生命周期与 Task 兼容

未被引用的 Asset 可以删除，生命周期固定为：带 Scope 的行锁查询 → 引用保护 → Storage
`verify_ready()` → 数据库删除并提交 → 实际 Storage 删除。预检失败时 Service 回滚当前数据库事务以
释放行锁，不删除 Asset Row，也不触碰原文件；`mounted` 模式因此向 DELETE 返回
`ASSET_STORAGE_UNAVAILABLE`（503）。被任何历史 Task 引用的 Asset 返回 `ASSET_IN_USE`，既不删 Row
也不删文件，确保历史 Task 不断引用、不出现 500。

数据库与 NAS 不是跨系统原子事务：正常的数据库提交失败会回滚，且不会尝试文件删除；实际文件删除在
提交后失败时，DELETE 返回 Storage 错误，已提交的 Asset Row 不会恢复，物理文件可能保留为孤儿文件。
这不是“交换删除顺序”可以消除的分布式一致性问题；本轮不引入补偿框架。发布或后续运维只能按稳定
`storage_key`（及其派生缩略图 key）审计和清理这类孤儿文件。数据库连接在提交结果不确定时也不得声称文件与 Row 具有原子
一致性，应按数据库事实进行恢复核对。

V2 不做全局去重。两个文件即使 SHA-256 相同，也可以拥有两个 Asset ID 和两个 Storage Key。

Task→Worker V1 保持图片专用兼容边界：TaskService 只允许 `media_type=image` 进入
`task_assets`；Worker Claim 仍精确返回 `asset_id / filename / position / content_type /
size_bytes / sha256 / download_path`，不增加 V2 内部字段。Worker 0.4.6 继续通过认证下载、校验
SHA-256 后写入 images_dir，无需升级。

## 6. 未来扩展

未来 AI 图片：`AI Generation Job → AssetService.create(AI_GENERATED, IMAGE) → asset_id`。

未来 AI 视频：先建立真实 Video Job 与文件校验需求，再复用同一 Service/Storage 并创建
`media_type=video` 的 Asset。Job 状态与高级媒体元数据仍属于各自 Domain；不把 duration、codec、
prompt、model 等提前塞进 Asset 表，也不在本轮引入 MinIO/S3、CDN 或缩略图服务。
