# 超级账号与团队授权 V1

## 1. 当前权威边界

本文件定义 `20260919_0037_super_account_team_authorization_v1` 之后的
正式人员权限模型。`13-Access Foundation V1.md`、`14-Human Auth V1.md`、
`16-Access Management V1.md` 中关于默认团队、`access_admin`、成员级模块
授权和 `SELF/TEAM/ALL` 的描述仅保留为升级前历史背景；当前请求和写入以本文件、
Pydantic schema 与 Service 为准。

系统只有两类人员：

| 类型 | 当前授权事实 | 团队关系 |
| --- | --- | --- |
| 超级账号 | `users.is_super_account = true`；拥有全部正式模块、公司资源和跨团队读取/管理能力 | 不需要、也不得依赖默认 TeamMembership。写入 Team-owned 对象时必须通过 `X-Team-ID` 明确目标团队。 |
| 普通成员 | 一条启用的 `TeamMembership` 与该 Team 的授权关系 | 至多一条启用 Membership；没有时仍可登录，但没有模块菜单和业务资源。 |

超级账号只能由受信任运维命令显式指定，绝不由登录名、旧 `access_admin` 角色或团队成员关系推断。
普通成员不能修改团队授权、公共凭据或公司资源归属。

## 2. 授权关系与生命周期

```text
User (super / normal)
  normal ── one enabled TeamMembership ── Team
                                           ├─ TeamModuleAccess
                                           ├─ TeamDeviceAccess
                                           └─ TeamShopAccess
```

- `team_module_accesses(team_id, module_code)` 是菜单与 Human API 模块 Guard 的唯一普通成员模块来源。
- `team_device_accesses(team_id, device_id)` 与 `team_shop_accesses(team_id, shop_id)` 是公司公共设备、店铺可分配给多个团队的关系；设备连接配置、Credential 和 ShopSession 不复制。
- `team_memberships` 的局部唯一索引只允许一个用户同时拥有一条 `enabled=true` 关系。停用行是历史，不参与当前授权。
- 当前 Team 授权变更、调组、移出成员或归档 Team 都会撤销受影响人员的服务端 Human Session；服务端仍在每个请求重新计算授权，不能由前端缓存恢复旧权限。

`membership_module_accesses`、`role_code` 和 `data_scope` 为历史升级/审计兼容数据，运行时不再作为普通成员权限输入。旧接口只保留最小读取兼容，不得为新 UI 新增成员级授权操作。

## 3. 请求身份与范围

```text
Human Session → HumanPrincipal → ActorContext → Module / Team resource guard → Service → Repository
```

- 超级账号未带 `X-Team-ID` 时可跨 Team 读取；带有效 Team ID 时将其作为写入归属上下文。
- 普通成员只能解析自己的唯一有效 Team；请求中的 Team ID 只是选择意图，不能扩大授权。
- 普通成员的列表、详情、搜索、分页总数、导出与 Asset Content 必须在 SQL 查询边界按 Team 过滤后再分页。直接 ID 读取同样应用 Team 条件。
- 无 Team 的普通成员对 `/access-management/me/module-access` 得到空模块集合，前端展示“未分配团队”；业务写入仍因缺少 Team 上下文拒绝。
- Worker 继续只使用 Device Token + `X-Device-ID`。Human TeamMembership、模块授权与资源授权不会进入 Heartbeat、Claim 或 Worker 身份链。

## 4. 资源和业务边界

设备和店铺的公共维护（创建、编辑、删除、连接、Credential/Session 管理、Device Binding）只允许超级账号。普通成员在已获模块与 Team resource grant 后，只能读取/使用获授权设备和店铺。

创建 Task 或 Schedule 时，后端同时验证：

1. 明确的 Team 归属；
2. Team 对目标 Device 和每个 Shop 的授权；
3. Device 启用、Shop 启用、有效 Shop–Device Binding、Credential/Session 与设备应用能力；
4. 参数预设、Asset 和业务对象的 Team 归属。

Device Binding 只表示执行资格，不能单独替代人员/Team 授权。撤销店铺、设备或模块授权后，新 Task 和后续 Schedule 触发会被拒绝或记录为 `BLOCKED`；已运行 Task 维持既有 Lease/安全执行规则，不被误杀或重复执行。

Asset、AI 产品/素材/生成结果、参数预设、Task 与 Schedule 均按 `team_id` 隔离；超级账号可跨 Team 读取，创建时仍选择明确 Team。历史 Task/Schedule 参数快照不因后续调组、授权变更或预设编辑而改写。

## 5. 管理操作

所有 `/api/v1/access-management/*` 人员、Team 与授权写操作要求超级账号：

| 操作 | 正式语义 |
| --- | --- |
| 创建成员 | 可指定一个 Team，也可创建未分配成员；新成员不会自动加入默认 Team。 |
| `PUT /members/{user_id}/team` | 指定 Team 时先停用旧有效关系再启用/创建新关系；`team_id: null` 表示移出团队。 |
| 移出成员 | 保留 User、已停用 Membership 和审计；撤销当前会话，不搬迁 Team 的素材、预设、历史 Task 或计划。 |
| 调组 | 同一事务中旧 Team 权限失效、新 Team 授权生效；不得留下两条有效 Membership。 |
| 更新 Team 授权 | 原子替换该 Team 的模块、设备、店铺集合；资源 ID 必须真实存在。 |
| 归档 Team | 停用 Team 与有效成员关系、撤销成员会话；业务数据与历史授权行保留。 |
| 删除 Team | 仅空 Team（无成员、资源授权和业务引用）可删除；否则返回 `TEAM_IN_USE`，不得级联删除。 |

超级账号自身不能通过普通成员调组接口被加入 Team，且不能停用系统中最后一个启用超级账号。超级账号交接使用受信任 CLI，不提供面向普通管理 UI 的提升入口。

## 6. 迁移与生产发布前置

Migration `20260919_0037` 增加：

- `users.is_super_account` 与唯一局部索引；
- Team 级模块、设备、店铺授权表和必要索引；
- 一人一条有效 Membership 的局部唯一索引；
- `audit_logs.team_id` 可空，以记录全局超级账号管理动作。

迁移只会复制**已证实相同**的旧成员模块集合，并只从既有 `devices.team_id` 种子化设备授权。它不会猜测 Shop 归属、不会把旧 `access_admin` 升级为超级账号、不会为多 Team 成员选择一个 Team，也不会用并集/交集归一不同成员模块权限。

升级前置检查会拒绝：

1. 有多个启用 TeamMembership 的用户；
2. 同一 Team 的启用成员存在不同旧模块授权集合。

生产 Release 前必须由受信任运营人员完成并记录：超级账号的精确 `user_id`、每个多 Team 成员的调组决定、每个 Team 的统一模块集合、无归属 Shop 的明确授权 Team/保留方案。执行 Migration 后，用以下交互式命令指定唯一超级账号：

```powershell
cd backend
.venv\Scripts\python.exe -m app.cli.human_auth designate-super-account <USER_UUID>
```

该命令不接受密码参数、不输出凭据、不按名称猜用户；已有其他超级账号时失败。迁移和 designation 都只能在经授权的发布窗口执行，不能由开发或 Integration 环境替代生产事实。

降级仅在不存在 `team_id IS NULL` 的全局审计记录时允许恢复 Audit 非空约束；一旦产生超级账号全局审计，必须保留 0037 或通过另行审查的数据迁移处理，不能强行回滚。

## 7. 验证责任

商品中心 UI_ONLY 模块登记：`ModuleCode` 新增 `product-selection`（选品库）、`product-library`（商品库）。现有 TeamAuthorizationUpdate
及 ModuleAccessService 继续负责授权保存、读取和校验；超级账号获取全部已登记模块，普通成员只获得当前
有效团队的显式授权。无自动种子或权限迁移，不借用其他模块授权。

只扩展既有模块值契约，不新增 API 或业务 Service；`team_module_access.module_code` 仍为现有字符串列，
无 Schema / Migration。升级顺序 Backend 先或前后端同版本发布，再由超级账号按需分配团队模块；
旧 Backend 不支持保存新模块值，不能用前端放行补偿。回滚前如已实际分配新值，须先通过正式授权入口
撤回新模块授权，再回退 Backend，避免旧枚举无法读取；不得直接改生产表。

Gate 1 必须验证 PostgreSQL `0036 → 0037 → 0036 → 0037`、迁移歧义拒绝、超级账号无 Team、普通成员范围、共享 Device、跨 Team 直接 ID 拒绝、移出/调组/归档/空 Team 删除、资源撤销后的 Schedule 阻断以及 Worker 身份未变。

Gate 2 必须在 Integration 的真实 Electron（`5180 / 8100 / control_center_integration`）执行超级账号、A/B Team 普通成员、共享设备和隔离素材/预设/Task/Schedule 场景。浏览器 Mock、构建或截图不能替代该验收。
