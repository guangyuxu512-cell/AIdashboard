# 定时计划与后台调度规范

## 1. 边界

Scheduler 只回答“什么时候创建 Task”。正式链路为：

```text
Schedule
→ Backend Due Scanner
→ ScheduleService
→ TaskService
→ 普通 PENDING Task
→ Worker Poll / Claim / Lease / Executor
```

禁止 Scheduler 连接 Worker、调用 ShadowBot、直接 INSERT `tasks` 或建立第二套执行状态机。Worker 不知道 Task 来源，仍只消费普通 Task。

## 2. 重复规则与时间语义

Schedule 只支持以下三种明确规则：

- `once`：`local_date + local_time + timezone` 表示唯一一次本地墙钟 occurrence；执行后
  `next_run_at=null`，过去的启用一次性计划不会补建历史 Task；
- `daily`：每天在 `local_time + timezone` 触发；
- `weekly`：每周 ISO weekday（`1=周一` 至 `7=周日`）的已选日，在
  `local_time + timezone` 触发。

每条 Schedule 显式保存无时区的 `local_time`、IANA `timezone`、可空 `local_date`、
JSON weekday 数组和 UTC `timestamptz next_run_at`。数据库约束保证三种规则的字段组合互斥且完整；
Due Query 只扫描 `enabled=true AND deleted_at IS NULL AND next_run_at <= now`，不全表临时计算。

时间计算统一位于 Schedule Domain，使用 Python `zoneinfo`：

- 正常日期按所选时区的本地墙钟时间解析；
- DST 不存在的本地时间顺延到同一天第一个有效分钟；
- DST 重复时间采用第一次出现的 Instant；
- Frontend 只展示 Backend 的 `next_run_at`，不自行计算下一次执行。

## 3. Trigger、幂等与漏跑

`schedule_runs` 表示一个理论触发时刻，不复制 Task 的 PENDING/RUNNING/SUCCESS/FAILED/LOST 状态机。`UNIQUE(schedule_id, scheduled_for)` 是最终幂等边界。

Due Schedule 使用 `next_run_at ASC, schedule_id ASC` 稳定顺序和 `FOR UPDATE SKIP LOCKED`。同一事务内完成：锁定 Schedule、按 COALESCE ONE 选择最近一次错过的 occurrence、调用 TaskService、写 ScheduleRun、关联 Task、推进次日 `next_run_at` 并 Commit。事务失败整体回滚；重复扫描、Backend 重启或未来多实例不会为同一 occurrence 创建重复 Task。

V1 的 Missed Run 固定为 `COALESCE ONE`：无论错过几天，恢复后只为最近一个已到期 occurrence 触发一次，不补全部历史。一次性计划成功或被阻止后都不再有下一次 occurrence。

## 4. 发生日期筛选

`GET /api/v1/schedules` 可同时接收 `occurrence_date=YYYY-MM-DD` 与
`view_timezone=<IANA timezone>`。Backend 以同一 DST 解析规则计算该本地日期的 UTC 半开区间
`[start, end)`，然后在 SQL、分页和总数之前筛选：

- `schedule_runs.scheduled_for` 位于区间内；或
- 当前 `schedules.next_run_at` 位于区间内。

因此已经执行的当日 occurrence 不会因为 `next_run_at` 已推进或过期而被隐藏。停用计划没有未来
`next_run_at`，但若有该日期的历史 ScheduleRun，在未额外传递 `enabled` 筛选时仍会显示；传递
`enabled` 时与该状态筛选相交。两个日期参数必须同时提供，Frontend 只传浏览器明确选择的时区，
不在本地重算 occurrence。

## 5. Guard 与状态

Schedule 保存时和触发时都复用 Task/Application 或 Business Skill 参数 Contract。触发时：

- Device OFFLINE：允许创建 PENDING，等待后续上线 Claim；
- Device disabled/deleted、Skill 缺失、Provider 不可用/需登录、Application 消失、参数 Schema 变化后失效：不创建 Task，写最小 `blocked` ScheduleRun，并推进下一次执行，避免高频重复；
- 三个同设备同时间计划会稳定创建三个 PENDING Task；Worker 当前单活动 Task 和 Provider capacity=1 负责依次执行，前一个 FAILED 不阻止后一个 Claim。

Schedule 的 `execution_type` 明确区分 `yingdao_application` 与 `business_skill`：

- 影刀应用固定映射 `yingdao.app.run`，Application 来自所选 Device 的 Provider Inventory，参数
  继续复用 `AutomationApplicationConfig`；
- Business Skill 来自所选 Device 的 Business Skill Catalog，`skill_id` 是目标 Skill，参数按
  当前 Catalog Input Schema 校验；Internal Skill 永不进入普通 Scheduler 选择器。

Schedule 保存稳定的 Device、有序 Shop 集合（可为空）、Skill、执行对象显示名快照、时间、IANA 时区和
enabled 列；动态 Task Input 使用 JSONB。Shop 集合保存在规范化 `schedule_shops`，不进入
`task_input_json`。Business Skill 保存时必须存在且 Schema 可用，触发时再次按当前 Device
Capability、当前 Schema 及（仅非空集合）每个 Shop 的有效 Binding 与 Credential 校验。Skill 消失、Schema
缺失、旧参数失效或非空集合中任一 Shop 已解绑时，本次 ScheduleRun 记录 blocked 且不创建非法 Task；不得
偷偷改写参数、删除已保存 Shop 或只执行剩余子集。合法触发只调用 TaskService 创建一个普通
Task，并按保存顺序复制整个 Shop 集合；空集合对应 Worker Claim 的 `accounts=[]`。账号明文只在
Worker Claim 时解密，Worker 不知道 Task 来源。

创建 Schedule 时，Frontend 可将所选 Device 的全部有效绑定 Shop 默认全选；保存后，Shop 集合是
明确配置。以后 Device 新增 Binding 不得自动加入既有 Schedule，编辑时必须保持已保存集合，只有
用户主动勾选才改变。

影刀计划可选保存同一 Team 可访问的参数预设，而不是永久绑定 Device。保存计划时仍完成当前 Device、
Shop 启用状态、Binding、Credential、Provider 与参数 Schema 校验；到点时再次以实际目标 Device 校验。
每次成功触发从预设最新已保存版本物化一个新的 Task 参数快照；预设已保存的字段集合是该次物化边界，未启用的
可选 Schema 字段不能因默认值重新加入。当前 Schema 新增必填字段而旧预设未显式保存时，本次 Run 明确 blocked，
不得静默补默认值、改用旧参数或手工参数；修改预设绝不改写已创建 Task。未归档计划引用预设时会阻止其逻辑
删除（停用计划也一样）；已归档计划保留历史引用但不会再次触发。预设不属于该 Team 或已不兼容时，同样按正式
失败记录收口。

## 6. 生命周期与后台服务

移除 Schedule 使用软归档：停用、清空 `next_run_at` 并写 `deleted_at`。ScheduleRun、Task 和 Runtime Event 历史保留；已知 Schedule ID 仍可读取 Run 审计记录，普通管理列表和详情排除归档计划。

Backend lifespan 独立启动 Scheduler 与 Runtime Event Retention。Scheduler 扫描间隔和单批上限来自 Settings；每次扫描异常记录日志并进入下一周期，正常 Shutdown 取消并等待任务。两个后台服务拥有独立循环、Session 和异常边界，一个失败不得终止另一个。

## 7. 权限与范围

全部 Schedule Human API 使用 Human Session、`schedule` Module Access 和 ActorContext。Create 从
ActorContext 写入 Team 与业务发起人；读取、更新、归档和发生日期筛选都在 Repository 的 SQL Query
边界应用 `SELF / TEAM / ALL`。Authorization 与 Device/Provider/Application 等业务合法性分离；
Permission 不进入 Repository，Data Scope 不由 Frontend 本地过滤。

## 8. 罗盘经营数据每日计划

经营数据不是 `Schedule → Task → Worker` 链路的一部分。它只为已保存、已启用且已接入经营采集的抖店创建
`operating_data_collection_jobs/items`，随后由服务端的现有 ShopSession + Signer + Connector 执行。每日计划
按 Asia/Shanghai 的 `BACKEND_OPERATING_DASHBOARD_DAILY_COLLECTION_LOCAL_TIME`（默认 `09:00`）判断“昨日”业务日期，
并以 `daily:<business_date>` 幂等键确保多个 Backend 扫描、重启或多进程不会重复建同一天计划。

执行器与每日计划必须同时显式启用，并配置非空的
`BACKEND_OPERATING_DASHBOARD_DAILY_COLLECTION_LOCAL_TIME`：
`BACKEND_OPERATING_DASHBOARD_COLLECTION_EXECUTION_ENABLED=true` 和
`BACKEND_OPERATING_DASHBOARD_DAILY_COLLECTION_ENABLED=true`。任一为 false 时 FastAPI lifespan 不启动对应
循环，也不执行启动补漏，避免 Feature/Integration 或仅部署了 API 的环境自动访问平台。数据可用时刻由实际平台
验证决定；计划只在配置时刻后尝试，并把暂时性错误留给 item 的有限 retry，不保证每天固定墙钟一定已有昨日数据。

Backend 启动发生在该墙钟时刻**之前**时，只能执行短数据库恢复（回收过期 lease、跳过停用或已确认未经营
日期的 pending item）；不得创建或占用当天 `daily:<business_date>`。这样启动恢复不会把平台尚未准备好的
昨日请求抢在正常日计划之前。到达时刻后，启动恢复和周期扫描才可走同一个 `daily:` 计划入口。

上述两个开关只控制**每日/启动自动触发**。既有店铺 Onboarding 和重新启用在同一业务事务中仍会按已有语义写入
有限的 `initial_backfill` / `reenable_backfill` 持久化计划；这不是日计划的隐式旁路，且当 execution 开关为 false
时执行器不会消费任何 item、不会发起平台 I/O。手动更新继续由它自己的 execution 开关与当前授权校验控制。

每日、Backend 启动、新建/重新启用 Shop 与有效 Session 重新授权均复用同一个有限补漏服务：先昨日，再由近到远
检查最近 30 个完整自然日（含昨日、不含今日）的缺口。若 Shop 有经管理人员明确确认的 `operating_start_date`，每个入口
都只检查该窗口与已确认经营期间的交集；此前日期不创建 item，也不会向平台发请求。起算日未知时保持完整窗口，不能从
接入时间、首单或首次采集猜测裁剪。有效成功核心事实要求已确认的成交金额和成交订单字段均非空；
同时必须匹配当前数据来源和指标契约；真实 `0` 是成功，不是缺口。0040 前核心事实的退款状态为 `unobserved` 时，
只允许一次有界的 `refund_order_cnt` 观测；之后的退款字段缺失、未就绪或结构异常分别进入可见状态，不能令日计划
无限重试。商家体验分 `null` 不参与补漏判断。查询需要上一等长区间而历史事实缺失时，调用方可明确提交不超过 60 个完整自然日的手动补采范围；不得因打开
看板、日计划或启动默认反复拉 60 天。

同店同日期已有 pending/running/paused item 时复用原 item；等待重新授权的 item 不会被每日扫描重复创建。自动
重试只对 retryable 失败开放，并同时遵守 `BACKEND_OPERATING_DASHBOARD_GAP_RECOVERY_RETRY_COOLDOWN_SECONDS`
与 `BACKEND_OPERATING_DASHBOARD_GAP_RECOVERY_MAX_ATTEMPTS`；不可重试的平台业务拒绝保留为可见失败，等待明确的
受控处理，不被后台高频请求。普通“更新数据”同样不会绕过终态失败、冷却或上限；它只补当前核心指标缺口，
完整范围不创建空 job。用户显式选择“重新采集当前筛选范围”时仍受同一终态/冷却/授权/停用/活动 item 保护，
并且失败不会覆盖已有成功事实。这个限制不把失败日变成数据墓碑：在有受控证据和既有 retry 契约的前提下，
可以按当前权限安排有限恢复。
解析契约修复也不改变这个全局限制：只有受控样本已经证明受某一解析缺陷影响的 Shop/日期，才可通过既有有界
补漏规划进行有限恢复；原失败 item 保留，不批量改状态，也不把所有不可重试失败改为可重试。

另有一个**只针对旧启动时序缺陷**的一次性恢复：仅当原 `daily:<business_date>` Job 本身和某个同日 item 都在
配置墙钟时刻前创建/开始，并且该 item 恰为 `failed`、`retryable=false`、`attempt_count=1`、
`DOUYIN_OPERATING_DATA_REJECTED / platform_response`、已结束时，时刻到达后才可建立一份
`daily-recovery:<business_date>` Job。该恢复只携带符合条件且当前仍启用的 Shop，原失败记录保留；恢复 Job 的
独立稳定键保证最多一次。它是对“日计划过早占键”的程序性修复，不把任意非零平台 `st` 解释成“数据未就绪”，
也不适用于时刻后出现的拒绝、会话/风控、解析错误或历史失败。

旧版曾将非核心响应字段误作核心字段，因而留下的终态 `response_parse` 失败不能仅凭通用失败码自动重试。当前核心路径若只返回
`unit`、没有标量值，则以专用 `DOUYIN_OPERATING_DATA_METRICS_UNAVAILABLE` 终态和看板 `unknown` 状态保留；它没有已证实的
平台零值或未经营语义，不能进入自动补漏或本段的恢复例外。若发布
核验以只读证据确认某个**原始** item 确实属于该缺陷，可在 root-only 部署配置中设置
`BACKEND_OPERATING_DASHBOARD_LEGACY_RESPONSE_PARSE_RECOVERY_ITEM_IDS` 为该 item UUID 的 JSON 数组。该列表默认
为空，且每个 UUID 还必须同时满足：`failed`、`retryable=false`、`attempt_count=1`、
`failure_code=DOUYIN_OPERATING_DATA_INVALID_RESPONSE`、`failure_stage=response_parse` 和已结束。满足条件的原 item
仅获得一次由既有补漏规划创建新 item 的资格；新 item 一旦成为最新状态，旧 UUID 不再匹配，后续失败继续遵守原有
终态、冷却和上限。不得用此配置列出会话、风控、平台拒绝、专用 `unknown` 状态或未核验的解析失败；恢复完成后应从部署配置移除已处理 UUID。

启动恢复只在两个自动开关均为 true 时执行一次短数据库事务：回收过期 lease、跳过已停用店铺和已确认起算日前的 pending item；
仅在每日墙钟时刻已到后才运行同样的 30 日缺口规划。它不等待 Session、Signer 或平台响应。停用或软移除 Shop 不派发新的 item；
排队后停用的 item 标记跳过，已发出的请求不承诺撤回。重新启用只补有限窗口内仍缺失的日期。
