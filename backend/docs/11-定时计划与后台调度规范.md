# 定时计划与后台调度规范

## 1. 边界

Scheduler 只回答“什么时候创建 Task”。正式链路为：

```text
Schedule
→ Backend Due Scanner
→ ScheduleService
→ TaskService
→ 普通 PENDING Task
→ Worker Poll / Claim / Lease / Executor
```

禁止 Scheduler 连接 Worker、调用 ShadowBot、直接 INSERT `tasks` 或建立第二套执行状态机。Worker 不知道 Task 来源，仍只消费普通 Task。

## 2. DAILY 与时间语义

V1 只支持 `DAILY`。每条 Schedule 显式保存无时区的 `local_time`、IANA `timezone` 和 UTC `timestamptz next_run_at`；Due Query 只扫描 `enabled=true AND deleted_at IS NULL AND next_run_at <= now`，不全表临时计算。

时间计算统一位于 Schedule Domain，使用 Python `zoneinfo`：

- 正常日期按所选时区的本地墙钟时间解析；
- DST 不存在的本地时间顺延到同一天第一个有效分钟；
- DST 重复时间采用第一次出现的 Instant；
- Frontend 只展示 Backend 的 `next_run_at`，不自行计算下一次执行。

## 3. Trigger、幂等与漏跑

`schedule_runs` 表示一个理论触发时刻，不复制 Task 的 PENDING/RUNNING/SUCCESS/FAILED/LOST 状态机。`UNIQUE(schedule_id, scheduled_for)` 是最终幂等边界。

Due Schedule 使用 `next_run_at ASC, schedule_id ASC` 稳定顺序和 `FOR UPDATE SKIP LOCKED`。同一事务内完成：锁定 Schedule、按 COALESCE ONE 选择最近一次错过的 occurrence、调用 TaskService、写 ScheduleRun、关联 Task、推进次日 `next_run_at` 并 Commit。事务失败整体回滚；重复扫描、Backend 重启或未来多实例不会为同一 occurrence 创建重复 Task。

V1 的 Missed Run 固定为 `COALESCE ONE`：无论错过几天，恢复后只为最近一个已到期 occurrence 触发一次，不补全部历史。

## 4. Guard 与状态

Schedule 保存时和触发时都复用 Task/Application 参数 Contract。触发时：

- Device OFFLINE：允许创建 PENDING，等待后续上线 Claim；
- Device disabled/deleted、Skill 缺失、Provider 不可用/需登录、Application 消失、参数 Schema 变化后失效：不创建 Task，写最小 `blocked` ScheduleRun，并推进下一次执行，避免高频重复；
- 三个同设备同时间计划会稳定创建三个 PENDING Task；Worker 当前单活动 Task 和 Provider capacity=1 负责依次执行，前一个 FAILED 不阻止后一个 Claim。

Schedule 保存稳定的 Device、Skill、Application 展示名快照、时间、时区和 enabled 列；动态 Task Input 使用 JSONB。Frontend V1 只开放“影刀应用”，内部固定映射 `yingdao.app.run`，Application 来自 Device Provider Inventory，参数复用 `AutomationApplicationConfig`。

## 5. 生命周期与后台服务

移除 Schedule 使用软归档：停用、清空 `next_run_at` 并写 `deleted_at`。ScheduleRun、Task 和 Runtime Event 历史保留；已知 Schedule ID 仍可读取 Run 审计记录，普通管理列表和详情排除归档计划。

Backend lifespan 独立启动 Scheduler 与 Runtime Event Retention。Scheduler 扫描间隔和单批上限来自 Settings；每次扫描异常记录日志并进入下一周期，正常 Shutdown 取消并等待任务。两个后台服务拥有独立循环、Session 和异常边界，一个失败不得终止另一个。

## 6. 权限扩展插槽

当前不实现员工 Auth/RBAC。Schedule Create/Update/Delete 的未来形态为：

```text
API → get_current_user → require_permission("schedule.manage") → ScheduleService
```

Authorization 与 Device/Provider/Application 等业务合法性分离；Permission 不进入 Repository，Data Scope 不由 Frontend 本地过滤。
