# 后端架构与目录

推荐模块内部：
```text
modules/shops/
├── api.py
├── schemas.py
├── models.py
├── service.py
├── repository.py
└── exceptions.py
```

不要使用全局大平层：
```text
controllers/
services/
models/
```

`shared` 只能放真正跨领域能力。
业务语义放具体 module。

阶段 2A 已建立 `modules/users`、`modules/shops`、`modules/devices`。ShopDeviceBinding 的唯一权威实现归属 `modules/shops`，由 ShopService 管理店铺与设备之间的绑定规则。

阶段 3A 增加 `modules/credentials`、`modules/sessions`、`modules/authentication`：前两者分别持久化凭证与 Session，后者只定义未来平台认证及验证码 Provider 的纯 Contract/Protocol，不包含浏览器、Worker 或平台实现。

Scheduler V1 增加 `modules/schedules`，内部仍按 `api / schemas / models / service / repository / scheduler` 分层。`scheduler.py` 只是 Backend lifespan 下的 Due Scanner，它通过 `ScheduleService → TaskService` 创建普通 Task，不是独立执行系统，也不得直接依赖 TaskRepository。

Access Foundation V1 增加 `modules/access`，统一拥有 Team、TeamMembership、ActorContext、
Active Team 解析和当前超级账号/团队授权判定。Human Management API 从请求级 ActorContext 获取
身份与有效 Team；业务模块不得各自解析 Membership。`role_code / data_scope` 是旧数据兼容投影，
不得作为新授权路径。Human Principal 的认证来源与 Worker Device Token 完全分离。

Operating Dashboard Data V1 增加 `modules/operating_dashboard`，内部按
`api / schemas / models / repository / service / executor / scheduler` 分层：Repository 只做授权范围后的
SQL，Service 负责日事实、补采、状态机和错误分类，Executor 只 claim/finalize 持久化 item 并复用现有
Douyin Collector。平台 HTTP、Session 解密和 Signer 继续属于既有 `platforms/douyin` 与 `modules/sessions`；
不得在看板模块复制 Cookie、签名或原始平台响应处理。

## Device Lifecycle 与 Notification（阶段 3D-1）

- `modules/devices` 管理 enabled、软移除与活动任务保护。
- `modules/workers` 管理持久化 ONLINE/OFFLINE 转换、Credential 与 Heartbeat。
- `modules/notifications` 管理全局 NotificationChannel、事件开关与通知编排。
- `integrations/notifications` 只负责飞书/企业微信 Webhook payload 与投递，不反向依赖 Device。

通知属于提交后的旁路副作用；业务事务不得依赖第三方 Webhook 成功。
