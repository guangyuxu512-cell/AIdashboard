# 手机商品资料采集真实接入 V1

## 1. 状态与适用范围

本文是 `feat/mobile-product-collection-integration-v1` 的版本化实施契约，基线为
`65ecf3f72a6ae9ea3114d7404841ad9aae876565`。ca97 已登记独立 Feature DB、受保护连接、Backend 8101
和 Migration Slot `20261020_0049`（down=`20261019_0048`）。Schema 复核已 `ACCEPT`；0049 已在该
Feature DB 完成 upgrade、downgrade、upgrade，当前精确 Head 为 0049。中控侧 API、可靠派发关系、
完整包 Inbox、UU cleaner 窄适配、商品版本入库和结算 Outbox 已实现；三个后台阶段开关仍全部为
`false`。当前采用手机直传中控，不再采用 NAS 保存/转发完整包的方案。中控原接收能力可复用，
NAS 向手机透传短期凭据及仅状态完成接口仍须配对确认；不得把离线解析或合成配对测试写成实机直传通过。

V1 只建立以下闭环：

1. 人员在中控按手工商品标识或已授权候选提交商品资料采集；
2. 中控可靠地把抖音任务登记到既有手机网关；
3. 既有网关继续负责设备领取、重试、取消和手机执行；
4. 手机保持原采集和完整包生成逻辑，使用任务附带的短期凭据直接上传中控原接收入口，原包不经 NAS；
5. 中控复用既有 `convertCompletePackage()` 清洗，提交不可变版本和当前商品事实；
6. 中控入库后仅向 NAS 回报对应 Job 的终态；商品库提供 Team 隔离的最小分页列表、详情和采集进度查询。

不在 V1 内：商品完整 CRUD、TXT/ZIP/目录导入导出、图片识别或 AI 改图、自动上架、店铺预检、
手机定时扩展、达人/百应、另建 Redis/Celery、外部服务直连中控 PostgreSQL。冻结前端候选
`e52570ffcb8f796301a67ee890ecb2c5f0056925` 不是本分支 Green 基线；只登记为后续经 ca97 审批后
正常 `--no-ff` 消费的 UI 依赖，不 cherry-pick、reset 或 rebase 到本候选。

平台边界：

- Douyin：V1 自动领取的唯一平台，网关必须 fail-closed；
- Pinduoduo：保持现有人工回传/统一清洗边界，不宣称具备 task/batch 直传；未来若直达中控，另冻
  `manual capture session` 协议；
- Taobao 及未知平台：拒绝进入自动队列。

## 2. 权威系统与禁止边界

- 中控是 Team 归属、人员授权、业务请求、商品当前事实和版本历史的权威。
- 手机网关是 `collection_jobs`、设备领取、`jobId`、`captureBatchId`、手机重试和取消的权威。
- 手机既有 Device Token 仅用于 NAS 领取任务，不用作中控 ingest 认证。NAS 只向当前领取手机透传
  中控签发的短期批次 credential；服务凭据和 HMAC 密钥绝不下发手机。中控不可信任手机提交的
  Team、人员、目标分组或权限结论。
- NAS 仅负责任务排队/分发与 Job 状态；不接收、暂存、转发原始商品包，也不写商品库。本任务不改
  NAS 队列、设备配对、claim/recovery 核心或手机采集/生成完整包逻辑。
- 浏览器只访问中控，不取得网关管理 Token、设备 Token 或服务凭据。
- 外部 Node/NAS 服务不得连接中控 PostgreSQL；服务间只走版本化 HTTP Contract。
- 中控不得通过 HTTP 回调自身；接收后的清洗和入库由中控 Domain Service/Inbox Processor 直接调用。
- 不保存 Cookie、认证 Token、平台请求签名、完整认证请求 URL 或 NAS 绝对路径。第 6 节明确允许的
  媒体资源级签名不作为身份凭据；只保留在来源包/不可变 UU 快照，对外展示投影仍按既有边界净化。

## 3. 稳定标识与认证

### 3.1 稳定标识

| 名称 | 生成方 | 语义 |
|---|---|---|
| `request_id` | 中控 | 一次人员业务提交 |
| `item_id` | 中控 | 提交内一个去重后的平台商品目标 |
| `dispatch_id` | 中控 | 一次向网关登记的可靠派发；网络重放和有限重试复用，显式重采才新建 |
| `external_job_id` | 中控 | 网关幂等键，等于版本化的 `dispatch_id` 表达，不复用旧失败派发 |
| `gateway_job_id` | 网关 | 既有 `collection_jobs.job_id` |
| `capture_batch_id` | 网关 | 每次设备 claim 新生成的批次 fence |
| `attempt_id` | 中控 | 对一个 `gateway_job_id + capture_batch_id` 的注册记录 |
| `upload_receipt_id` | 中控 | 原始完整包可靠接收回执 |
| `persist_receipt_id` | 中控 | 清洗与数据库提交完成回执 |
| `product_id` | 中控 | Team 级商品库身份 |
| `version_id` | 中控 | 一个不可变来源版本 |

平台商品 ID、SKU ID、网关 Job ID、Device ID 和 Capture Batch ID 全链路均按字符串处理；不得经过
JavaScript Number、数据库整数或任何浮点类型。

### 3.2 认证分离

1. 人员 API 使用现有 Human Session、`ModuleCode.PRODUCT_LIBRARY` 和 ActorContext。
2. 中控到网关使用独立服务凭据；不得复用人员 Cookie、网关人工管理 Token或手机 Device Token。
3. 网关到中控的 attempt 注册和状态通知使用独立服务凭据，凭据放受保护配置，不进入业务表。
4. claim 提交后，网关以服务身份注册 attempt；中控返回只绑定
   `gateway/device/job/batch/platform/product` 的 opaque ingest credential。
5. credential 由中控以受保护的 256-bit 服务密钥、attempt/batch 和每 attempt 128-bit 随机 salt 经
   HMAC-SHA256 派生；响应丢失时可对同一 attempt 幂等重发。数据库只保存 key id、salt、SHA-256 hash、
   签发/消费/失效时间和绑定关系，不保存明文。
6. 手机 Device Token 仍只用于网关；NAS 只持久化 attempt/credential ID、时限等非秘密元数据。
   已注册的 `controlIngest` 作为领取响应中的独立上传描述交给当前手机，不写入完整包正文、日志、截图
   或任务公开查询结果。注册/续发响应使用 `Cache-Control: no-store`。凭据到期时只允许 NAS 经已有
   internal refresh 接口续发同批次凭据；不能让手机持有服务 Token，也不能重新 claim 或重采来补传原包。

服务认证失败为 401/403，不进入业务重试；目标绑定不一致为 409，不能降级为宽松接收。

## 4. 人员 API

统一 Service 接受两种来源，API Contract 使用有鉴别联合而不是散落的页面请求。

### 4.1 创建请求

`POST /api/v1/product-collection/requests`

共同字段：

- `submission_key: UUID`：同一 Team、人员和 key 幂等；
- `target_group_id: UUID | null`：`null` 表示未分组；
- `source`：
  - `manual`：`targets[{platform, product_id_or_supported_url}]`；
  - `selection_candidates`：`candidate_ids[]`。

服务端规则：

- Team 只来自当前 ActorContext；Body、手机和网关提交的 Team 一律不可信。
- 手工来源要求明确 Team 上下文。候选来源逐个通过既有候选可见性规则解析，并要求同一 Team；
  不可见、跨 Team、已删除来源返回 404，不泄漏其存在性。
- 候选解析后只冻结标准化 `platform + source_product_id`，不复制前端 Mock 字段。
- 分组必须属于同一 Team 且未归档；否则 404。
- 同一请求内相同平台商品去重；同一 submission key + 同规范 payload 返回原请求，payload 不同返回 409。
- Douyin 可进入自动派发；PDD 只登记人工边界，不进入自动 claim；未知/淘宝返回明确不支持。
- 返回 202 表示业务请求已持久化，不表示网关已领取或商品已入库。

### 4.2 查询、取消与重试

- `GET /api/v1/product-collection/requests/{request_id}`：返回聚合状态、逐 Item 状态、已接收/已入库数和
  脱敏失败；授权过滤在聚合前完成。
- `GET /api/v1/product-collection/requests?page=&page_size=`：复用 `DataScopePolicy`，超级账号未选 Team
  时跨团队读取，选定 Team 后只读取该团队；普通成员保持当前有效团队隔离。列表、总数与直接详情均在
  SQL 聚合／分页前应用同一范围，稳定次序为
  `created_at DESC, request_id DESC`。
- 读取不推断写入团队。新建、取消、有限重试与重新采集仍要求明确 Team，且目标必须属于该 Team；
  “全部团队”写入返回 `TEAM_CONTEXT_REQUIRED`，跨范围目标仍不可访问。商品库只读范围见 4.3，不因跨团队读取扩大写权限。
- `POST /api/v1/product-collection/requests/{request_id}/cancel`：只取消非终态 Item；已开始的手机网络动作
  只能请求网关取消，不能承诺物理撤销。
- 取消请求到达网关时，若网关按既有严格冲突格式确认同一 `gateway_job_id` 已是 `failed`，中控保留
  `cancel_requested_at/by_user_id` 审计，但以网关权威终态将原 Dispatch/Attempt/Item/Request 对账为失败，
  不伪装成取消成功，也不永久保留 running。只有精确 `failed/canceled` 终态可对账；网络错误、未知 409、
  completed 或无法解释的业务响应继续保留原状态并等待安全处理。回写前必须复核 Team、当前 Dispatch 和
  `gateway_job_id`，迟到结果不得覆盖较新的派发结果。
- `POST /api/v1/product-collection/items/{item_id}/retry`：只允许明确可重试的原 Job；网络投递失败时
  以同 `external_job_id + canonical payload` 重放，网关执行失败/取消的有限重试调用既有 retry，复用
  原 `gateway_job_id/external_job_id`，保留并累加 attempts。
- `POST /api/v1/product-collection/items/{item_id}/recapture`：人员明确“重新采集”才新建
  `dispatch_id/external_job_id`。重试与重采不得混为同一种身份。
- Request 的取消审计不清空；取消意图只作用于 `Dispatch.created_at <= cancel_requested_at` 的当前派发。
  显式重采在持有 Request 行锁后读取数据库 `clock_timestamp()`，以该时间创建新派发；不得使用可能早于
  旧取消的事务起始时间 `now()`。这样旧取消仍作用于同请求的其他旧派发，但不会取消后来明确创建的重采。
  重采后的新取消更新取消时间，仍可终止新派发；普通 retry 复用旧派发，不借此绕过取消。原有 Team、
  current Dispatch、Gateway Job 迟到回写校验保持不变。

### 4.3 商品库最小查询

- `GET /api/v1/product-library/products`：列表、总数、搜索、分组/未分组过滤、分页和稳定排序统一在 SQL 边界复用 `DataScopePolicy`；超级账号未选 Team 时跨团队只读，选定 Team 和普通成员均只读该 Team；
- `GET /api/v1/product-library/products/{product_id}`：当前采纳版本、来源版本摘要、SKU/图片快照和最近
  采集状态；先用同一 `DataScopePolicy` 授权 Product，再严格按该 Product 自身
  `team_id` 读取 Version 与 Item，不使用当前选择团队替代资源归属；
- `GET /api/v1/product-library/groups`：使用 `DataScopePolicy` 只读当前授权范围内的未归档分组；分组筛选只接受同一读取范围内的 `group_id`。V1 不借此宣称已完成分组完整 CRUD。

商品库写操作权限不变；全部团队不允许编辑、导入、移动分组或重采。单商品 TXT
导出继续以已授权详情的 `adopted_version_id` 精确选择完整 `uu_snapshot`。

商品完全没有可靠价格时返回 `null`；真实 0 按 0 返回。外部图片只返回来源 URL，不通过带
`Authorization`/`X-Team-ID` 的中控 HTTP Client 代理请求。

## 5. 网关与手机协议

### 5.1 中控派发到既有网关

本节保留既有中控任务标识、创建 API 与 `taskId↔jobId` 映射，不新增一套队列。
`central_ingest_v1` 仍是现有中控协议名，不代表需要 NAS 转发数据；只有外部实现已明确把该模式的
原包上传定向到中控后，才能启用实际派发。不能直接部署旧 relay 候选来满足本节。现有 NAS legacy
创建响应与中控窄适配的兼容性须独立配对，不能把按商品复用的无关 Job 当作当前 Dispatch 的幂等成功。

中控使用稳定 `external_job_id` 提交网关。网关必须实现：

- 同 key + 同 canonical payload 返回原 Job；
- 同 key + 不同 payload 返回 409；
- 网络重放和网关有限 retry 复用原 key；只有人员显式 recapture 使用新 key；
- 新 Job 显式带 `ingest_mode=central_ingest_v1`；legacy Job 默认 `gateway_v1`，旧任务不会因新能力过滤
  被饿死；
- 自动 claim 仅允许 `source_platform=douyin`、`ingest_mode=central_ingest_v1` 且服务端登记允许该
  protocol/platform 的设备。heartbeat 上报只能进入 `reported_capabilities`，不能覆盖服务端维护的
  `assignment_protocols/assigned_platforms`，更不能作为授权依据；
- PDD、Taobao 和未知平台不得被 Douyin 自动化领取。

中控只保存派发关系和可靠投递状态，不复制网关的设备执行队列，也不提供第二套手机 claim。
派发领取使用短 lease 和 fence；进程在最后一次允许的 `delivering` 期间中断时，下一轮扫描会把到期
记录显式终态化为 `delivery_failed`，同步 Request/Item 的脱敏错误，而不是永久保留无剩余预算的
执行中状态。该恢复不创建新 Dispatch，也不绕过人员显式 recapture 边界。

新派发的手机执行预算使用 `BACKEND_PRODUCT_COLLECTION_CAPTURE_MAX_ATTEMPTS`：正式默认 3，合法正整数
范围为 1–3。隔离单次 Gate 在接受提交和计划派发之前设置为 1，并持续保留到网关登记完成；不增加人员
表单字段，不把隔离预算变为所有正常业务的永久单次限制。预算在创建 Dispatch 时进入原 canonical payload
hash，HTTP `maxAttempts` 使用相同值。0049 已保存该 hash，因此不新增列或改写迁移：重放在有限的六种
`recapture × budget` 合法组合中恢复唯一匹配命令，同时核对 external job ID；不匹配时拒绝，不猜默认值。
历史默认 3 的 hash/身份保持兼容，配置后来改变不会扩大或缩小原 Dispatch 的预算。

中央网络投递次数与手机 capture 次数保持分离。有限执行重试同时受原累计次数和冻结预算限制，不因切换
配置重置额度；人员显式重采仍新建 Dispatch，并按当时配置冻结新预算，旧派发和历史次数保留。
下一轮受控实测由原手机项目协调领取窗口，通过原查询确认 Gateway 已持久 Job 的 `maxAttempts=1`、原
Dispatch/external key/hash 对应后才允许 claim。手机始终沿用生产 `192.168.0.102:3602`、管理端 `:3600`，
不切换到隔离采集网关或重新配对/轮换凭据/替换 APK。发送预算的合成 HTTP 测试不能替代 claim 前现场核验。

### 5.2 claim 后注册 attempt

`captureBatchId` 由网关 claim 事务生成，不能在中控派发时预造。顺序固定：

1. 网关短事务原子 claim 并提交 `running + deviceId + captureBatchId`；
2. 事务外调用中控 internal API 注册 attempt；
3. 中控校验 dispatch、job、platform、product 和当前状态，返回
   `controlIngest{protocol, attemptId, uploadUrl, credential, credentialId, expiresAt}`；
4. NAS 持久关联中控 attempt/credential ID 后，将原 Job/任务上下文和上述 `controlIngest` 独立描述一起
   返回当前领取手机；不是把凭据拼进原包，也不是把原包上传改成 NAS 转发；
5. 注册失败时，网关用 `jobId + deviceId + captureBatchId + running` CAS 回
   `retry_wait/failed` 并释放设备，claim 返回 503，手机不得开始页面操作。

此处是待外部配对的最小交接契约，不代表现有生产领取响应已经返回该描述。未支持直传描述的手机不能
被登记为直传已验收；不把旧 NAS 上传结果冒充中控直传闭环。网关为同 `jobId + captureBatchId`
续发 credential 时，只能使用注册 attempt 时保存的 `credentialId`。在 `accept_until` 内，完全相同的
续发命令必须幂等返回同一 credential ID/version/token，只把服务端校验有效期延长到
`min(accept_until, now + ttl)`。这使丢失的续发响应可重放，且网关重启后不需要持久化明文
token。不同 credential ID、device/job/batch 或超过总接收窗口仍拒绝。续发不重新 claim、不更换
batch。NAS 在受保护领取响应中交付当前凭据的实现由外部 Owner 负责，中控不新增第二个原包入口。

### 5.3 续租与迟到 fence

本任务不修改 NAS 原设备 heartbeat、claim、回收或队列规则。注册传入实际 Job lease，中控 attempt
保留 `lease_expires_at/last_heartbeat_at/accept_until` 与当前批次 fence，不替代 NAS 权威 lease。
任一迟到结果仍按原 `dispatch + device + job + batch` 绑定及当前 Item 检查；旧批次不能覆盖新批次成功
或人工编辑。若外部接口不能提供实际绑定或接收窗口，不得伪造值，应保持该处未配对。

### 5.4 双回执

手机用 `controlIngest.uploadUrl` 直接向现有
`POST /api/v1/mobile-collection/ingest/{attempt_id}` 上传原 UTF-8 完整包，
`Authorization: Bearer {controlIngest.credential}`、`Content-Type: application/json`；不包裹新 envelope，
不添加 Team，不改写 `detailBody/skuBody` 或原 SHA 字段。URL 只接受匹配部署配置的中控 origin，
不把 Bearer 跟随重定向发送给其它主机。原 `taskContext.jobId/captureBatchId/sourcePlatform/sourceProductId`
必须与注册绑定一致；`attempt_id` 在 URL 中，不用 NAS jobId 或中控 request_id 替代。

下列 202 仅指中控 Upload Receipt；没有回执、HTTP 失败或响应身份不匹配时必须保留手机原包，
只重传同一份内容，不重新采集。收到 `ok=true`、`receipt.accepted=true`、
`status=received/duplicate` 且 `attemptId/captureBatchId` 匹配、`receiptId` 有效后，才可删除本地待传原包。
这证明 Raw 已可靠接收，不表示清洗或商品入库已成功；`superseded` 或未知状态不作为删除依据。

| 返回 | 手机处理 |
|---|---|
| 202，身份匹配的 `received/duplicate` | Raw 已持久接收，可删除对应本地待传包；不宣称商品已入库 |
| 401 | 保留原包，经 NAS 服务身份检查/续发同批次短期凭据；不暴露或使用服务 Token |
| 404/409 | 保留原包并显示批次/内容冲突；不换商品、批次或重新采集绕过 |
| 413/422 | 保留原包与安全错误；不删字段、不篡改 SHA 来凑接收成功 |
| 超时、连接中断、5xx、无有效匹配回执 | 按有限上传重试重发同一包；未知结果不当作成功，也不重新抓详情/SKU |

1. 中控在短事务内验证 opaque token 与全部绑定字段，规范化 JSON、计算 content hash，可靠写入
   Upload Receipt；
2. 首个合法包原子写 Receipt 并把 credential 标记 consumed；在当前 `token_expires_at` 与
   `accept_until` 内，同 credential 只允许同 content hash 重放并返回原 receipt，不同 hash 返回 409。
   即使后台已把 Receipt/Attempt 推进到 persisted、failed 或 superseded，202 响应在网络中丢失后的同内容
   重放仍稳定返回 `duplicate + 原 receiptId`；服务端必须先校验 attempt/credential/时限，错误或过期 token
   不能借既有 Receipt 获取回执。已可靠接收后，同一幂等续发 credential 仍只能在
   `accept_until` 内上传；同内容由既有 content hash 返回 `duplicate + 原 receiptId`，异内容仍 409。
   续发不清除 consumed/hash，不改变 attempt/batch，也不允许 canceled 或无 Receipt 的非活动 attempt 复活；
3. HTTP 202 + `accepted=true/status=received/receiptId` 只代表原始包已可靠接收；
4. 后台 Inbox Processor 用 lease/heartbeat/fence 领取 receipt，事务外调用既有
   `convertCompletePackage()` 的窄适配器；
5. 清洗/入库成功时，在同一短事务提交不可变 Version、当前 Product、Persist Receipt，并将 Upload Receipt
   置为 `persisted + gateway_settlement_state=pending` 后，才把中控 Item 标为成功；
6. 清洗/入库失败或旧批次失效时，不伪造 Persist Receipt；在同一短事务将 Upload Receipt 置为
   `failed/superseded + gateway_settlement_state=pending`，保留 Raw 与脱敏失败原因；
7. 独立结算领取器以 Upload Receipt 为统一 outbox，以服务认证通知网关；成功结算再把 Upload Receipt
   标记 settled，并在同一事务镜像 Attempt.settled_at。成功回调由唯一 Persist Receipt 取得
   productVersionId/uuSha256，失败回调直接使用 Upload Receipt 的 receiptId/error；
8. NAS 仅接收当前 `jobId + deviceId + captureBatchId` 的状态元数据，不接收 Raw、UU 或商品内容；按外部
   已核实接口结算为 completed/retry_wait/failed。回调失败按有限预算
   持久重试，进程重启不会因不存在 Persist Receipt 而丢失失败结算；
9. 未收到 Upload 的取消仍走网关 cancel API；旧 batch 不修改 Product，也不把网关的新任务结算完成。

结算响应的 `jobStatus` 使用网关完整既有枚举
`pending/running/retry_wait/captured/completed/failed/canceled`。旧 batch 返回 `settlement.status=superseded`
时，同一 Job 可能已被新批次推进到 pending/running/captured；中控接受真实当前状态，但仍严格核对
`gatewayJobId + captureBatchId`，未知状态继续作为无效响应拒绝，网关不得为满足 DTO 伪报 retry_wait。

中控到网关的终态回调最少固定：`jobId/captureBatchId/deviceId/sourcePlatform/sourceProductId/attemptId/`
`receiptId/status/errorCode`；成功再带 `productVersionId/uuSha256`。网关只有同一条件 UPDATE 成功后才结算。
手机只有取得与本次匹配的中控 received/duplicate 回执才完成上传；任务完成仍需入库后对应终态，不能
用 HTTP 202 冒充 completed。

当前只读 NAS 源码快照 `e4f19b9bb3e6546947d7dcd26586892ccac62a69` 的配对缺口：

- 原 claim 响应只含 `job/settings`，未返回已取得的 `controlIngest`；其内部续发函数也不等于手机可调用的
  已上线续发入口。需外部 Owner 核对受保护透传与过期后同包续传方式，不修改手机采集/生成逻辑。
- 旧 `PATCH /api/v1/jobs/{jobId}` 的 product completed 要求 `status IN (captured, converted)` 且
  `result_capture_id IS NOT NULL`。因此“原包不落 NAS”的 Job 不能借这个旧接口伪报完成；不补造 NAS 结果。
- 中控现有状态 Adapter 的 `/api/v1/control/collection-settlements` 只发身份、回执和终态元数据，
  不发商品包；但它出自此前隔离配对契约，不能据源码中存在就认定生产 NAS 已部署支持。当前保持明确
  配对阻塞，既不回退为 NAS 转发，也不在此任务部署旧 relay 候选。

Collector、Automation、设备 ID、原 LSPosed 有效凭据和完整包生成保持；Watchdog 回退及旧待发包问题不在
本轮处理。两份原包的离线 cleaner 证据（均 19 SKU / 8 主图 / 5 详情图）及旧定向测试只作兼容依据，
不是手机直传实机证据。

### 5.5 网关失败终态的只读同步

中控复用原 `ProductCollectionExecutor.dispatch_once` 循环，不创建新队列或消费者。取消仍优先；
每轮再有界检查一个到期的当前 `dispatched/running` 派发，然后继续原计划/投递。查询接口与 NAS
Candidate `65f66d81bafcc4d827f9a1db42130b62ad691ada` 配对：

- `GET /api/v1/jobs/{gatewayJobId}/result?externalJobId={URL编码后的externalJobId}`；使用原
  `CONTROL_DISPATCH_TOKEN`，不是 NAS 管理员或手机凭据。NAS 只允许精确 Job/external ID 且
  `central_ingest_v1` 的只读查询；不返回完整 result 或 Token。
- 严格 root DTO：`ok=true/jobId/externalJobId/status/sourcePlatform/sourceProductId/captureBatchId/`
  `attempts/maxAttempts/lastError/updatedAt/finishedAt`。批次、错误和完成时间可为 null；时间须带时区，
  商品 ID 保持字符串，未知字段/状态或无效类型拒绝。状态沿用网关既有七项枚举。
- 短事务冻结 Team、gateway、Job/external ID、当前 Dispatch、当前 Attempt/批次/设备；复用
  Dispatch 的 `next_attempt_at` 与既有 scan interval 预约下一次检查，提交后才发 GET。多进程通过原
  行锁/到期谓词选择；进程中断后到期可继续，查询不消耗 delivery/capture 次数。
- 回写短事务再次复核上述身份和当前状态。只有 `failed` 且批次匹配时收敛：Dispatch 使用既有
  `execution_failed`，Item/当前 Attempt 使用 `failed`，Request 走原聚合规则。已经可靠接收上传或
  正在处理的 Attempt 不被该查询覆盖；旧批次、旧派发和已终态重复结果不改新记录。
- `pending/running/retry_wait/captured/completed/canceled`、网络/HTTP故障、未知响应或不匹配结果
  均不据此改业务状态；特别不能根据网关 completed 伪造中控已入库。没有当前 Attempt 时，只接受
  同样无批次的绑定；无法证明最后批次时不猜测。
- 固定中控码为 `PRODUCT_COLLECTION_GATEWAY_EXECUTION_FAILED`，阶段 `gateway_execution`。
  仅将已取证的两条完整包超时原文映射为固定安全提示；任意其他 lastError 使用通用失败提示，不透传
  URL、凭据或诊断建议。NAS 的 LSPosed/插件建议不作为已证实根因。现有任务详情读取原错误字段即可展示。

同步不创建 Upload Receipt/商品版本、不回写 NAS、不自动 retry/recapture。原取消、有限重试预算和人员
显式重采入口保持；达到 3/3 后普通重试仍受原限制，显式重采仍新建 Dispatch 并保留历史。

## 6. 清洗与业务字段边界

中控不重写 UU 清洗算法，使用经测试的窄 Adapter 调用现有 `convertCompletePackage()`。Adapter 负责：

- 将外部函数错误转换为稳定的中控错误阶段，不记录原始敏感内容；
- cleaner 子进程只继承启动 Node 所需的最小系统环境，不继承数据库连接、网关凭据、HMAC key 或其它
  Backend 服务配置；
- 验证 package 内 product ID 与绑定商品一致；
- 固定 `source_format_version/cleaner_version`；
- 保留 Raw Package hash、不可变 UU Snapshot 和原始 SKU/图片顺序；
- Product/SKU 源 ID 强制字符串；未知数值为 `null`；
- 商品业务价格只采用有原始证据的当前销售价，排除账号券/专享券价格。即使清洗器兼容输出 0，原始包
  没有价格证据时也必须写 `null`，不能把未知伪装为 0。

入口边界固定为：解压后的 UTF-8 JSON 最多 16 MiB、最大嵌套深度 64、单个普通字符串最多 1 MiB、
单个 URL 最多 4096 字符；超过限制返回 413/422，不写 Receipt。中控同时保留两个明确版本：

- 历史紧凑 V1：顶层只允许 `eventType=complete`、`detailBody`、`skuBody`、`capturedAt`、
  `skuCapturedAt` 和非秘密 `taskContext`；
- 现有 Douyin Collector 原始 V2：严格允许
  `schemaVersion=2/source=douyin/eventType=complete/trigger/productId/capturedAt/detailCapturedAt/`
  `skuCapturedAt/appVersion/detailSha256/skuSha256/sha256/detailBody/skuBody/taskContext`。
  `trigger` 仅为当前收集器会生成的 `cart_sku/detail_single_sku`，顶层 product/source 必须与
  taskContext 一致；三个 SHA-256 字段均严格为 64 位小写十六进制，不接受占位文本、大写或
  其他长度。V2 入口保留这些原始元数据并把 `raw_format_version` 记为 2，不在接收层删字段或
  改写为历史紧凑包。

taskContext 只允许本文稳定键，其他 HTTP headers/request/cookie 字段拒绝。`merchant_snapshot` 只保留
merchant source ID（字符串）、展示名和已净化主页路径；`category_path` 最多 8 层、每层 120 字符。

Product `source_url` 只允许 http/https、拒绝 userinfo，并删除 query 和 fragment。`primary_image_url` 展示
投影只允许 https、无 userinfo、host 在配置 allowlist 中；仅保留明确允许的非秘密 query，默认删除全部
query/fragment。若净化后不可加载，显示缺图，不为显示成功保存认证 URL。Raw 与不可变 `uu_snapshot`
保留来源媒体信息/资源签名；它们的内容 hash 与展示 URL 净化分开，资源签名绝不被当作服务或 Session 凭据。

完整包继续递归拒绝 Cookie、Authorization、headers、认证 Token、平台请求签名和 request_url 等字段，
以及含这些认证 query 的 URL。仅 Collector V2 的 `detailBody` 在以下已取证位置允许资源签名，V1 和
`skuBody` 不继承例外。兼容表同时约束实际 JSON 对象/数组路径、HTTPS、精确域名/资源路径和全部 query
名称；伪造带点字段或用对象代替数组、userinfo、非 443 端口、fragment、额外 query、未知 host/path 均不放宽。

  `finished_at nullable`；timestamps。
- `UNIQUE(attempt_id, team_id)`、`UNIQUE(gateway_id, gateway_job_id, capture_batch_id)`；
  `UNIQUE(dispatch_id, attempt_no)`；当前批次 partial unique `(dispatch_id)` 精确 WHERE
  `state IN ('registered','running','received','processing')`；salt/hash/content hash 格式 CHECK；
  consumed 与 accepted hash 成对、`accept_until >= token_expires_at >= token_issued_at`。
- 索引 `(state, lease_expires_at, attempt_id)`。

### 7.8 `product_collection_upload_receipts`

- `upload_receipt_id` PK；`team_id`；`attempt_id + team_id` 复合 RESTRICT FK，`attempt_id` unique；
  `upload_key` unique；`content_sha256`；
  `raw_payload JSONB`；`raw_format_version`；
  `state`（received/processing/failed/superseded/persisted）；
  `processing_attempts`、`processing_next_attempt_at`、`lease_id/lease_expires_at/last_heartbeat_at`；
  处理阶段脱敏 `last_error_code/stage/message`；`received_at/processed_at`；
  `gateway_settlement_state/attempts/next_attempt_at/settled_at`；独立的结算
  `settlement_error_code/message`；timestamps。
- `UNIQUE(upload_receipt_id, team_id)`；content/upload hash 格式和 JSON object CHECK；处理领取索引
  `(state, processing_next_attempt_at, received_at, upload_receipt_id)`；结算领取索引
  `(gateway_settlement_state, next_attempt_at, upload_receipt_id)`。
- `received/processing` 时 settlement 必须为空；进入 `persisted/failed/superseded` 的同一事务将 settlement
  置 `pending`；`settled_at` 当且仅当 settlement=settled；settlement=failed 必须有独立 error_code；
  `next_attempt_at` 仅可用于有限重试中的 settlement=failed；settled 时清空 next/error。

### 7.9 `product_collection_persist_receipts`

- `persist_receipt_id` PK；`team_id`；`upload_receipt_id + team_id` 复合 RESTRICT FK，
  `upload_receipt_id` unique；`product_id` 非 unique；`version_id` unique；
  `outcome`（applied/not_applied/superseded）；`applied` boolean；`persisted_at`；timestamps。
- `(product_id, team_id)` 复合 RESTRICT FK；`(version_id, product_id, team_id)` 复合 RESTRICT FK，保证
  Product/Version/Team 一致；CHECK `applied` 与 outcome 一致。该表只证明清洗与数据库提交，不再承担
  网关结算 outbox；`Upload.state=persisted -> 唯一 Persist Receipt` 由同一 Service 事务 invariant 与 PG 测试保证。

### 7.10 已有候选键与延迟引用

现有 `product_selection_candidates` 的真实 PK 为 `candidate_id`，现有唯一键是
`(team_id, platform, platform_product_id)`，没有 `(candidate_id, team_id)`。批准的新 Migration 需只追加
`UNIQUE(candidate_id, team_id)`，再由 Item 使用复合 FK；它不改候选事实。Service 在创建 Request 时仍用
现有可见性 SQL 以 404 复核，Item 冻结 candidate_id/team/platform/product，候选后续屏蔽或来源变化不影响审计。

Item 的 `current_dispatch_id` 可空仅限尚未派发/PDD 人工边界；一旦创建 Dispatch，终态也保留指针用于审计，
不清空。Dispatch 提供 `UNIQUE(dispatch_id,item_id,team_id)`；Migration 后置创建
`fk_collection_item_current_dispatch`：
`(current_dispatch_id,item_id,team_id) -> dispatch(dispatch_id,item_id,team_id)`，避免跨 Item/Team 指针。

### 7.11 状态集合与关键 CHECK

| 表 | 允许状态 | 关键数据库规则 |
|---|---|---|
| Request | `pending/running/partial/succeeded/failed/canceled` | 终态=`partial/succeeded/failed/canceled`，`finished_at` 当且仅当终态非空；cancel actor/time 成对；item_count > 0；status 随 Item 转换同事务更新，计数查询聚合 |
| Item | `pending_dispatch/dispatching/dispatched/running/received/processing/succeeded/failed/canceled` | 终态=`succeeded/failed/canceled`；succeeded 必须有 library_product_id；finished_at 当且仅当终态；current dispatch 创建后永久保留；PDD 不得 auto_gateway |
| Dispatch | `pending_delivery/delivering/dispatched/running/completed/delivery_failed/execution_failed/canceled` | 终态=`completed/delivery_failed/execution_failed/canceled`；delivering 才可持 delivery lease；gateway_job_id 在 dispatched/running/completed/execution_failed 必填；finished_at 当且仅当终态 |
| Attempt | `registered/running/received/processing/persisted/failed/superseded/canceled` | 终态=`persisted/failed/superseded/canceled`；credential 时间有序；received/processing/persisted 必须 consumed；finished_at 当且仅当终态；同 dispatch 仅一个 active batch |
| Upload Receipt | `received/processing/persisted/failed/superseded`；settlement `pending/delivering/settled/failed` 或未进入终态前 NULL | 终态=`persisted/failed/superseded`；received_at 必填；processed_at 当且仅当终态必填；processing 才有处理 lease；终态同事务建立 settlement=pending；settled_at 当且仅当 settled；settlement=failed 必须有独立脱敏 error_code，next_attempt_at 仅在有限结算重试时非空，settled 时 next/error 为空；persisted→Persist Receipt 是同事务 Service invariant 与 PG 测试，不伪装成单表 CHECK |
| Persist Receipt | outcome `applied/not_applied/superseded` | applied 等价 outcome=applied；persisted_at 永远非空；只证明清洗和数据库提交，不承担网关结算状态 |

跨表终态映射在同一 Domain Service 事务内执行；数据库 CHECK 负责单行非法组合，FK/unique/fence 负责跨行身份，
不得仅靠前端状态。

## 8. 事务、幂等与迟到保护

- 创建 Request/Items、领取派发、接收 Raw、提交 Version/Product/Persist Receipt 与 Upload 终态/outbox、
  回写网关结算结果分别是短事务；
  网关 HTTP 和清洗均在事务外。
- Product upsert 以 `(team_id, platform, source_product_id)`；同一个 Receipt 只能产生一个 Version。
- Item 创建时冻结已有 Product 的 `manual_revision`。自动采纳要求：当前 capture attempt 未被替换、
  Product `manual_revision` 仍等于冻结值，且 `captured_at` 不早于当前 adopted version。否则保留 Version，
  Persist Receipt 为 `not_applied/superseded`，不覆盖人工编辑或更新成功。
- Request 计数只从授权范围内 Item 聚合；不存在“收到包即成功”。
- 进程重启只恢复到期 lease；同一 receipt/dispatch 由数据库 partial unique 和 fence 防重复领取。
  到期的最后一次派发 lease 不再重试，而是提交明确的 interrupted 终态；处理中 lease 仍由新执行者
  领取并生成新 fence，旧执行者不能迟到回写。
- 取消、失败或旧批次不删除历史；网络/网关有限 retry 复用原 Dispatch/Job 并累加次数；人员
  recapture 才新建 Dispatch，旧记录全部保留。

### 8.1 后台消费者与部署配置

中控只复用 PostgreSQL durable state，不新增 Redis、Celery 或第二套手机队列。Backend 中存在三个相互
独立的有限循环：派发/取消、完整包处理、终态结算。任一阶段短暂失败不会阻塞另两个阶段；数据库 claim、
lease 和 fence 仍支持多进程安全恢复。所有开关默认关闭：

- `BACKEND_PRODUCT_COLLECTION_EXECUTION_ENABLED`：计划并派发 Douyin 自动 Item，处理取消；
- `BACKEND_PRODUCT_COLLECTION_PROCESSING_ENABLED`：领取已可靠接收的 Raw，调用既有 cleaner 并入库；
- `BACKEND_PRODUCT_COLLECTION_SETTLEMENT_ENABLED`：把成功或失败终态可靠结算回既有网关。
- `BACKEND_PRODUCT_COLLECTION_CAPTURE_MAX_ATTEMPTS`：只在新 Dispatch 冻结手机 capture 预算，默认 3；
  隔离单次实测为 1。它不修改中央 delivery/settlement 重试配置，也不重写已有 Dispatch/Gateway Job。

启用派发需持久化配置 Gateway ID、Gateway Origin 和独立 control token；启用结算需独立 callback token；
启用处理需配置经审核的 `convertCompletePackage()` `.mjs` 路径。网关到中控另使用 service token；手机
批次 credential 由 ingest HMAC key 派生；中控 upload URL 只从 public origin 生成。任一已启用阶段缺少
所需配置时 Backend 启动 fail-closed，不会静默跳过或退回 Mock。密钥只进入受保护部署配置，不进 Git、
业务表、日志或交接报告。

发布顺序固定为：应用 0049 并核验 Head → 部署但保持三开关关闭 → 完成网关/手机成对契约与隔离闭环 →
再按 Release Gate 写入持久化配置并重启。仅改临时容器环境不算启用；回滚先关闭入口和三个阶段并保留
Schema/Raw/Version/Receipt，再回退应用镜像。

## 9. 为什么不能复用 0047/0048

`shop_product_data_products/series/generations/metric_snapshots` 及
`shop_product_data_collection_batches` 的权威键是 Shop 和滚动指标范围，服务的是店铺经营商品指标：

- `shop_product_data_products` 唯一键为 `(shop_id, platform, platform_product_id)`，不是 Team 共享商品库；
- generation/batch 表表达指标采集的店铺并发、序列和 current/previous 快照，不表达手机 Device/Job/Batch；
- metric snapshot 不保留完整商品包、SKU/图片版本或采纳/人工编辑 fence；
- 0048 的队列不能被改造成手机网关的第二 claim 队列。

因此 V1 不修改 0047/0048 表、事实或迁移字节。Product Selection Candidate 也仅是候选身份与观察来源，
不是正式商品库；只以 RESTRICT 引用其主键并在 Service 内执行可见性复核。
