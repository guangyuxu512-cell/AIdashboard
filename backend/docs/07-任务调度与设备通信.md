# 任务调度与设备通信

## 3B-Lite 固定边界

3B-Lite 当时只建立 `Device`、`device_runtime`、`worker_device_credentials` 和单表
`Task`。Scheduler V1 后新增的 Schedule / ScheduleRun 只负责按时间创建同一个普通 Task，仍不引入 TaskRun、Redis、重试或自动故障转移。

网络方向固定为 Worker 主动访问 Backend。Backend 不连接 Worker 本机端口，
Worker 不需要公网 IP，也不得持有数据库连接信息、店铺密码或 Session Payload。

## Worker 身份与在线状态

- 每个 Device 独立签发 Worker Token，数据库只保存 SHA-256 `token_hash`。
- Token 明文只在中控台签发/轮换响应（CLI 仅为高级运维兼容入口）输出一次，任何 GET 都不能恢复。
- Worker API 使用 Bearer Token 与 `X-Device-ID` 共同认证。
- 首次 GUI 配置的 `GET /api/v1/worker/provisioning` 是唯一例外：它只接收 Bearer Token，
  Backend 从 Token Hash 解析该 Token 自己的 Device 身份，避免用户手填 UUID；它不接受
  Body/Header 中的目标 Device ID。
- Worker 每 15 秒发送 Heartbeat；Backend 只更新独立的 `device_runtime`。
- `last_seen_at` 距当前时间不超过 45 秒为 ONLINE，否则为 OFFLINE。
- Device 的 `enabled` 与 Worker 的 ONLINE/OFFLINE 是两个独立状态。

上述 45 秒阈值通过 Backend Config 配置，不写入设备主表。

## Task Contract

普通创建接口为 `POST /api/v1/tasks`，调用方必须明确传入
`target_device_id`、白名单 `skill_id` 与符合 Skill 契约的 `input`。

当前 Worker Skill 白名单为 `system.echo`、`system.sleep`、`yingdao.test`、
`yingdao.discover`、`yingdao.app.run`。`yingdao.discover` 是 Provider Inventory 发现能力；
`yingdao.app.run` 是通过 app_id + params 执行当前账号可访问影刀应用的稳定通用 Skill，不为
每个应用创建动态 Skill。新增 Skill 只扩展 Skill Check Constraint，不改变 Task 状态机、Claim 或
Lease。

管理端即时 Task 创建资格按固定顺序判断：Device 存在且未删除、Device 已启用、Worker 当前 ONLINE、
目标 Device 已声明该 `skill_id`、Skill 所依赖的 Provider 已就绪，然后才进入 Application 和参数契约校验。
错误码分别使用 `TASK_DEVICE_DISABLED / TASK_WORKER_OFFLINE / TASK_SKILL_NOT_AVAILABLE /
TASK_PROVIDER_NOT_READY / TASK_PROVIDER_LOGIN_REQUIRED /
TASK_PROVIDER_VERSION_UNSUPPORTED / TASK_APPLICATION_NOT_AVAILABLE`，Frontend 不通过文案猜测。
`discovery` Runtime 用于恢复 Provider 状态，不要求 Provider 预先 READY。

Schedule 到点触发仍复用同一 Task Guard，仅按正式业务语义豁免“Worker 当前 ONLINE”：启用且未删除的离线 Device 可以先产生 PENDING Task，等待 Worker 后续上线 Claim；Device 停用/删除、Skill 缺失、Provider 未就绪、Application 消失或参数失效仍会阻止 Task 创建，并由 ScheduleRun 记录安全阻塞摘要。

Task 只使用以下五种状态：

- `PENDING`：等待目标设备领取。
- `RUNNING`：目标 Worker 已领取并持有 Lease。
- `SUCCESS`：Worker 明确回传成功结果。
- `FAILED`：Worker 明确回传执行失败。
- `LOST`：执行中 Lease 超时，结果未知。

## Task Center 查询边界

Task Center 是现有 Task 的只读执行总控与审计入口，不是 Scheduler，也不创建新的 Task
状态。管理列表支持分页、status/device/search/created range，并按最新 Task 优先稳定排序；
日期范围只基于 `Task.created_at` 且使用 `[from, to)`；Worker Claim
继续保持 `created_at ASC, task_id ASC`，两种排序职责不得混用。

列表摘要在分页 Task 集合内一次关联 Device 与最新 progress/status/log Event，不返回完整
日志且不得形成逐行查询。结构化 progress 只读取 Runtime Event metadata 的 `current/total`；
没有该 metadata 的影刀 tasklog 显示无进度，不解析 message 猜值。当前消息优先级为最新
progress message、最新 status message、最新安全 log message；FAILED/LOST 使用安全错误摘要。

日志统一依附 Task：影刀 `tasklog → TaskLogFollower → RuntimeEventBus` 与 Python Business
Skill `ctx.log()/ctx.progress() → RuntimeEventBus` 都写入 `task_events`。Frontend 列表只取
摘要，详情使用“有限历史窗口 + `before_seq` 加载更早 + `after_seq` 实时追加”；不建立独立
RPA/Python 日志中心。

## Runtime Event 生命周期

Task 长期保留，Runtime Event 默认保留 90 天。年龄从 Task 的 `finished_at` 计算，Terminal
集合统一来自 Task Domain 的 SUCCESS/FAILED/LOST；PENDING/RUNNING 不清理。Backend
lifespan 启动轻量 Maintenance，每日按 Terminal Task 小批次、短事务清理，并支持同一规则的
人工立即 Sweep。并发实例通过 Task 行 `FOR UPDATE SKIP LOCKED` 分批，删除和 Marker 更新均
幂等；Retention 不与 Scheduler 共用业务锁或事务，也不引入 Redis Lock、VACUUM FULL 或 Event 逐条删除入口。

## Scheduler V1 关系

```text
Schedule → ScheduleService → TaskService → PENDING Task → Worker Claim
```

Scheduler 不连接 Worker 或 ShadowBot，不直接写 TaskRepository。详细的 DAILY、Timezone、COALESCE ONE、ScheduleRun 幂等和后台生命周期见 `11-定时计划与后台调度规范.md`。

Worker API 独立位于 `/api/v1/worker`，提供 heartbeat、claim、renew、complete、
fail 和认证后的 provider-inventory、skill-capabilities 上报。Worker 每 3 秒普通轮询；没有任务时返回
204，不使用 Long Poll。

Provider Inventory 以 `(device_id, provider_code)` 唯一，只保存最近一次 Worker 上报快照。
设备身份只来自 Bearer Worker Token 与 `X-Device-ID` 的认证 Principal，不信任请求
Body。Worker 启动与周期检测都会上报 Inventory；未安装、版本不支持、需登录和接口不可达
作为 Provider 状态保存，而不是令 Worker 离线。手工 Discovery Task 仍在 complete 前上报。

Skill Capability 以 `(device_id, skill_id)` 唯一保存 Worker Registry 最近一次完整快照。
`PUT /api/v1/worker/skill-capabilities` 采用 snapshot replace，不接受 Body `device_id`，Worker
只能同步认证 Principal 自己的能力。OFFLINE 不删除快照；重连后重新同步。Skill Capability
同时持久化 `internal | business` 分类，但 Task Guard 始终按 `(device_id, skill_id)` 查询完整
能力，不按 UI 可见性过滤；`internal` 的 `system.echo` 与 `yingdao.app.run` 仍可正常调度。
不存 Application 列表，Provider Application 仍属于 Provider Inventory。

Worker Runtime Event Batch 复用同一设备认证和现有 Task/Lease 归属。认证设备不能给
其他设备的 Task 写事件；运行中按有效 Lease 写入，终态允许原目标设备重试尚未送达的
尾部批次。`(task_id, seq)` 唯一保证幂等，事件不新增 Task 状态。Frontend 通过 after_seq
增量读取；设备当前执行摘要只投影现有 PENDING/RUNNING Task。Task 创建时保存稳定
`execution_display_name`：普通 Skill 取 Capability 展示名，影刀通用 Skill 取当前
Application 名；Active Summary 直接返回该快照，历史不受 Application 后续改名影响。

## Claim、Lease 与 LOST

Claim 通过 PostgreSQL `FOR UPDATE SKIP LOCKED` 候选行与条件 `UPDATE ...
RETURNING` 原子完成，只允许 `PENDING → RUNNING`，并严格限定目标设备。

领取时 Lease 为 60 秒，Worker 执行期间每 20 秒续租。Backend 每 10 秒执行
轻量 Reconcile，将过期的 `RUNNING` 更新为 `LOST`。`LOST` 不自动重排、重试，
也不会转交另一台电脑，由中控台人工决定后续动作。

时间间隔都通过正式配置管理。未来确有多次 Attempt、取消、进度、幂等或调度
需求时，再通过契约和 Migration 引入 TaskRun 等能力。

## 设备执行资格与在线转换

- Heartbeat 认证允许 `enabled=false, deleted_at=null` 的设备，Runtime 继续表达真实 ONLINE/OFFLINE。
- Task Claim 在锁定设备后检查 `enabled=true AND deleted_at IS NULL`；不满足时不领取任务。
- Offline reconcile 只把持久 `ONLINE` 且超过阈值的 Runtime 转为 `OFFLINE`，同一次状态转换最多尝试一次通知。
- Heartbeat 只在持久 `OFFLINE → ONLINE` 时尝试恢复通知；持续在线不通知。
- 停用或软移除不修改 Runtime 状态，也不产生异常掉线通知。
