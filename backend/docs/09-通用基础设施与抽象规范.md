# 09-通用基础设施与抽象规范

## 1. 目的

本规范解决：

- 新模块各写一套 HTTP Client。
- 新平台各写一套请求方式。
- 每个 Service 各自处理 Retry / Error / Logging。
- Repository 风格不一致。
- 第三方 SDK 能解决却重复手写。
- 为单一需求不断增加重复工具函数。

核心原则：

> 业务模块负责业务语义，通用基础设施只实现一次。

---

## 2. 通用能力分类

建议统一基础设施：

```text
app/
├── core/
│   ├── config/
│   ├── database/
│   ├── security/
│   ├── logging/
│   ├── errors/
│   └── observability/
│
└── shared/
    ├── http/
    ├── pagination/
    ├── storage/
    ├── encryption/
    ├── id/
    └── time/
```

具体结构以项目实际代码为准。

禁止 shared 变成没有边界的杂物箱。

---

## 3. HTTP Client

所有服务器侧外部 HTTP 请求统一通过正式 Client / Connector。

使用：
- HTTPX

统一考虑：

- timeout
- connection pool
- proxy（如果项目需要）
- retry（明确允许的请求）
- request_id
- error mapping
- logging
- sensitive header masking

禁止每个模块直接：

```python
httpx.get(...)
requests.get(...)
```

散落全项目。

---

## 4. Platform Connector

平台差异必须收敛在 Connector / Adapter 层。

建议：

```text
platforms/
├── base.py
├── douyin/
├── pdd/
└── taobao/
```

上层 Service 调用稳定接口：

```text
fetch_orders
fetch_products
fetch_metrics
```

而不是：

```python
if platform == "douyin":
    ...
elif platform == "pdd":
    ...
```

在几十个业务 Service 中重复出现。

阶段 3C-2 的首个真实实现位于 `app/platforms/douyin/`，只提供抖店罗盘店铺身份读取。
其已验证请求为 `GET /compass_api/shop/mall/common/shop_info_v2`；URL、Accept Header、
Cookie 用法和响应 `data.shop_id/shop_name` 均来自当前 Electron 登录适配器与真实 HuanYu
响应证据。该身份请求不需要签名，继续由抖店请求层按未签名 Endpoint 发出。上层只暴露
`GET /api/v1/shops/{shop_id}/platform-identity`，禁止通用 Raw HTTP Proxy。

抖店请求层中的 Endpoint Contract 明确标记 `sign_required`：只有已验证的签名 Endpoint 才会调用
`DouyinSignerClient` 并注入新的 `a_bogus`。当前已验证的 `GET /product/tproduct/list` 仅用于验证
Cookie → Signer → 抖店请求链路，不因此新增商品业务 API、同步或数据模型。

### 抖店罗盘经营数据执行底座 V1

`GET /compass_api/shop/common/homepage/core_index_v3` 的最小只读链路位于
`app/platforms/douyin/operating_data.py`：

```text
ShopSessionAccessor
    → ShopSessionHealthService（按需身份校验）
    → DouyinOperatingDataConnector
    → DouyinApiClient（未含 a_bogus 的 URL）
    → DouyinSignerClient
    → 注入新的 a_bogus
    → Compass core_index_v3
```

- 查询日期按调用方已经确定的 Asia/Shanghai 日期传入，`begin_date/end_date` 均为该日 `00:00:00`；
  对这类显式单日边界，`date_type=999` 和已验证的 `index_selected` 属于该 Endpoint Contract。此前
  `date_type=20` 的抓包重放证据不能替代当前服务端 Session 的验证：在同一 HuanYu Session、同日、
  其他正式参数不变且重新签名的只读对照中，改为 `999` 后返回 `st=0`。这只证明已验证日期的显式
  单日模式，不将其扩展为浏览器动态字段或任意日期范围的充分证据。
- `a_bogus` 绝不能出现在签名前 URL 中。`_lid` 仅是临时调用上下文：已有抓包证明其不是永久常量，
  但尚未证明服务器生成规则，因此 V1 仅允许显式、一次性传入，不持久化、不猜测生成。`verifyFp`、`fp`
  与 `msToken` 同样没有已验证的服务器生成/持久化来源，默认不发送空占位符；不能把抓包上下文的字段名
  当成可复用的常量。
- 响应只从固定路径
  `data.module_data.homepage_core_index.compass_general_multi_index_card_value.data[0]`
  读取当前 `index_value.value.value`。当前日事实持久化 `income_amt`（整数分）、`pay_cnt`（订单数）及已确认的
  `refund_order_cnt`（退款时间订单数，单位单）；金额以 `Decimal / 100` 展示，`null` 保持缺失，不读取 `last_value`、不补零。
  成功响应可以省略其它已请求的卡片指标；可选退款字段的缺失、`null` 或结构异常绝不能使已验证的成交金额/订单观察
  被标记为整日解析失败。反之，两个已确认核心字段任一缺失、`null` 或结构异常时仍是明确的
  `response_parse` 失败，不能伪造成完整覆盖。
- `refund_order_cnt` 已冻结为页面“退款订单数（退款时间）”。它是可选于核心成交事实的独立观测：真实 0 可持久化，
  缺失、未就绪或异常结构分别记录状态且不自动无限重试；状态不完整时不会把旧值伪装成当前完整退款覆盖。
  `refund_order_cnt_pay_time`（支付时间口径）在本期保持未解析，不能替代退款时间口径或参与退款率推断。
  商家体验分仍须先有独立 Endpoint/字段/时间语义证据，继续保持 `null`。
- `DouyinOperatingDataBatchExecutor` 仍是有限、无状态的并发执行器；Operating Dashboard Data V1 在其外层
  增加 `OperatingDataCollectionJob / OperatingDataCollectionItem` 持久化计划与
  `OperatingDataCollectionExecutor`。后者短事务 claim → 既有 Batch Executor 的有限并发外部 I/O → 短事务
  finalize，绝不把数据库事务、行锁、Cookie 或签名跨越平台请求。
- `BACKEND_DOUYIN_COMPASS_COLLECTION_CONCURRENCY` 默认 5，是**全局** running Shop 上限，而不只是单一
  Backend 进程的批次大小。PostgreSQL 在每次短 claim 事务内取得事务级 advisory lock、回收过期 lease 后
  计数 running item，再决定是否 claim；锁在 commit 前释放，绝不跨越 Session、Signer 或平台 I/O。部分唯一索引
  同时保证跨 Backend 进程同店同日只有一个 active item、同店只有一个 running item。完成一家立即补位；同店
  下一日期只会在前一日期完成后 claim。进程崩溃留下的租约到期后才恢复 pending，不能把进程内 Lock 当作
  跨进程互斥。
- 失败结果持久化 Shop、统计日期、阶段、安全错误码、有限 retry 与分段耗时。核心指标解析失败额外只保存本地
  推导出的安全提示（例如缺少“成交订单数”），不得保存原始响应、Cookie、签名或 URL。Session 过期只暂停该
  Shop 的未派发日期，其他 Shop 继续；Electron 重新授权经现有身份健康校验成功后才恢复原 item。风险响应、
  签名失败、网络失败和响应解析失败各自分类，不能一律触发登录。
- 手动和 retry item 在 claim 后、平台 I/O 前重解析发起人的当前 Team、模块和 Shop 权限；撤权、调组或停用
  发起人时安全跳过，不将排队时的前端范围视为持续授权。系统初始补采和每日计划没有人类发起者，不混用该规则。
- FastAPI 生命周期只有在 `BACKEND_OPERATING_DASHBOARD_COLLECTION_EXECUTION_ENABLED=true` 时才启动执行循环。
  每日计划与启动补漏还要求额外 `BACKEND_OPERATING_DASHBOARD_DAILY_COLLECTION_ENABLED=true`，并以显式配置的
  `BACKEND_OPERATING_DASHBOARD_DAILY_COLLECTION_LOCAL_TIME` 的 Asia/Shanghai 墙钟时间创建日计划；默认值为
  `09:00`，但两个开关默认均为 false，因此该默认时刻不会让 Feature/Integration 自动访问平台。每日计划、
  新店/重新启用、重新授权和启动恢复共用最近 30 个完整自然日的数据库缺口判断：真实 0 完整、未接入退货/评分
  字段不造成缺口，已有 active/paused item 复用；retryable 自动失败还受冷却和跨计划累计上限约束。启动恢复在
  每日墙钟前只做 lease/停用状态整理，不占用当天 `daily:` 键；到时后才可计划缺口。对旧启动时序造成的、原
  `daily:` Job 与同日 item 都在时刻前发生且恰为一次 `DOUYIN_OPERATING_DATA_REJECTED / platform_response`
  终态的项目，服务层可用独立 `daily-recovery:` 稳定键建立最多一次的窄恢复；这不是把全部非成功平台状态解释
  为“未就绪”。所有路径绝不把外部 I/O 放到 lifespan 事务中。
  Feature/Integration 默认均关闭；生产启用属于独立 Release Gate，不能因部署 API 自动启用真实平台调用。
- Signer 的 `DOUYIN_SIGNER_WARM_POOL_SIZE`（默认 2）与采集并发独立。池预启动**单次使用**的
  `sign_once.js` 进程，签名完成立即退出并补位。不得复用一个签名 JS 全局环境：实测连续调用会产生
  状态污染/缺失签名风险。超时子进程会被终止和替换；错误响应只返回安全错误码，不能泄露 Cookie、签名
  或第三方堆栈。

---

## 5. Repository

Repository 负责数据访问，不承担复杂业务判断。

禁止：

- 同一个查询在多个 Service 复制 SQLAlchemy 条件。
- API 层直接执行大量 SQLAlchemy Query。
- Repository 返回无明确边界的任意字典。

重复查询必须形成语义化 Repository 方法。

---

## 6. Service

Service 负责：

- 业务规则。
- 权限之后的业务动作。
- Repository 协调。
- 外部 Connector 协调。

禁止：

- Service 自己重新实现加密。
- Service 自己重新实现 HTTP Retry。
- Service 自己重新实现日志体系。
- 一个 Service 变成所有平台的超级类。

---

## 7. Schema / Contract

Pydantic Schema 是跨系统 API 契约的重要来源。

禁止：

- 直接复用 SQLAlchemy Model 当 API Contract。
- 不同模块定义同义但不同结构的分页结果。
- 不同模块重复定义相同状态枚举。

通用 Contract 应集中定义并复用。

---

## 8. Error

建立统一错误基类和错误响应。

业务模块定义业务错误码，但遵守统一结构：

```text
code
message
request_id
details（可选）
```

禁止：

- 到处 `raise Exception("失败")`
- 同一错误多个不同 error_code
- 把底层数据库异常原样返回前端

---

## 9. Config

所有配置进入统一配置层。

禁止散落：

```python
BASE_URL = "..."
TIMEOUT = 30
PATH = "D:/..."
```

环境差异通过配置管理。

秘密信息不得进入代码仓库。

---

## 10. Encryption / Credential

加密、解密、掩码、Credential 访问必须使用统一安全组件。

禁止每个模块各写：

```text
encrypt_password
decrypt_cookie
mask_token
```

---

## 11. Storage

文件、截图、账单、报表等通过统一 Storage Adapter。

后续允许：

```text
LocalStorage
MinIOStorage
S3Storage
```

业务模块不直接依赖具体 MinIO API。

---

## 12. Time / ID

时间和 ID 生成统一。

禁止：
- 各模块自定义 ID 拼接规则。
- 依赖名称作为唯一标识。
- 各模块使用不同 timezone 处理方式。

---

## 13. Retry

Retry 只能用于明确可安全重试的操作。

统一重试策略，禁止每个模块各自写 while loop。

涉及副作用操作时必须先判断：
- 是否幂等。
- 是否有 idempotency_key。
- 重试是否可能重复执行。

---

## 14. 第三方库优先

新增基础能力前必须先检查：

1. Python 标准库。
2. 当前项目依赖。
3. 既有公共抽象。
4. 成熟第三方库。

已有成熟库稳定解决的问题禁止自行造轮子。

同时禁止同类库重复：

```text
HTTPX + requests + aiohttp 同时无规则混用
```

---

## 15. 新增公共基础设施条件

只有满足以下条件才进入 shared/core：

- 跨 2 个以上业务模块复用。
- 没有具体业务语义。
- 生命周期稳定。
- 有明确接口边界。

单一业务模块专用能力应留在该 module。

---

## 16. 禁止“万能工具类”

禁止建立：

```text
utils.py
common.py
helpers.py
misc.py
```

不断堆入无关函数。

必须按语义拆分：

```text
time/
id/
pagination/
storage/
http/
security/
```

---

## 17. 新模块开发前检查

新增 Backend Module 前检查：

- 现有 Connector 是否可复用。
- 现有 Repository 基础能力是否可复用。
- 现有 Schema/Enum 是否可复用。
- 现有 Error 是否已经存在。
- 现有 Config 是否已有配置。
- 现有第三方库是否可解决。
- 是否真的需要新增 shared 能力。

避免因新模块产生第二套基础设施。

## Notification 抽象

通用链路为 `Domain/Runtime Service → NotificationService → WebhookNotificationAdapter`。NotificationService 负责通道启用与事件开关，Adapter 负责 Provider payload。任何业务模块不得直接 import 飞书或企业微信 Client，也不得把 Webhook 塞入领域实体。
