# 09-通用基础设施与抽象规范

## 1. 目的

本规范解决：

- 新模块各写一套 HTTP Client。
- 新平台各写一套请求方式。
- 每个 Service 各自处理 Retry / Error / Logging。
- Repository 风格不一致。
- 第三方 SDK 能解决却重复手写。
- 为单一需求不断增加重复工具函数。

核心原则：

> 业务模块负责业务语义，通用基础设施只实现一次。

---

## 2. 通用能力分类

建议统一基础设施：

```text
app/
├── core/
│   ├── config/
│   ├── database/
│   ├── security/
│   ├── logging/
│   ├── errors/
│   └── observability/
│
└── shared/
    ├── http/
    ├── pagination/
    ├── storage/
    ├── encryption/
    ├── id/
    └── time/
```

具体结构以项目实际代码为准。

禁止 shared 变成没有边界的杂物箱。

---

## 3. HTTP Client

所有服务器侧外部 HTTP 请求统一通过正式 Client / Connector。

使用：
- HTTPX

统一考虑：

- timeout
- connection pool
- proxy（如果项目需要）
- retry（明确允许的请求）
- request_id
- error mapping
- logging
- sensitive header masking

禁止每个模块直接：

```python
httpx.get(...)
requests.get(...)
```

散落全项目。

---

## 4. Platform Connector

平台差异必须收敛在 Connector / Adapter 层。

建议：

```text
platforms/
├── base.py
├── douyin/
├── pdd/
└── taobao/
```

上层 Service 调用稳定接口：

```text
fetch_orders
fetch_products
fetch_metrics
```

而不是：

```python
if platform == "douyin":
    ...
elif platform == "pdd":
    ...
```

在几十个业务 Service 中重复出现。

阶段 3C-2 的首个真实实现位于 `app/platforms/douyin/`，只提供抖店罗盘店铺身份读取。
其已验证请求为 `GET /compass_api/shop/mall/common/shop_info_v2`；URL、Accept Header、
Cookie 用法和响应 `data.shop_id/shop_name` 均来自当前 Electron 登录适配器与真实 HuanYu
响应证据。该请求不需要签名，因此不得提前增加 Signer。上层只暴露
`GET /api/v1/shops/{shop_id}/platform-identity`，禁止通用 Raw HTTP Proxy。

---

## 5. Repository

Repository 负责数据访问，不承担复杂业务判断。

禁止：

- 同一个查询在多个 Service 复制 SQLAlchemy 条件。
- API 层直接执行大量 SQLAlchemy Query。
- Repository 返回无明确边界的任意字典。

重复查询必须形成语义化 Repository 方法。

---

## 6. Service

Service 负责：

- 业务规则。
- 权限之后的业务动作。
- Repository 协调。
- 外部 Connector 协调。

禁止：

- Service 自己重新实现加密。
- Service 自己重新实现 HTTP Retry。
- Service 自己重新实现日志体系。
- 一个 Service 变成所有平台的超级类。

---

## 7. Schema / Contract

Pydantic Schema 是跨系统 API 契约的重要来源。

禁止：

- 直接复用 SQLAlchemy Model 当 API Contract。
- 不同模块定义同义但不同结构的分页结果。
- 不同模块重复定义相同状态枚举。

通用 Contract 应集中定义并复用。

---

## 8. Error

建立统一错误基类和错误响应。

业务模块定义业务错误码，但遵守统一结构：

```text
code
message
request_id
details（可选）
```

禁止：

- 到处 `raise Exception("失败")`
- 同一错误多个不同 error_code
- 把底层数据库异常原样返回前端

---

## 9. Config

所有配置进入统一配置层。

禁止散落：

```python
BASE_URL = "..."
TIMEOUT = 30
PATH = "D:/..."
```

环境差异通过配置管理。

秘密信息不得进入代码仓库。

---

## 10. Encryption / Credential

加密、解密、掩码、Credential 访问必须使用统一安全组件。

禁止每个模块各写：

```text
encrypt_password
decrypt_cookie
mask_token
```

---

## 11. Storage

文件、截图、账单、报表等通过统一 Storage Adapter。

后续允许：

```text
LocalStorage
MinIOStorage
S3Storage
```

业务模块不直接依赖具体 MinIO API。

---

## 12. Time / ID

时间和 ID 生成统一。

禁止：
- 各模块自定义 ID 拼接规则。
- 依赖名称作为唯一标识。
- 各模块使用不同 timezone 处理方式。

---

## 13. Retry

Retry 只能用于明确可安全重试的操作。

统一重试策略，禁止每个模块各自写 while loop。

涉及副作用操作时必须先判断：
- 是否幂等。
- 是否有 idempotency_key。
- 重试是否可能重复执行。

---

## 14. 第三方库优先

新增基础能力前必须先检查：

1. Python 标准库。
2. 当前项目依赖。
3. 既有公共抽象。
4. 成熟第三方库。

已有成熟库稳定解决的问题禁止自行造轮子。

同时禁止同类库重复：

```text
HTTPX + requests + aiohttp 同时无规则混用
```

---

## 15. 新增公共基础设施条件

只有满足以下条件才进入 shared/core：

- 跨 2 个以上业务模块复用。
- 没有具体业务语义。
- 生命周期稳定。
- 有明确接口边界。

单一业务模块专用能力应留在该 module。

---

## 16. 禁止“万能工具类”

禁止建立：

```text
utils.py
common.py
helpers.py
misc.py
```

不断堆入无关函数。

必须按语义拆分：

```text
time/
id/
pagination/
storage/
http/
security/
```

---

## 17. 新模块开发前检查

新增 Backend Module 前检查：

- 现有 Connector 是否可复用。
- 现有 Repository 基础能力是否可复用。
- 现有 Schema/Enum 是否可复用。
- 现有 Error 是否已经存在。
- 现有 Config 是否已有配置。
- 现有第三方库是否可解决。
- 是否真的需要新增 shared 能力。

避免因新模块产生第二套基础设施。

## Notification 抽象

通用链路为 `Domain/Runtime Service → NotificationService → WebhookNotificationAdapter`。NotificationService 负责通道启用与事件开关，Adapter 负责 Provider payload。任何业务模块不得直接 import 飞书或企业微信 Client，也不得把 Webhook 塞入领域实体。
