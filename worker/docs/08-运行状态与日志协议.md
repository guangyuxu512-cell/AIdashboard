# 运行状态与日志协议

## 边界

Backend Task 仍只有 `PENDING / RUNNING / SUCCESS / FAILED / LOST`。Provider 内部可使用
`queued / launching / running / succeeded / failed / timeout`，但不得扩展顶级 Task 状态。
`task_id`、影刀 `app_uuid`、每次运行的 `yingdao_task_uuid` 是三个不同 ID。

统一链路：

```text
Executor / Provider / TaskLogFollower
→ RuntimeEventBus
→ EventBuffer
├→ BackendEventReporter
└→ LocalRuntimeState → runtime-status.json → Tkinter Status UI
```

Skill 不连接中控台；Backend Reporter 是唯一事件 HTTP 调用方。本地 UI 消费非敏感快照并通过
正式 Config Service 写入本机必要配置，未打开或关闭都不影响 Worker Core。

## Runtime Event

事件字段为 `task_id / seq / event_type / level / message / event_at / metadata`；类型只包含
`status / log / progress / completed / failed`。每 Task 的 seq 从 1 递增，metadata 只放
Provider、App UUID/名称、yingdao task UUID、phase 等必要上下文，不得含 Cookie、Token、
Credential、Authorization 或完整敏感 Input。

EventBuffer 默认约 400ms 或最多 30 条批量上传；终态立即 flush。Backend 暂不可达时有界
内存缓冲有限重试，不能因为日志失败终止正在执行的任务。Backend 使用 `(task_id, seq)`
唯一约束保证重试幂等；Frontend 使用 `after_seq` 增量读取，运行中约 1 秒轮询，终态停止。

## 影刀 tasklog

记录格式严格为：1 byte 原始 level、8 bytes 小端 .NET DateTime Ticks、4 bytes 小端 UTF-8
正文长度、N bytes UTF-8 message。未知 level 显示为 `L<n>`，不猜 info/warning/error。

TaskLogFollower 在 URI 提交前保存目录快照和 dispatch 时间，只关联之后的新文件；第一版
Provider 互斥保证同一时刻最多一个影刀执行。Follower 保存 read offset，只读取追加字节；
半条记录留在 Parser buffer 等待后续，异常长度显式失败，临时文件占用等待重试。原始
tasklog 永不修改。只有匹配目标 App 的真实 `robot task <appName> started` 与
`robot task <appName> exited` 都出现，且没有已验证 Failure 条件，才能判定 SUCCESS。

## 本地快照与状态窗口

`runtime-status.json` 位于 Worker 私有数据目录，使用临时文件原子替换。仅允许设备 ID/名称、
Worker 版本、连接与 Token 有效性状态、最近一次成功 Heartbeat、Skill 同步摘要、当前 Task ID、Skill
展示名、Provider、App 名、phase、最新消息、ShadowBot 安全状态/版本/账号/应用数量、开始/
更新时间和最近 50 条脱敏事件。不得保存 Worker Token、Cookie、Session、Credential、
Authorization 或完整 Task Input。

Heartbeat Loop 由 Worker Core 内的轻量 Supervisor 独立监督。同一 Core 同时最多存在一个 Loop；
网络瞬断、Timeout 与 Backend 5xx 只影响单次尝试并保持正常周期，Loop 非预期结束时记录原因并在
一个 Heartbeat 周期后只重建 Heartbeat。正常 shutdown 会取消 Supervisor，禁止退出期间复活。
`last_heartbeat_at` 的正式语义是“最近一次成功 Heartbeat”，失败不得刷新该时间；状态窗口按
45 秒新鲜度判断 Backend 连接，不能将历史 `connected` 布尔值永久显示为在线。Core 状态同时
校验受控进程身份与快照 `updated_at` 新鲜度；GUI 只展示状态，不承担 Watchdog 职责。

`worker-state.json` 与 Runtime 快照分离，只记录 Core 的 PID、启动时间、EXE 绝对路径和 Device
ID，不包含 Token。GUI/控制入口必须联合校验这些字段，不能只凭 PID 操作未知进程。

发行包中的 `ecommerce-worker.exe` 默认打开同一个 Tkinter 状态/配置/诊断窗口；
`打开Worker状态.cmd` 是兼容入口。状态页与诊断页只读脱敏快照，配置页只写 Backend URL、
DPAPI Token、只读 Device 身份和经过 6.3.6 校验的 ShadowBot 路径。窗口不提供任务创建、
Application 参数、账号、店铺或 Skill 管理；关闭窗口不停止 Worker Core。
